### Claude

#### 한 줄 답
가능하다. 핵심은 **요청**과 **강제**를 나누는 것이다. CLAUDE.md 같은 파일에 적은 글은 Claude에게 하는 **요청**(맥락)이라 어겨질 수 있다. 꼭 지켜야 하는 것은 권한 규칙·훅·샌드박스·CI처럼 Claude가 넘을 수 없는 장치로 막는다. 공식 문서도 CLAUDE.md는 강제 설정이 아니며, 무조건 막을 동작은 PreToolUse 훅으로 막으라고 안내한다.

※ 적어 주신 목록의 이름 몇 개는 실제와 다르다 (`setting.json` → `settings.json`, `Claude.md` → `CLAUDE.md` 등). 자세한 건 6번에 있다.

#### 낱말
- 훅(hook): 편집하기 전, 편집한 뒤, 끝내기 전처럼 정해진 순간에 자동으로 도는 스크립트
- 샌드박스: Claude가 실행한 셸 명령이 정한 폴더 밖에 쓰거나 허락하지 않은 곳에 접속하지 못하게 운영체제 수준에서 막는 기능 (읽기는 기본으로 대부분 허용)
- 세션: Claude와 나누는 대화 하나. 아이폰 앱 사이드바의 대화 하나가 세션 하나다. Claude는 그 대화에서 읽은 파일과 한 생각(맥락)만 기억한다 (4-1)
- 워크트리(worktree): 같은 저장소를 다른 폴더에 한 번 더 꺼내 놓고, 그 폴더에서 다른 브랜치로 일하는 git 기능. 작업 폴더를 하나 더 만드는 것이다 (4-2)
- 인수 테스트: 명세의 인수 조건을 그대로 옮긴 테스트. "다 됐다"의 기준이다
- 태그(tag): 커밋 하나에 붙이는 이름표. 브랜치는 새 커밋을 따라 앞으로 가지만, 태그는 누가 일부러 옮기지 않는 한 그 커밋에 그대로 있다. 그래서 "승인한 그 시점"을 가리키는 데 쓴다 (4-3)
- 서브에이전트: Claude가 일을 떼어 맡기는 보조 Claude. 따로 맥락을 갖고 결과만 돌려준다
- fork: 지금까지의 대화를 그대로 물려받아 갈라져 나온 서브에이전트 (GitHub 저장소 fork와 다르다)
- CI: 코드를 올리면 서버가 자동으로 빌드·테스트하는 장치 (주제 3의 CI/CD)
- 브랜치 보호: 정한 검사와 사람 승인을 통과해야만 main에 합칠 수 있게 하는 GitHub 설정
- lint: 코드 형식과 흔한 실수를 자동으로 찾는 검사
- diff: 바뀐 부분만 모아 보여 주는 것
- 권한 모드: Claude가 무엇을 묻고 무엇을 바로 할지 정하는 방식 (5번)

#### 전체 흐름

```
1. 사람: Why·What을 정리하고
   명세를 승인한다
2. Claude(plan 모드): 구현 방법 조사,
   영향 분석, 대안 → 계획 → 사람 승인
3. 다른 세션: 인수 테스트를 먼저 쓴다
4. 구현(새 세션, 필요하면 worktree):
   코드·테스트,
   훅이 테스트 결과를 되돌려 준다
5. 검증(구현과 분리): CI 테스트,
   보안 검사, 리뷰 에이전트, 사람 리뷰
6. 배포 승인(사람): 브랜치 보호,
   CI 배포 승인
7. 운영 측정: 장애·성능·보안·비용·가치
   → 명세·규칙·테스트를 고친다 → 1로
```

#### 1. 사람은 Why와 What을 소유한다
- 적어 주신 일곱 가지 질문(왜 필요한가, 누구의 문제인가, 무엇을 만드나, 무엇을 바꾸면 안 되나, 어떤 위험을 허용하나, 무엇이 완료인가, 누가 운영 반영을 승인하나)은 그대로 **명세의 앞부분 칸**이 된다 (3번의 템플릿). 사람이 쓰고 사람이 승인한다.
- Claude가 도울 수 있는 일은 **빈칸 찾기**다. 큰 기능을 만들 때 공식 권장 방법은 이렇다. Claude가 사람을 **인터뷰**한 뒤 명세(`specs/<기능>/spec.md`)로 정리하게 하고, 구현은 **새 세션**에서 시작한다. 새 세션의 구현자는 깨끗한 맥락에서 글로 된 명세만 보고 일한다.
- "운영 반영을 누가 승인하는가"를 위한 승인 기능은 Claude Code 안에 따로 없다. 브랜치 보호, CI의 배포 승인 단계, 그리고 Claude가 배포 명령을 실행하지 못하게 막는 deny 규칙을 조합해 만든다.

#### 2. Claude Code는 How의 탐색과 실행을 맡는다
- **조사·영향 분석·대안 제안 → plan 모드.** 이 모드에서 Claude는 파일을 읽고 계획만 쓴다. 사람이 승인해야 수정을 시작한다. 시작할 때 `claude --permission-mode plan`으로 켜고, 세션 중에는 `Shift+Tab`이나 `/plan`으로 들어간다.
  - 주의: plan 모드는 작업 방식이지 보안 장치가 아니다. bypassPermissions를 쓸 수 있는 대화형 터미널 세션에서는 plan 모드의 편집 차단이 강제되지 않는다. 꼭 막아야 하는 것은 deny 규칙이나 PreToolUse 훅으로 막는다.
- **코드·테스트·문서 초안, 빌드·테스트 실행, 오류 분석 → 구현 세션.** 공식 권장 순서는 탐색 → 계획 → 구현 → 커밋이다. 무엇보다 먼저 "Claude가 직접 돌려 볼 수 있는 확인 방법(테스트, 빌드)을 줘라"를 강조한다. 확인 방법이 없으면 Claude는 "다 된 것처럼 보이면" 멈추고, 결국 사람이 검증을 떠맡게 된다.
- **대규모 반복 변경 →** 일을 여러 서브에이전트에게 나눠 맡기거나, `claude --worktree`로 세션을 여러 개 열어 동시에 돌린다.
- **PR 설명과 변경 요약 →** 커밋·PR 단계에서 Claude가 쓴다.

#### 3. 명세가 구현의 기준이다 (가장 어려운 부분)
**이렇게 쓴다**
1. Claude가 나를 인터뷰하게 해서, 아래 템플릿의 칸을 채운다. 코드를 먼저 조사해야 하면 plan 모드로 시작하고, 계획을 승인한 뒤 명세를 쓰게 한다 (4-3의 ①).
2. 답할 수 없는 곳은 `[NEEDS CLARIFICATION]`으로 남긴다.
3. 표시가 0개가 될 때까지 사람이 답한다.
4. 다른 세션이 인수 조건을 테스트로 바꾼다 (4-3의 ②).
5. 사람이 승인한 뒤, 새 세션에서 구현한다.

**왜 어려운가.** 사람 머릿속의 "당연한 것"은 글로 잘 나오지 않는다. AI는 그 빈칸을 그럴듯하게 채운다. 그래서 핵심은 빈칸을 없애는 게 아니라 **빈칸을 드러내 표시하는 것**이다.

**좋은 명세의 조건** (여러 도구·가이드의 공통점)
- **관찰할 수 있는 행동으로 쓴다.** "큰 파일을 잘 처리한다" 대신 "10MB를 넘으면 오류 배너를 보여 준다"라고 쓴다. 기준은 코드를 본 적 없는 테스터도 통과 여부를 판단할 수 있느냐다 (OpenSpec 가이드).
- **요구사항 하나에 행동 하나.** "시스템은 ~해야 한다(MUST)"로 쓰고 번호를 붙인다 (FR-001).
- **인수 조건은 정해진 틀로 쓴다.** Given(상태) / When(행동) / Then(결과)이나 EARS("~인 동안, ~할 때, 시스템은 ~해야 한다")를 쓴다.
- **바꾸면 안 되는 것을 따로 적는다.** AWS Kiro의 버그 명세에는 "바뀌지 않아야 할 동작" 칸이 따로 있고, 그 내용을 회귀 테스트로 만든다.
- **모르는 것은 표시하고 묻는다.** GitHub Spec Kit은 범위·보안·사용자 경험에 크게 영향을 주는 빈칸에 `[NEEDS CLARIFICATION]`을 단다 (최대 3개). 사소한 것은 합리적 기본값을 가정으로 적는다. 표시가 남아 있으면 명세가 완성되지 않은 것으로 보고, 질문 단계에서 해결한다.
- **완료 조건은 확인할 수 있게 쓴다.** 측정 가능한 끝 상태 하나, 확인 방법(예: `npm test`가 0으로 끝남), 지켜야 할 제약을 적는다. `/goal`로 이 조건을 주면 별도 모델이 매 턴 충족 여부를 판단한다. 다만 그 모델은 명령을 직접 실행하지 않고 대화에 남은 결과를 보고 판단한다. 그러니 Claude가 테스트를 실행해 결과를 대화에 남기게 한다.
- **결정은 ADR로 남긴다.** 짧게, 번호를 붙여 쓴다. Nygard 형식(제목, 상태, 맥락, 결정, 결과)이나 MADR을 쓴다. 위치(`docs/adr/` 또는 `docs/decisions/`)는 하나로 정해 CLAUDE.md에 적는다.

**명세의 수준** (Thoughtworks 분류)
- spec-first: 작업 전에 명세를 쓴다.
- spec-anchored: 작업 뒤에도 명세를 유지하고, 기능을 바꿀 때 명세도 같이 고친다. ← **이 방법론의 목표**
- spec-as-source: 명세가 주된 소스가 되고 코드는 거기서 나온다.

**도구** (처음엔 아래 템플릿 하나로 충분하다)
- GitHub Spec Kit: 원칙 → 명세 → (선택) 질문 → 설계 → 작업 목록 → 구현 → 수렴 점검. 수렴 점검(converge)은 구현을 명세·계획과 대조해 남은 일을 추가하므로 4번의 검증과도 이어진다. Claude Code에는 `.claude/skills`에 skill로 설치된다.
- AWS Kiro: 요구사항·설계·작업 3개 문서, EARS 표기
- OpenSpec: 바뀐 부분만 델타로 기록

#### 4. 생성과 검증을 분리한다 (지금 Claude Code에서)
**짧게**
1. 인수 테스트는 구현 **전에**, **다른 세션**이 쓴다.
2. 구현은 또 다른 새 세션이 하고, 그 세션은 테스트와 명세를 고치지 못하게 막는다. 다른 일과 동시에 할 때만 worktree에서 한다 (4-1).
3. 검증은 CI에서 다시 돌리는 테스트, 읽기 전용 리뷰 에이전트, 사람 리뷰가 맡는다.

Claude Code에 "생성 → 검증" 파이프라인이 통째로 들어 있지는 않아서, 이미 있는 기능을 이렇게 조합한다.

**생성 경로: 승인된 명세 → 구현 에이전트 → 자체 테스트**
- 승인된 명세를 가리키며 **새 세션**을 연다. 순서대로 하나씩 하면 같은 폴더에서 새 세션만 열면 된다. 다른 일과 동시에 하려면 worktree에서 연다 (4-1. 여는 법은 4-3의 "동시에 하고 싶을 때", 처음 쓸 때 걸리는 것은 4-2).
- 편집할 때마다 피드백을 받는다. PostToolUse 훅으로 편집 뒤 lint와 빠른 테스트를 돌린다. 실패하면 스크립트가 `exit 2`로 끝나야 stderr의 오류 내용이 Claude에게 전달된다 (`exit 0`이면 stderr는 전달되지 않는다. `exit 0`으로 끝내면서 JSON으로 `decision: "block"`과 `reason`을 출력하는 방법도 있다). PostToolUse는 이미 끝난 편집을 되돌리지는 못한다.
- 끝내기 전에 관문을 둔다. Stop 훅으로 테스트가 통과하기 전에는 끝내지 못하게 막거나, `/goal`로 "npm test가 0으로 끝날 때까지"를 완료 조건으로 준다. 다만 Stop 훅은 도구 호출 없이 8번 연속 막히면 Claude Code가 그냥 멈춘다. 그래서 최종 확인은 CI에서 한다.
- 한계: 여기까지는 구현자 **자신의** 검사다. 독립 검증이 아니다.

**검증 경로: 승인된 명세 → 독립 테스트·보안 검사 → 리뷰 에이전트 → 사람 리뷰**
- **독립 테스트.** 인수 테스트는 구현보다 먼저, 다른 세션이 쓴다. 공식 문서도 한 방법으로 "한 세션이 테스트를 쓰고, 다른 세션이 그 테스트를 통과하는 코드를 쓰게 한다"를 소개한다.
  - 구현 세션은 그 테스트 파일과 명세를 고치지 못하게 막는다 (5번의 설정 예시).
  - 막아야 하는 이유: Claude Code가 기본으로 보호하는 경로(`.git`, `.claude` 등)에 `tests/`와 `specs/`는 없다. 막지 않으면 구현 세션이 자기 테스트나 명세를 고쳐서 "통과"시킬 수 있다.
- **CI에서 다시 돌리기.** 구현 세션 밖에서 전체 테스트를 다시 돌린다. 훅으로 돌린 테스트는 구현자 자신의 피드백일 뿐이다.
- **보안 검사.** `/security-review`(현재 브랜치와 기본 브랜치의 차이를 검사)에, CI의 정적 분석과 의존성 검사를 더한다.
- **리뷰 에이전트.** 새 맥락에서 시작하는 리뷰어를 둔다. 공식 문서도 방금 쓴 코드에 치우치지 않도록 새 맥락이 리뷰에 낫다고 말한다.
  - `.claude/agents/`에 리뷰어를 만들고, `tools`에는 읽기 도구만 준다. 명세 경로와 diff만 넘긴다.
  - **fork는 리뷰어로 쓰지 않는다.** fork는 구현자의 대화와 추론을 그대로 물려받아, 같은 착각을 하기 쉽다.
  - 다른 선택지
    - `/code-review`: 로컬 diff나 PR을 리뷰한다.
    - GitHub의 Claude Code Review: Team·Enterprise용 연구 미리보기다. 저장소 루트의 `REVIEW.md`를 리뷰 기준으로 읽는다. 로컬 `/code-review`는 REVIEW.md를 읽지 않으니, 같은 기준을 로컬에도 쓰려면 CLAUDE.md에도 적는다.
    - GitHub Actions(`anthropics/claude-code-action`)
- **사람 리뷰.** 마지막 관문이다. 브랜치 보호로 사람이 승인하지 않으면 머지할 수 없게 한다.

**주의 세 가지**
- 서브에이전트는 맥락(대화 기록)은 분리되지만, 부모 세션이 auto·acceptEdits·bypassPermissions 모드면 그 모드를 따르고 자기 `permissionMode` 설정은 무시된다. 그래서 읽기 전용은 `tools` 목록으로 강제한다.
- Claude Code Review의 체크는 **머지를 막지 않는다** (항상 neutral로 끝난다). 막으려면 CI에서 결과를 읽어 실패로 바꿔야 한다.
- 리뷰어도 같은 폴더의 파일을 본다. 구현자가 남긴 메모나 커밋하지 않은 파일을 읽을 수 있으니, 리뷰어에게 넘기는 것은 **명세와 diff로 한정**한다. 커밋된 것만 보게 하려면 깨끗한 worktree의 새 세션이나 CI에서 검증한다.

<details>
<summary><b>리뷰 에이전트 예시 펼치기</b> (.claude/agents/spec-reviewer.md)</summary>

```markdown
---
name: spec-reviewer
description: 구현이 끝난 뒤, 승인된 명세와 diff만 보고 독립적으로 검토할 때 사용한다.
tools: Read, Grep, Glob
model: inherit
---
너는 이 변경을 처음 보는 리뷰어다.
위임 메시지로 받은 명세 경로와 diff만 근거로 판단한다.
1. 명세의 인수 조건마다 충족 여부와 근거(파일:줄)를 적는다.
2. "바꾸면 안 되는 것"을 건드린 곳이 있는지 찾는다.
3. 명세에 없는 동작이 추가됐는지 찾는다.
코드는 고치지 않는다. 결과만 보고한다.
```

`tools`에 Bash를 넣지 않았다. Bash로는 파일을 쓸 수도 있어서 읽기 전용이 깨지기 때문이다. 그래서 diff는 위임할 때 함께 넘긴다.

#### 4-1. "다른 세션"은 새 폴더를 만들라는 뜻일까? (추가 질문)
**한 줄 답:** 아니다. 독립 검증에 필요한 것은 새 폴더가 아니라 **새 세션(새 대화)**이다. 같은 폴더에서 새 대화를 열면 된다. 여기에 순서·권한·CI(아래 표)를 더하면 독립 검증이 되는데, 이것도 새 폴더 없이 갖출 수 있다. 새 폴더(worktree)는 두 세션이 **동시에** 파일을 고칠 때 필요하다.

**세션과 worktree는 나누는 대상이 다르다**
- **세션 = Claude와의 대화 하나.** 아이폰 앱 사이드바에 보이는 대화 하나가 세션 하나다. Claude는 그 대화에서 읽은 파일과 한 생각만 기억한다. 새 세션의 Claude는 앞 대화에서 무슨 일이 있었는지 모른다.
- **worktree = 작업 폴더를 하나 더 만드는 git 기능.** 같은 저장소를 다른 폴더에 한 번 더 꺼내 놓아서, 두 작업이 서로의 파일을 건드리지 않게 한다 (4-2).
- 정리하면 세션은 **"무엇을 기억하나"**를, worktree는 **"어느 폴더의 파일을 고치나"**를 나눈다. 독립 검증에 중요한 것은 앞의 것이다.

**코드 리뷰로 생각하면 쉽다**
- 작성자가 자기 코드를 다시 보면 같은 착각을 하기 쉽다. 그래서 코드를 처음 보는 동료에게 리뷰를 맡긴다.
- 새 세션의 Claude가 그 "처음 보는 동료"다. 동료가 리뷰하려고 새 폴더가 필요하지는 않다.
- 거꾸로, 새 worktree를 만들어도 같은 세션(같은 대화)이 검증하면 독립이 아니다. 작성자가 자리만 옮겨 자기 코드를 다시 보는 셈이다.

**"독립"을 만드는 다섯 가지 분리**

| 분리 | Claude Code에서 | 막아 주는 문제 |
|---|---|---|
| 대화(기억) | 새 세션, 서브에이전트 (fork 말고) | 자기 코드에 너그러움, 같은 착각 |
| 순서 | 인수 테스트를 구현 **전에** 커밋 | 코드에 맞춰 쓴 테스트 |
| 권한 | deny 규칙, `tools` 목록 | 테스트·명세를 고쳐서 "통과" |
| 실행 장소 | CI | "내 컴퓨터에선 됐다" |
| 작업 폴더 | worktree | 동시 작업끼리 파일이 섞임 |

새 작업 폴더(worktree)는 다섯 가지 가운데 하나일 뿐이다. 나머지 넷은 폴더를 새로 만든다고 생기지 않는다.

**새 작업 폴더(worktree)가 필요한 때**
- 세션 두 개가 **동시에** 파일을 고칠 때. 한 폴더에서 동시에 고치면 서로의 변경이 같은 브랜치에 섞인다.
- 구현을 맡겨 둔 채 원래 폴더에서 다른 일을 계속하고 싶을 때.
- 검증하는 쪽이 **커밋된 코드만** 보게 하고 싶을 때. 같은 폴더에는 구현자가 남긴 메모나 커밋하지 않은 파일이 있을 수 있다. 가장 깨끗한 곳은 CI다.
- 내 작업을 건드리지 않고, PR로 올라온 코드만 따로 꺼내 돌려 보고 싶을 때 (4-3의 ⑥).

**저장소 안에 생기긴 하지만, 커밋해서 "관리"하는 폴더는 아니다**
- Claude Code가 만드는 worktree는 저장소 안 `.claude/worktrees/` 아래에 생긴다. 이 폴더는 `.gitignore`에 넣어 커밋하지 않는다.
- 코드를 복사해 만든 별도 프로젝트도 아니다. 같은 저장소의 작업 폴더를 하나 더 만든 것이다.
- 잠깐 쓰고 지운다. 결과는 브랜치 → PR → main으로 돌아오고, 폴더는 정리한다.

**아이폰에서 쓰는 클라우드 세션이라면**
- claude.ai/code의 클라우드 세션은 세션마다 별도의 가상 머신에서 돌고, 저장소도 세션마다 새로 받는다.
- 그래서 클라우드에서는 새 세션을 열면 대화도 작업 폴더도 저절로 따로다. 세션끼리는 git 브랜치와 PR로 주고받는다.
- 클라우드 세션에서는 `/clear`를 쓸 수 없다. 새 대화가 필요하면 사이드바에서 새 세션을 연다.

#### 4-2. worktree란? (추가 질문)
**한 줄 정의:** 저장소 하나에 작업 폴더를 여러 개 두는 git 기능이다. 폴더마다 다른 브랜치를 꺼내 놓고, 커밋 기록은 하나를 같이 쓴다.

**왜 필요한가**
- 보통은 저장소 하나에 작업 폴더 하나다. 폴더 하나에는 한 번에 브랜치 하나만 꺼내 놓을 수 있다.
- 다른 브랜치를 보려면 `git switch`로 바꿔야 하고, 그러면 폴더의 파일이 그 브랜치 것으로 바뀐다. 커밋하지 않은 변경은 그대로 따라오고, 겹치는 파일이 있으면 git이 전환을 거부한다. 그래서 보통 먼저 커밋하거나 `git stash`로 치워 둔다.
- worktree를 쓰면 브랜치마다 폴더가 따로 있다. 바꿀 필요 없이 두 브랜치를 나란히 열어 둔다.

**모양**
```
my-app/        ← 원래 폴더 (main)
├── .git/      ← 기록은 여기 하나
├── src/
└── .claude/worktrees/
    ├── login/ ← worktree-login 브랜치
    │   ├── .git  (주소만 적힌 파일)
    │   └── src/
    └── pr-12/ ← PR 12번 코드
```
worktree 안의 `.git`은 폴더가 아니라 파일이다. "기록은 my-app/.git/worktrees/login에 있다"는 주소만 적혀 있다.

**복사, clone, worktree 비교**

| | 폴더 복사 | clone 한 번 더 | worktree |
|---|---|---|---|
| 커밋 기록 | 따로 | 따로 | 하나를 같이 씀 |
| 한쪽 커밋이 다른 쪽에 | 안 보임 | push·fetch 뒤 | 바로 보임 |
| 같은 브랜치를 두 곳에 | 막지 않음 | 됨 | git이 막는다 |
| 정리 | 폴더 삭제 | 폴더 삭제 | `git worktree remove` |

같은 브랜치를 두 곳에 꺼내는 것을 git이 막기 때문에, 두 작업 폴더가 같은 브랜치를 동시에 고치다 꼬이는 일이 없다.

**git 명령으로 직접**
```bash
# 새 폴더 + 새 브랜치
git worktree add ../my-app-login -b login
# 이미 있는 브랜치를 꺼내기
git worktree add ../my-app-x login-lock
# 목록
git worktree list
# 정리
git worktree remove ../my-app-login
```
`remove`는 고친 파일이나 추적하지 않는 새 파일이 있거나 worktree가 잠겨 있으면 거부한다. 폴더를 지워도 브랜치는 남는다.

**Claude Code에서**
- `claude --worktree login` (줄여서 `-w`): `.claude/worktrees/login/` 폴더를 만들고 새 브랜치 `worktree-login`에서 세션을 시작한다. 이름을 빼면 이름을 지어 준다.
- **어디서 갈라지나:** 기본은 원격의 기본 브랜치(보통 main)다.
  - 지금 브랜치의 커밋(아직 push하지 않은 것 포함)에서 시작하려면 설정에 `"worktree": {"baseRef": "head"}`를 넣는다.
  - 브랜치 이름은 지정할 수 없다. 이미 있는 브랜치로 하려면 git으로 `.claude/worktrees/<이름>`에 먼저 꺼내 두고 `claude --worktree <이름>`으로 연다. 이미 있는 폴더 이름을 주면 새로 만들지 않고 그 worktree를 연다 (4-3에서 이렇게 쓴다).
- **PR 번호로도 만든다:** `claude --worktree "#12"`를 실행하면 `.claude/worktrees/pr-12`에 그 PR의 코드를 꺼낸다. 따옴표를 붙여야 셸이 `#`를 주석으로 읽지 않는다.
- 세션 중에 "worktree에서 작업해"라고 말해도 만들어 준다.
- 서브에이전트 설정에 `isolation: worktree`를 쓰면 그 서브에이전트는 늘 임시 worktree에서 일한다. `/batch`도 서브에이전트마다 worktree를 따로 쓴다.

**한 줄로: worktree는 파일만 나눈다. 보안 장치가 아니다.**

<details>
<summary><b>처음 쓸 때 걸리는 것, 지켜 주는 것과 못 지키는 것 펼치기</b></summary>

**처음 쓸 때 걸리는 것**
- `.claude/worktrees/`를 `.gitignore`에 넣는다. 그러지 않으면 원래 폴더에서 추적하지 않는 파일로 잔뜩 보인다.
- 새로 꺼낸 폴더라서 `node_modules` 같은 설치물이 없다. 그 폴더에서 다시 설치한다.
- `.env`처럼 git에 없는 파일도 없다. 프로젝트 루트의 `.worktreeinclude`에 적어 두면 Claude Code가 만드는 새 worktree에 복사해 준다 (gitignore된 파일만).
- 훅이 지금 작업 중인 폴더를 알아야 하면 훅 입력 JSON의 `cwd`를 읽는다. `$CLAUDE_PROJECT_DIR`는 `claude --worktree`로 시작했으면 worktree를 가리키지만, 세션 중에 worktree로 들어갔으면 원래 폴더를 가리킨다.
- **끝낼 때:** 바뀐 것(고친 파일, 새 파일, 새 커밋)이 없으면 이름 없는 세션은 worktree를 자동으로 지우고, 이름 붙인 세션은 먼저 묻는다. 바뀐 것이 있으면 남길지 지울지 묻는다.
- `claude -p`로 돌린 것은 잠긴 채 남는다. `git worktree unlock` → `git worktree remove`로 지우고, 브랜치는 `git branch -D worktree-<이름>`으로 지운다.

**지켜 주는 것**
- Claude Code가 연 worktree 세션(`--worktree`로 시작, 세션 중에 worktree로 들어감, 그 세션을 다시 엶)은 원래 폴더의 파일을 Edit·Write로 고치지 못한다. 원래 폴더에서 도는 명령, 원래 폴더를 대상으로 하는 git 명령(`git -C <원래 폴더>` 등)도 막는다.
- git으로 만든 worktree 폴더에 `cd`로 들어가 그냥 `claude`를 실행하면 이 검사가 없다. 그때는 권한 규칙과 샌드박스만 남는다.
- `cp`나 `>`처럼 셸 명령이 직접 쓰는 파일까지 쫓지는 않는다. 그건 권한 규칙과 샌드박스 몫이다.

**같이 쓰는 것**
- `.git`(커밋 기록)
- Bash 명령에 "다시 묻지 않기"로 허락한 권한. 원래 폴더의 `.claude/settings.local.json`에 저장되어 모든 worktree에 적용된다 (v2.1.211 이상. Windows 등은 예외).
- 프로젝트에 설치한 플러그인
- auto memory (같은 저장소면 하나)

**나누지 않는 것**
- 공식 문서는 worktree를 **파일 분리**로만 설명한다. 그러니 포트, 로컬 DB, 네트워크, 환경 변수는 나뉘지 않는다고 보는 게 맞다 (문서에서 끌어낸 추론). 예를 들어 두 worktree에서 같은 포트(3000)로 서버를 띄우면 부딪친다.
- 위의 격리 검사는 셸 명령의 쓰기를 쫓지 않으니 샌드박스를 대신하지 못한다.

</details>

#### 4-3. 구체적으로: 기능 하나를 생성과 검증으로 나눠 돌려 보기 (추가 질문)
**한 줄 답:** 기준을 쓰는 세션, 코드를 쓰는 세션, 검사하는 세션을 따로 둔다. 서로 다른 대화라서 앞 단계의 생각을 물려받지 않는다. 기준은 구현 **전에** 커밋하고 태그로 표시해 두고, 구현하는 동안 바뀌지 않았는지 git으로 확인한다.
- 여기서 **기준**은 사람이 승인한 명세와 인수 테스트다.

예: "로그인을 5번 틀리면 15분 잠금" 기능. 명세는 3번의 템플릿을 쓴다. 아래 명령은 노트북 터미널 기준이다. 아이폰(클라우드)에서 하는 법은 맨 끝에 있다.

**한눈에**

| 단계 | 누가 | 지키는 장치 |
|---|---|---|
| ① 명세 | 사람 + 세션 A | 사람 승인 |
| ② 인수 테스트 | 세션 B | 실패 확인, 승인 태그 |
| ③ 구현 | 세션 C | deny 규칙, 훅 |
| ④ 검증 | 세션 D + 리뷰어 | 태그 비교, 읽기 전용 |
| ⑤ CI | GitHub Actions | 브랜치 보호 |
| ⑥ 사람 리뷰 | 사람 | 브랜치 보호 |

- 생성 경로는 ③, 검증 경로는 ②④⑤⑥이다.
- 세션은 A, B, C, D 넷이지만 폴더는 ①~④ 모두 원래 폴더 하나로 된다. 동시에 다른 일을 할 때만 ③④를 worktree로 보낸다 (아래 "동시에 하고 싶을 때").

**① 명세: 세션 A**
```bash
git switch -c login-lock
claude
```
> 로그인 잠금 기능을 만들고 싶다. 질문을 하나씩 던져 나를 자세히 인터뷰해라. 끝나면 specs/login-lock/spec.md에 명세만 써라. 코드는 쓰지 마라.

- 코드를 먼저 조사해야 하면 plan 모드(`claude --permission-mode plan`)로 시작한다. plan 모드에서는 파일을 고치지 못하니, 계획을 승인한 뒤 `spec.md`를 쓰게 한다.
- 사람이 `spec.md`를 읽고 고친 뒤 승인하고 커밋한다.
- A의 대화에는 인터뷰에서 나눈 말이 다 들어 있다. 그래서 다음 단계는 A에게 맡기지 않는다.

**② 인수 테스트: 세션 B (새 세션)**
```bash
claude   # 새 터미널. 같은 터미널이면 /clear
```
> specs/login-lock/spec.md의 인수 조건마다 tests/acceptance/login-lock.test.ts에 테스트를 하나씩 써라. 명세에 적힌 것만 근거로 한다. 구현 코드는 쓰지 마라. 테스트를 돌려 모두 실패하는 것까지 확인해라. 명세가 모호해서 테스트를 쓸 수 없는 곳은 목록으로 보고해라.

- **B를 따로 두는 이유:** B는 명세에 **글로 적힌 것**만 안다. 그래서 명세의 빈칸이 바로 드러난다. "모호해서 못 쓰겠다"는 보고가 곧 명세 검토다 (3번 템플릿의 "확인 필요" 칸과 같은 역할). 이런 보고가 오면 ①로 돌아가 명세를 고친 뒤 ②를 다시 한다.
- **모두 실패해야 하는 이유:** 구현 전에 통과하는 테스트는 아무것도 검사하지 않는 테스트다. 실패 이유도 본다. "기능이 없어서" 실패해야 한다. 오타나 import 오류로 실패하는 것은 확인이 아니다.
- 사람이 "테스트가 인수 조건과 맞나"를 보고 커밋한다.
- 승인한 지점에 태그를 달고 **바로 올린다**. 이 태그가 "승인된 기준"의 표시다. 내 컴퓨터에만 있는 태그는 셸을 쓰는 누구든(구현 세션 포함) 옮길 수 있어서 바로 올린다.
```bash
git tag spec-approved/login-lock
git push origin spec-approved/login-lock
```

**③ 구현: 세션 C (새 세션, 기준은 못 고친다)**
```bash
claude --settings \
  .claude/implement-settings.json
```
> specs/login-lock/spec.md를 구현해라. tests/acceptance/login-lock.test.ts가 모두 통과해야 끝이다. 테스트와 명세는 고칠 수 없다. 테스트가 틀렸다고 생각되면 고치지 말고 이유를 보고해라.

- `implement-settings.json`은 5번 설정 예시에 있는 파일이다 (`specs/`와 `tests/acceptance/` 편집 금지).
- 샌드박스를 켜 두면 이 편집 금지 경로가 Bash 명령에도 적용된다. 그래서 `sed` 같은 명령으로 테스트를 고치는 길도 대부분 막힌다. 그래도 빈틈이 있을 수 있으니 ④에서 git으로 한 번 더 확인한다.
- 편집 뒤 lint 훅, 끝내기 전 테스트 관문(Stop 훅이나 `/goal`)은 4번 그대로 쓴다.
- 테스트가 모두 통과하면 커밋한다 (C에게 시키거나 사람이 확인하고). 커밋하지 않으면 ④의 `git diff main...HEAD`에 구현이 잡히지 않는다.
- "테스트가 틀렸다"는 보고가 오면 사람이 판단한다. 기준을 바꿀지는 사람 몫이다 (원칙 1). 바꾸기로 했다면 ②로 돌아가 C가 아닌 새 세션이 고치고, 새 이름으로 태그를 달아 바로 올린다 (예: `spec-approved/login-lock-2`). ④의 명령과 CI 기준 검사의 태그 이름도 새 태그로 바꾼다. 옛 태그와 비교하면 승인한 수정까지 "기준이 바뀌었다"로 잡혀 CI가 계속 실패한다.

**④ 검증: 세션 D (새 세션, 구현 과정을 모른다)**

먼저 기준이 그대로인지 본다. D에게 시키거나 사람이 직접 친다.
```bash
git fetch --force --tags origin
git diff --stat \
  spec-approved/login-lock \
  -- specs/login-lock/ \
     tests/acceptance/login-lock.test.ts
```
- 첫 줄은 올려 둔 태그를 다시 받아 내 컴퓨터의 태그를 덮어쓴다. 구현하는 동안 내 컴퓨터의 태그가 옮겨졌을 수 있어서다 (②). 이때 `[tag update]`가 나오면 누군가 태그를 옮긴 것이니 그것부터 확인한다.
- 둘째 명령은 아무것도 나오지 않아야 한다. 무언가 나오면 구현하는 동안 기준이 바뀐 것이다.
- `HEAD`를 붙이지 않아서 커밋하지 않은 수정까지 잡힌다.

그다음 D에게 맡긴다.
> spec-reviewer 에이전트에게 specs/login-lock/spec.md와 `git diff main...HEAD` 결과를 넘겨 검토하게 해라. 그리고 /security-review를 돌려라.

- **리뷰어를 C가 아니라 D에서 부르는 이유:** 위임 메시지를 C가 쓰면 C의 설명("이건 이래서 이렇게 했다")이 섞인다. D는 구현 과정을 모르니 명세와 diff만 넘긴다.

**⑤ CI**
```bash
git push -u origin login-lock
```
- PR을 연다. CI가 깨끗한 서버에서 전체 테스트, 정적 분석, 의존성 검사를 다시 돌린다.
- ④의 기준 검사도 CI에 넣는다. 바뀐 게 있으면 1로 끝나 CI가 실패한다.
```bash
git diff --quiet \
  spec-approved/login-lock HEAD \
  -- specs/login-lock/ \
     tests/acceptance/login-lock.test.ts
```
- GitHub Actions의 `actions/checkout`은 기본으로 워크플로를 실행시킨 커밋 하나만 받는다. `fetch-depth: 0`으로 기록과 태그를 다 받게 한다.
- 경로는 이 기능의 것으로 좁혀 둔다. PR에서 CI가 검사하는 커밋은 PR을 main에 합쳐 본 커밋이라, 넓게 잡으면 main에서 바뀐 다른 명세까지 걸린다.

**⑥ 사람 리뷰**
- 브랜치 보호로 CI 통과와 사람 승인 없이는 머지가 안 되게 한다.
- **여기서 worktree가 쓸모 있는 때:** 원래 폴더에서는 다음 기능을 하고 있는데 이 PR(예: 12번)을 내 컴퓨터에서 직접 돌려 보고 싶다면, `claude --worktree "#12"`로 PR 코드만 따로 꺼낸다. 원래 폴더는 건드리지 않는다.

**동시에 하고 싶을 때 (여기서 worktree가 필요하다)**
- 예: C가 로그인 잠금을 구현하는 동안, 나는 원래 폴더에서 다음 기능(가입)의 명세를 쓰고 싶다. 한 폴더에서 동시에 하면 C의 변경과 내 변경이 섞인다.
- 그래서 원래 폴더는 다음 기능 브랜치로 옮기고, login-lock 브랜치는 worktree로 꺼내 C에게 준다.
```bash
# ②까지 커밋하고 태그를 올린 상태에서
git switch -c signup main
git worktree add \
  .claude/worktrees/login login-lock
claude --worktree login --settings \
  .claude/implement-settings.json
```
- 마지막 줄은 worktree를 새로 만들지 않고 방금 꺼낸 것을 연다. 브랜치 이름이 login-lock 그대로라 ④⑤ 명령을 바꾸지 않아도 된다.
- `--worktree`로 열어야 Claude Code의 격리 검사가 켜진다 (4-2).
- `--settings` 경로는 명령을 친 원래 폴더 기준이다. 원래 폴더는 이제 main에서 갈라진 signup이니, `implement-settings.json`은 main에 커밋해 둬야 한다. login-lock에만 있으면 파일을 찾지 못해 멈춘다.
- ④의 세션 D도 같은 worktree에서 새로 연다: `claude --worktree login`. ④의 기준 검사를 사람이 직접 칠 때도 먼저 `cd .claude/worktrees/login`으로 들어간다. 원래 폴더(signup)에서 치면 기준 파일이 모두 지워진 것처럼 나온다.
- 머지가 끝나면 직접 정리한다: `git worktree remove .claude/worktrees/login`
- 기능 두 개를 처음부터 동시에 시작할 때는 더 간단하다. 터미널 두 개에서 `claude -w login`, `claude -w signup`을 실행하면 각자 원격 main에서 새 브랜치(`worktree-login`, `worktree-signup`)로 갈라진다. 이때는 ①의 `git switch`가 필요 없고, ⑤의 push는 `git push -u origin worktree-login`으로 바꿔 친다.

**아이폰(클라우드)에서 할 때**
- 세션 A~D를 사이드바에서 하나씩 새로 연다. 세션마다 별도의 머신이라 폴더가 섞일 걱정은 없다.
- 단계가 끝날 때마다 login-lock 브랜치에 push하고, 다음 세션은 그 브랜치에서 시작한다.
- 아이폰에서 여는 클라우드 세션에는 `--settings` 같은 명령줄 옵션을 줄 수 없다. 클라우드 세션은 저장소에 커밋된 `.claude/settings.json`을 읽는다.
- 그래서 ②의 승인 커밋에, 이 기능의 기준을 막는 deny 규칙을 `.claude/settings.json`의 `permissions` 안에 함께 넣는 방법이 있다 (설계 제안).
```json
"permissions": {
  "deny": [
    "Edit(**/specs/login-lock/**)",
    "Edit(**/tests/acceptance/login-lock*)"
  ]
}
```
- 이미 `permissions`가 있으면 그 안 `deny` 목록에 두 줄만 더한다. `permissions`를 하나 더 붙이면 뒤의 것만 남아 기존 deny 규칙이 사라진다.
- 그 뒤 이 브랜치에서 여는 세션은 모두 기준을 고치지 못한다. C, D뿐 아니라 ③에서 기준을 고치러 여는 새 세션도 막힌다. 그래서 클라우드에서 기준을 바꾸기로 했다면 사람이 GitHub에서 명세·테스트를 직접 고치고 새 태그를 단다. 세션에 맡기려면 이 deny 규칙을 잠시 빼는 커밋을 하고, 고친 뒤 규칙을 되돌리는 커밋과 함께 새 태그를 단다.
- 이 규칙은 main에 합친 뒤에도 남는다. 그러면 "승인된 명세는 사람만 고친다"는 규칙이 된다.
- **클라우드 세션은 태그를 올리지 못한다.** GitHub 프록시가 브랜치가 아닌 push(태그 등)를 거부해서, ②의 `git push origin spec-approved/login-lock`이 실패한다. 그래서 ②의 승인 커밋을 login-lock에 push한 뒤, ③을 시작하기 전에 사람이 태그를 만든다.
  - 아이폰뿐이면: GitHub 저장소의 Releases → Draft a new release를 연다. 태그 칸에 `spec-approved/login-lock`을 새로 쓰고, **Target을 login-lock 브랜치로 바꾼 뒤** 게시한다. Target을 기본값(main)으로 두면 엉뚱한 커밋에 달리고, 초안으로 저장만 하면 태그가 생기지 않는다.
  - 노트북이 있으면: `git fetch origin` → `git tag spec-approved/login-lock origin/login-lock` → `git push origin spec-approved/login-lock`
- 태그가 GitHub에 있어야 새로 받는 세션(C, D)과 CI가 쓸 수 있다. 기준 검사(태그 비교)는 ⑤의 CI가 맡는다.

**이 문서도 이렇게 만들었다**
- 주제 1~6은 작성한 Claude가 초안을 쓰고, 새 맥락에서 시작한 검증 에이전트들이 공식 문서와 원문에 대조해 틀린 곳을 찾았다.
- 이번 4-1~4-3도 사실 확인 에이전트와 읽기 검토 에이전트가 두 번 봤고, 찾은 문제마다 반박 에이전트가 정말 문제인지 다시 따졌다. 틀린 곳(훅의 `$CLAUDE_PROJECT_DIR`, 클라우드에서 태그 push)과 순서가 어긋난 곳 여럿을 고쳤다.
- 다만 검증 에이전트를 작성한 Claude가 직접 불렀으니, 4-3 기준으로는 "반쯤 독립"이다. 마지막 관문은 사람(당신)의 확인과 머지다.

#### 5. 자율성은 위험에 비례한다

| 위험 | 예 | 설정 |
|---|---|---|
| 낮음 (되돌릴 수 있음) | 문서, 테스트 | 편집 자동 허용(acceptEdits) + 샌드박스 |
| 중간 | 비즈니스 로직, API | 하나씩 묻기(기본 모드) + 샌드박스, diff 확인 |
| 높음 | 고객 데이터, 권한, 결제, 운영 | deny로 금지, 배포는 사람 승인 뒤 CI에서만 |

**장치별 역할**
- **권한 모드:** 기본(default, 화면에는 Manual), acceptEdits, plan, auto, dontAsk, bypassPermissions가 있다.
  - acceptEdits: 작업 폴더 안의 파일 편집은 묻지 않고 허용한다.
  - auto: 사람 대신 분류 모델이 판단한다. 운영 배포·마이그레이션, 권한 부여, force push 등은 기본으로 막는다. 그래도 분류기는 사람이 아니다.
  - dontAsk: 물어봐야 하는 것은 모두 거부한다. CI용이다.
  - bypassPermissions: 격리된 컨테이너나 VM에서만 쓰라고 안내돼 있다.
  - auto와 bypassPermissions는 프로젝트의 `settings.json`이나 `settings.local.json`에 써도 **무시된다.** 사용자 설정(`~/.claude/settings.json`), 관리자 설정, 명령줄(`--permission-mode`, `--settings`)에서 정한다.
- **권한 규칙:** deny → ask → allow 순서로 검사하고, 처음 맞는 규칙이 이긴다. 어느 범위의 deny든 allow보다 앞선다.
- **Bash 규칙은 보안 경계가 아니다.** `Bash(rm *)`로 막아도 `/bin/rm`이나 `bash -c 'rm ...'`은 막지 못한다. 운영체제 수준으로 막으려면 샌드박스를 쓴다.
  - 샌드박스는 기본으로 꺼져 있다. 켜도 설치가 안 된 환경에서는 샌드박스 없이 그냥 실행된다. 그래서 `failIfUnavailable`을 켜 둔다.
- **훅이 오류로 끝나도 작업은 막히지 않는다.** 막으려면 `exit 2`로 끝내야 한다. `exit 1`은 경고만 남기고 그대로 진행된다.
- **조직 정책은 관리자 설정(managed settings)으로 둔다.** 개발자가 덮어쓸 수 없다.

<details>
<summary><b>설정 예시 펼치기</b> (.claude/settings.json, 구현 세션 전용 설정, 보호 훅)</summary>

팀 공통 `.claude/settings.json` (낮은 위험 저장소 기준이다. 중간 위험이면 `defaultMode` 줄을 뺀다):
```json
{
  "permissions": {
    "defaultMode": "acceptEdits",
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(kubectl *)",
      "Bash(terraform apply *)"
    ],
    "ask": ["Bash(git push *)"],
    "allow": ["Bash(npm test)", "Bash(npm run lint)"]
  },
  "sandbox": { "enabled": true, "failIfUnavailable": true },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
```

구현 세션에만 거는 추가 잠금 `.claude/implement-settings.json`. 명령줄 `--settings`는 프로젝트 설정보다 우선하고, deny 목록은 합쳐진다. 주의: 이 파일에서 `/specs/**`처럼 `/`로 시작하는 경로는 **이 파일이 있는 `.claude/` 기준**으로 풀린다. 그래서 `**/`로 쓴다.
```json
{
  "permissions": {
    "deny": ["Edit(**/specs/**)", "Edit(**/tests/acceptance/**)"]
  }
}
```
실행: `claude --settings .claude/implement-settings.json`. 다른 일과 동시에 돌리려면 worktree로 연다 (4-3의 "동시에 하고 싶을 때").

보호 훅 `.claude/hooks/protect-files.sh`:
```bash
#!/bin/bash
INPUT=$(cat)
FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
case "$FILE" in
  *.env*|*/migrations/*)
    echo "Blocked: $FILE 는 사람 승인이 필요한 파일입니다" >&2
    exit 2 ;;
esac
exit 0
```
그다음 `chmod +x .claude/hooks/protect-files.sh`로 실행 권한을 준다. 실행 권한이 없으면 훅이 시작조차 못 하는데, 이때도 편집은 그대로 통과한다. `exit 2`만 차단한다. 커밋된 훅은 팀원 컴퓨터와 CI에서 실행되는 코드이므로 코드처럼 리뷰한다.

</details>

#### 6. 프로젝트 지식은 저장소에서 관리한다: 무슨 뜻?
**뜻.** 대화창에 길게 쓴 프롬프트는 세션이 끝나거나 대화가 압축(`/compact`)되면 사라진다. 다른 사람, 다른 세션, CI에서는 보이지도 않는다. 저장소의 파일은 버전 관리되고, PR로 리뷰되고, 모든 세션이 같은 내용을 본다. 즉 **"AI에게 하는 말"을 코드처럼 다루자**는 뜻이다. 공식 문서도 대화로만 준 지시는 압축 뒤에 남지 않으니 CLAUDE.md에 적으라고 한다.

**가까운 예: 이 저장소.** Daily_Think가 이미 원칙 6의 작은 예다. CLAUDE.md가 규칙이고, `index/memo.md`가 원문, `daily/`가 정리, `references/`가 근거다. 어제(10/14) CLAUDE.md에 "참조자료가 있으면 마지막에 정리" 한 줄이 들어가자, 그다음 답부터 참조자료가 붙었다. 대화로 매번 부탁하지 않아도 저장소의 규칙이 일을 바꾼 것이다. 다만 빈틈도 보인다. CLAUDE.md의 폴더 구조에 `references/`가 없고, `.claude/settings.json`도 없다. 그래서 이 저장소의 규칙은 아직 모두 "요청"이다.

**두 종류로 나눠 본다**
- Claude Code가 **스스로 읽는 것:** CLAUDE.md, `.claude/rules/`, `.claude/skills/`, `.claude/agents/`, `.claude/settings.json`
- **가리켜 줘야 읽는 것:** `docs/architecture/`, `docs/adr/`, `specs/`, `policies/`, `tests/`

※ 표가 넓어서 휴대폰에서는 옆으로 밀어서 본다.

| 무엇 | 어디에 | 언제 로드되나 | 성격 |
|---|---|---|---|
| 공통 규칙 | CLAUDE.md (200줄 이하 권장) | 매 세션 | 요청 |
| 경로별 규칙 | .claude/rules/*.md | 맞는 파일을 읽거나 고칠 때 | 요청 |
| 구조·경계 | docs/architecture/ | 가리킬 때 | 요청 |
| 기술 결정 | docs/adr/ | 가리킬 때 | 요청 |
| 요구사항·설계 | specs/ | 작업할 때 지정 | 요청, 테스트로 바꾸면 검증 |
| 조직 정책 | policies/ | 가리킬 때 | 요청, 강제는 설정으로 |
| 기대 동작 | tests/ | 실행할 때 | **검증** |
| 반복 절차 | .claude/skills/ | 맞을 때, /이름 | 요청 |
| 전문 작업자 | .claude/agents/ | 위임할 때 | 요청, 도구 목록은 강제 |
| 차단·자동화 | .claude/settings.json | 항상 | **강제** |
| 개인 학습 | auto memory (저장소 밖) | 매 세션 앞부분 | 요청, 공유 안 됨 |

**운영 요령**
- CLAUDE.md에 명세 전체를 `@import` 하지 않는다. import한 파일도 매 세션 통째로 로드된다. "명세는 `specs/<기능>/spec.md`에 있다"처럼 위치만 적는다.
- CLAUDE.md의 한 부분이 "사실"이 아니라 "절차"로 자라면 skill로 옮긴다. skill 본문은 쓸 때만 로드된다.
- CLAUDE.md 수정도 PR로 리뷰한다. 큰 모델 업데이트 뒤에는 다시 읽어 본다. 예전 모델의 한계를 피하려던 지시가 오히려 짐이 될 수 있다.
- auto memory에서 쓸 만한 교훈을 발견하면 CLAUDE.md나 rule로 옮겨 적는다("승격").
- 무엇이 로드됐는지는 `/memory`, `/context`, `/permissions`, `/hooks`로 확인한다.

<details>
<summary><b>적어 주신 목록에서 고칠 점 펼치기</b></summary>

- `.claude/setting.json` → **`.claude/settings.json`** (팀 공유, 커밋). 개인용은 `.claude/settings.local.json`이다. 우선순위는 관리자 설정 > 명령줄 `--settings` > `settings.local.json` > `settings.json` > 사용자 `~/.claude/settings.json`이다.
- `Claude.md` → **`CLAUDE.md`** (대문자). 저장소 루트나 `.claude/CLAUDE.md`에 둔다.
- `.claude/rules/`는 **있다**. 다만 언어를 고르는 칸은 없고, 파일 경로 패턴(`paths:`)으로 범위를 정한다. 그래서 언어별 규칙도 `**/*.py`처럼 만든다. `paths`가 없는 규칙은 매 세션 통째로 로드된다.
- `docs/architecture/`, `docs/adr/`, `specs/`, `policies/`, `tests/`는 Claude Code가 이름을 보고 알아서 읽거나 강제하는 폴더가 **아니다**. 평범한 폴더라서 CLAUDE.md, rule, skill에서 가리켜 줘야 읽는다.
- `policies/`에 정책 문서를 두는 것만으로는 아무것도 막지 못한다. 막아야 하는 정책은 권한 규칙의 deny, 훅, 관리자 설정으로 옮긴다.
- auto memory는 저장소 **밖**(`~/.claude/projects/<프로젝트>/memory/`)에 있다. 내 컴퓨터에만 있고 버전 관리도 안 돼서 팀 지식이 될 수 없다.

#### 7. 운영 결과가 최종 피드백이다: 어떤 개념?
**뜻.** 성공의 기준을 "AI가 코드를 얼마나 빨리, 많이 만들었나"가 아니라 "운영에서 실제로 무슨 일이 일어났나"에 둔다. 그리고 문제가 생기면 코드만 고치지 않고, **같은 문제를 다시 만들지 않도록 명세·규칙·테스트를 고친다.** 저장소가 운영에서 배우는 구조다.

**왜 필요한가**
- DORA 2024 조사: AI 도입 정도가 25% 높아질 때마다 배포 처리량은 약 1.5%, 안정성은 약 7.2% 낮아지는 것으로 추정됐다. DORA는 코드가 빨리 나오면서 변경 단위가 커진 탓으로 본다.
- DORA 2025 조사(주제 5): 처리량은 오르는 쪽으로 바뀌었지만 불안정성은 여전히 늘었다. AI는 증폭기라서, 작은 단위로 일하기와 버전 관리가 그 불안정성을 막는 안전망이 된다.
- DORA는 "받아들여진 코드 줄 수" 같은 생산량 지표가 도구를 얼마나 쓰는지 보는 데는 쓸 만하지만, 실제 생산성의 척도로 기대지는 말라고 권한다. AI가 코드 양을 쉽게 부풀리기 때문이다.

**무엇을 재나**
- **배포 성과(DORA 5개 지표).** 처리량은 변경 리드 타임, 배포 빈도, 실패 배포 복구 시간이다. 불안정성은 변경 실패율과 배포 재작업률이다. 흔히 말하는 "4대 지표"는 옛 모델이고, 2024년에 재작업률이 더해졌다.
- **SLO(서비스가 지켜야 할 품질 목표)와 에러 버짓(그 목표 안에서 허용되는 실패량).** 예를 들어 목표가 99.9%면, 4주 동안 요청 100만 건 중 1,000건까지 실패를 허용한다. 구글 SRE의 예시 정책은 이 버짓을 다 쓰면 긴급 수정(P0)과 보안 수정 말고는 배포를 멈춘다.
- **보안:** 취약점, 비밀 유출, 권한 사고
- **비용:** 인프라 비용, AI 토큰 비용
- **사용자 가치:** 명세의 성공 기준과 실제 사용 지표

**되먹임 고리: 장애 → 저장소**
- 장애가 나면 **비난 없는 포스트모템**(장애 뒤에 쓰는 회고 문서. 사람 탓이 아니라 원인에 집중한다)을 쓰고, 고칠 곳을 정한다.
  - 명세가 빠뜨렸다 → `specs/` 갱신 ("바꾸면 안 되는 것"에 추가)
  - 테스트가 못 잡았다 → `tests/`에 회귀 테스트 추가
  - Claude가 규칙을 어겼다 → CLAUDE.md나 rule 수정, 반복되면 훅으로 강제
  - 결정이 틀렸다 → 새 ADR (이전 ADR은 "대체됨"으로 표시)
  - 위험 등급을 낮게 잡았다 → 권한 규칙과 승인 절차 강화
- 이 변경도 모두 PR로 리뷰한다.
- Claude Code가 도울 수 있는 일: 포스트모템 초안, 회귀 테스트 작성, CLAUDE.md 수정 제안. 예약 실행되는 GitHub Actions(schedule 트리거)로 정기 점검을 돌릴 수도 있다.
- 다만 운영 지표를 읽어 명세까지 자동으로 고쳐 주는 도구는 없다. 이 고리는 **팀의 절차**다.

**주의 (DORA)**
- 지표를 목표로 삼지 않는다. 목표가 된 지표는 지표 구실을 잃는다 (굿하트의 법칙).
- 서로 다른 팀이나 서비스끼리 비교하지 않는다.
- 토큰 사용량 같은 입력 지표로 사람을 평가하지 않는다. DORA는 회사 전체 합계는 의미가 없고, 개인 점수는 해롭다고 한다.

#### 작게 시작하는 순서
1. CLAUDE.md를 200줄 이하로 정리하고, `settings.json`에 deny(비밀 파일, 운영 명령)를 넣고, 샌드박스를 켠다.
2. `specs/` 템플릿을 만든다. 기능 하나를 명세 승인 → 다른 세션이 인수 테스트 → 새 세션 구현(필요하면 plan 모드로 계획부터)으로 해 본다 (4-3). 명세를 쓰기 전에 코드를 조사해야 하면 그때도 plan 모드로 시작한다.
3. 리뷰 에이전트, CI 테스트, 브랜치 보호를 붙인다.
4. 보호 훅과 편집 뒤 lint 훅을 걸고, 장애가 나면 명세·테스트를 고치는 습관을 들인다.
5. 그다음에 Spec Kit 같은 도구를 쓰거나 auto 모드의 범위를 넓힌다.

#### 앞 주제와 이어 보면
- 주제 5의 DORA 2025 "AI는 증폭기"와 7가지 역량(AI 방침 공유, 건강한 데이터 생태계, AI가 접근할 수 있는 내부 데이터, 버전 관리, 작은 단위로 일하기, 사용자 중심, 양질의 내부 플랫폼)이 이 방법론을 뒷받침한다. 특히 "AI가 접근할 수 있는 내부 데이터"가 원칙 6이다.
- 주제 5에서 딜로이트 조사 기업 가운데 에이전트 거버넌스 체계가 성숙한 곳은 21%였다 (에이전트를 어느 정도 이상 쓰는 곳은 23%, 2년 뒤 예상 74%). 원칙 4와 5가 바로 그 거버넌스다.
- 주제 4 표의 "앞으로" 줄에 적은 "AI가 코드·배포를 돕고 사람이 검토"를 실제로 운영하는 방법이 이 주제다.
