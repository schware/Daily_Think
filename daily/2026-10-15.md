## 주제 6: AI를 통한 개발 방법론, Claude Code로 운영하기

### 질문
- AI를 통한 개발 방법론 7원칙을 Claude Code로 어떻게 운영할 수 있을까?
  1. 사람은 Why와 What을 소유한다
  2. Claude Code는 How의 탐색과 실행을 맡는다
  3. 명세가 구현의 기준이다 (가장 어려운 부분: 명세를 제대로 정리하고 구체화하기)
  4. 생성과 검증을 분리한다 (지금 Claude Code에서 어떻게?)
  5. 자율성은 위험에 비례한다
  6. 프로젝트 지식은 저장소에서 관리한다 (무슨 뜻일까?)
  7. 운영 결과가 최종 피드백이다 (어떤 개념일까?)

### Claude

#### 한 줄 답
가능하다. 핵심은 **"요청"과 "강제"를 나누는 것**이다. CLAUDE.md, rules, skills, agents에 적은 내용은 Claude에게 하는 **요청(맥락)** 이다. 반드시 지켜져야 하는 것은 permissions, hooks, sandbox, CI 같은 **강제 장치**에 둬야 한다. 공식 문서도 CLAUDE.md는 강제 설정이 아니라 맥락이며, 무조건 막아야 하는 동작은 PreToolUse 훅으로 막으라고 안내한다.

#### 먼저 바로잡을 것: 계획과 실제 Claude Code의 차이
- `.claude/setting.json` → **`.claude/settings.json`** (팀 공유, 커밋). 개인용은 `.claude/settings.local.json`. 우선순위는 관리자(managed) 설정 > 명령줄 `--settings` > `settings.local.json` > `settings.json` > 사용자 `~/.claude/settings.json`.
- `Claude.md` → **`CLAUDE.md`** (대문자). 저장소 루트나 `.claude/CLAUDE.md`에 둔다.
- `.claude/rules/`는 **있다**. 다만 "언어별"이 아니라 파일 경로 패턴(`paths:`)으로 범위를 정한다 (예: `**/*.py`). `paths`가 없는 규칙은 매 세션 통째로 로드된다.
- `docs/architecture/`, `docs/adr/`, `specs/`, `policies/`, `tests/`는 Claude Code가 이름만 보고 알아서 읽거나 강제하는 폴더가 **아니다**. 평범한 폴더라서 CLAUDE.md, rule, skill에서 가리켜 줘야 읽는다.
- `policies/`에 정책 문서를 두는 것만으로는 아무것도 막지 못한다. 막아야 하는 정책은 permissions의 deny, hooks, 관리자 설정으로 옮겨야 한다.
- auto memory는 저장소 **밖**(`~/.claude/projects/<프로젝트>/memory/`)에 있다. 내 컴퓨터에만 있고 버전 관리도 되지 않아서 팀 지식이 될 수 없다. 배운 것은 CLAUDE.md, rule, skill로 옮겨 적어야("승격") 팀이 쓴다.

#### 전체 흐름

```
① 사람: Why·What을 정리하고
   명세를 승인한다
② Claude(plan 모드): 조사, 영향 분석,
   대안 → 계획 → 사람 승인
③ 구현 세션(worktree): 코드·테스트,
   훅이 테스트 결과를 되돌려 준다
④ 검증(구현과 분리): 독립 테스트(CI),
   보안 검사, 리뷰 에이전트, 사람 리뷰
⑤ 배포 승인(사람): 브랜치 보호,
   CI 배포 승인
⑥ 운영 측정: 장애·성능·보안·비용·가치
   → 명세·규칙·테스트를 고친다 → ①로
```

#### 1. 사람은 Why와 What을 소유한다
- 적어 주신 일곱 가지 질문(왜 필요한가, 누구의 문제인가, 무엇을 만드나, 무엇을 바꾸면 안 되나, 어떤 위험을 허용하나, 무엇이 완료인가, 누가 운영 반영을 승인하나)은 그대로 **명세의 앞부분 칸**이 된다 (3번의 템플릿). 사람이 쓰고 사람이 승인한다.
- Claude가 도울 수 있는 일은 **빈칸 찾기**다. 공식 권장 방법은 Claude가 사람에게 **질문하며 인터뷰**한 뒤 `SPEC.md`로 정리하게 하고, 구현은 **새 세션**에서 시작하는 것이다. 새 세션의 구현자는 깨끗한 맥락에서 글로 된 명세만 보고 일한다.
- "운영 반영을 누가 승인하는가"에 해당하는 승인 기능은 Claude Code 안에 따로 없다. 브랜치 보호(사람 승인 없이는 머지 불가), CI의 배포 승인 단계, 그리고 Claude가 배포 명령을 실행하지 못하게 막는 deny 규칙을 조합해 만든다.

#### 2. Claude Code는 How의 탐색과 실행을 맡는다
- **조사·영향 분석·대안 제안 → plan 모드.** 이 모드에서 Claude는 파일을 읽고 계획만 쓰며, 사람이 승인해야 수정을 시작한다. 시작할 때 `claude --permission-mode plan`, 세션 중에는 `Shift+Tab`이나 `/plan`으로 들어간다.
  - 주의: 일부 대화형 세션에서는 plan 모드의 차단이 강제되지 않는다는 문서 설명이 있다. 꼭 막아야 하는 것은 deny 규칙이나 PreToolUse 훅으로 막는다.
- **코드·테스트·문서 초안, 빌드·테스트 실행, 오류 분석 → 구현 세션.** 공식 권장 순서는 탐색 → 계획 → 구현 → 커밋이다. 가장 먼저 강조하는 것은 "Claude가 직접 돌려 볼 수 있는 확인 방법(테스트, 빌드)을 줘라"이다. 확인 방법이 없으면 Claude는 "다 된 것처럼 보이면" 멈추고, 사람이 검증을 떠맡게 된다.
- **대규모 반복 변경 →** 서브에이전트, 여러 에이전트를 병렬로 돌리는 동적 워크플로, `claude --worktree`로 여는 병렬 세션.
- **PR 설명과 변경 요약 →** 커밋·PR 단계에서 Claude가 쓴다.

#### 3. 명세가 구현의 기준이다 (가장 어려운 부분)
**왜 어려운가.** 사람 머릿속에서 "당연한 것"은 글로 잘 나오지 않는다. AI는 그 빈칸을 그럴듯하게 채운다. 그래서 핵심은 빈칸을 없애는 게 아니라 **빈칸을 드러내 표시하는 것**이다.

**좋은 명세의 조건** (여러 도구·가이드의 공통점)
- **관찰할 수 있는 행동으로 쓴다.** "큰 파일을 잘 처리한다" 대신 "10MB를 넘으면 오류 배너를 보여 준다". 기준은 코드를 본 적 없는 테스터도 통과 여부를 판단할 수 있느냐다 (OpenSpec 가이드).
- **요구사항 하나에 행동 하나.** "시스템은 ~해야 한다(MUST)" 형태로 쓰고 번호를 붙인다 (FR-001).
- **인수 조건은 정해진 틀로 쓴다.** Given(상태) / When(행동) / Then(결과), 또는 EARS("~인 동안, ~할 때, 시스템은 ~해야 한다").
- **바꾸면 안 되는 것을 따로 적는다.** AWS Kiro의 버그 명세에는 "바뀌지 않아야 할 동작" 칸이 따로 있고, 그 내용을 회귀 테스트로 만든다.
- **모르는 것은 추측하지 말고 표시한다.** GitHub Spec Kit은 불분명한 곳에 `[NEEDS CLARIFICATION]`을 달게 하고, 표시가 하나라도 남아 있으면 명세가 미완성이라고 본다.
- **완료 조건은 기계가 판단할 수 있게 쓴다.** "npm test가 0으로 끝난다"처럼 명령으로 확인할 수 있는 끝 상태 하나, 확인 방법, 지켜야 할 제약을 적는다 (Claude Code `/goal` 문서의 기준).
- **결정은 ADR로 남긴다.** 짧게, 번호를 붙여서 쓴다. Nygard 형식(제목, 상태, 맥락, 결정, 결과)이나 MADR을 쓴다. 위치(`docs/adr/` 또는 `docs/decisions/`)는 하나로 정해 CLAUDE.md에 적는다.

**명세의 수준** (Thoughtworks 분류)
- spec-first: 작업 전에 명세를 쓴다.
- spec-anchored: 작업 뒤에도 명세를 유지하고, 기능을 바꿀 때 명세도 같이 고친다. ← **이 방법론의 목표**
- spec-as-source: 명세가 주된 소스가 되고 코드는 거기서 나온다.

**도구:** GitHub Spec Kit(원칙 → 명세 → 질문으로 빈칸 메우기 → 설계 → 작업 목록 → 구현, Claude Code에는 skill로 설치됨), AWS Kiro(requirements·design·tasks, EARS), OpenSpec(변경분만 델타로 기록). 처음에는 도구 없이 아래 템플릿 하나로 시작해도 충분하다.

#### 4. 생성과 검증을 분리한다 (지금 Claude Code에서)
Claude Code에 "생성 → 검증" 파이프라인이 통째로 들어 있지는 않다. 이미 있는 기능을 조합해서 만든다.

**생성 경로: 승인된 명세 → 구현 에이전트 → 자체 테스트**
- 승인된 명세를 가리키며 **새 세션**을 연다: `claude --worktree <기능이름>`. 별도 체크아웃과 브랜치에서 일하므로 다른 작업과 섞이지 않는다.
- 편집할 때마다 피드백을 받는다: PostToolUse 훅으로 편집 뒤 lint와 빠른 테스트를 돌리고, 실패하면 결과가 Claude에게 되돌아간다.
- 끝내기 전에 관문을 둔다: Stop 훅으로 "테스트가 통과하기 전에는 끝낼 수 없음"을 걸거나, `/goal`로 "npm test가 0으로 끝날 때까지"를 완료 조건으로 준다.
- 한계: 여기까지는 구현자 **자신의** 검사다. 독립 검증이 아니다.

**검증 경로: 승인된 명세 → 독립 테스트·보안 검사 → 리뷰 에이전트 → 사람 리뷰**
- **독립 테스트.** 인수 테스트는 구현보다 **먼저, 다른 세션이** 쓴다. 공식 권장도 "한 Claude가 테스트를 쓰고, 다른 Claude가 그 테스트를 통과하는 코드를 쓰게 하라"이다.
  - 구현 세션은 그 테스트 파일과 명세를 고치지 못하게 막는다 (5번의 설정 예시).
  - 이렇게 막아야 하는 이유: Claude Code가 기본으로 보호하는 경로(`.git`, `.claude` 등)에 `tests/`와 `specs/`는 들어 있지 않다. 막지 않으면 구현 세션이 자기 테스트나 명세를 고쳐서 "통과"시킬 수 있다.
- **CI에서 다시 돌리기.** 구현 세션 밖에서 전체 테스트를 다시 돌린다. 훅으로 돌린 테스트는 구현자의 피드백일 뿐이다.
- **보안 검사.** `/security-review`(현재 브랜치와 기본 브랜치의 차이를 검사)에 CI의 정적 분석과 의존성 검사를 더한다.
- **리뷰 에이전트.** 새 맥락에서 시작하는 리뷰어를 둔다. 공식 문서도 "방금 쓴 코드에 치우치지 않도록, 새 맥락이 리뷰에 낫다"고 말한다.
  - `.claude/agents/`에 리뷰어를 만들고, `tools`에 읽기 도구만 준다. 명세 경로와 diff만 넘긴다.
  - **fork는 리뷰어로 쓰지 않는다.** fork는 구현자의 대화와 추론을 그대로 이어받기 때문이다.
  - 다른 선택지: `/code-review`(로컬 diff나 PR 리뷰), GitHub의 Claude Code Review(Team·Enterprise, 연구 미리보기), GitHub Actions(`anthropics/claude-code-action`). 저장소 루트의 `REVIEW.md`에 리뷰 기준을 적을 수 있다.
- **사람 리뷰.** 마지막 관문이다. 브랜치 보호로 사람이 승인하지 않으면 머지할 수 없게 한다.

**주의 세 가지**
- 서브에이전트는 **맥락만 분리되고 권한은 부모를 따른다.** 부모가 auto, acceptEdits, bypassPermissions 모드면 리뷰어의 `permissionMode` 설정은 무시된다. 읽기 전용은 `tools` 목록으로 강제한다.
- Claude의 Code Review 체크는 **머지를 막지 않는다** (항상 neutral로 끝난다). 막으려면 CI에서 결과를 읽어 실패로 바꿔야 한다.
- 리뷰어도 같은 파일시스템을 본다. 구현자가 남긴 메모 파일을 읽을 수 있으므로, 리뷰어에게 넘기는 것은 **명세와 diff로 한정**한다. 완전한 독립은 별도 세션이나 CI 작업으로 만든다.

<details>
<summary><b>리뷰 에이전트 예시 펼치기</b> (.claude/agents/spec-reviewer.md)</summary>

```markdown
---
name: spec-reviewer
description: 구현이 끝난 뒤, 승인된 명세와 diff만 보고 독립적으로 검토할 때 사용한다.
tools: Read, Grep, Glob
model: inherit
---
너는 이 변경을 처음 보는 리뷰어다.
위임 메시지로 받은 명세 경로와 diff만 근거로 판단한다.
1. 명세의 인수 조건마다 충족 여부와 근거(파일:줄)를 적는다.
2. "바꾸면 안 되는 것"을 건드린 곳이 있는지 찾는다.
3. 명세에 없는 동작이 추가됐는지 찾는다.
코드는 고치지 않는다. 결과만 보고한다.
```

`tools`에 Bash를 넣지 않았다. Bash는 쓰기까지 할 수 있어서 읽기 전용이 깨지기 때문이다. 그래서 diff는 위임할 때 함께 넘긴다.

</details>

#### 5. 자율성은 위험에 비례한다

| 위험 | 예 | Claude Code 설정 |
|---|---|---|
| 낮음 (되돌릴 수 있음) | 문서, 테스트, 리팩터링 | auto 모드(개인 설정) 또는 acceptEdits + sandbox |
| 중간 | 비즈니스 로직, API | 기본(Manual) 모드 + sandbox, 사람이 diff 확인 |
| 높음 | 고객 데이터, 권한, 결제, 운영 | deny로 실행 자체를 막음, 사람 승인, 배포는 CI에서만 |

**장치별 역할**
- **권한 모드:** default(화면에는 Manual), acceptEdits, plan, auto, dontAsk, bypassPermissions.
  - auto: 사람 대신 분류 모델이 판단한다. 운영 배포·마이그레이션, 권한 부여, force push 등은 기본으로 막는다. 그래도 분류기는 사람이 아니다.
  - dontAsk: 물어봐야 하는 것은 모두 거부한다. CI용이다.
  - bypassPermissions: 격리된 컨테이너나 VM에서만 쓰라고 안내돼 있다.
- **permissions 규칙:** deny → ask → allow 순서로 검사하고, 처음 맞는 규칙이 이긴다. 어느 범위의 deny든 allow보다 앞선다.
- **Bash 규칙은 보안 경계가 아니다.** `Bash(rm *)`로 막아도 `/bin/rm`이나 `bash -c 'rm ...'`은 막지 못한다. OS 수준으로 막으려면 sandbox를 쓴다.
  - sandbox는 기본으로 꺼져 있다. 켜야 하고, 설치가 안 되면 sandbox 없이 그냥 실행된다. 그래서 `failIfUnavailable`을 켜 둔다.
- **훅은 실패하면 통과시킨다.** 차단하려면 exit 2를 써야 한다. exit 1은 경고만 남기고 그대로 진행된다.
- **조직 정책은 관리자 설정(managed settings)으로 둔다.** 개발자가 덮어쓸 수 없다.
- 프로젝트 `settings.json`에 `defaultMode: "auto"`나 `"bypassPermissions"`를 써도 **무시된다.** 이 둘은 개인 설정이나 관리자 설정에서만 정할 수 있다.

<details>
<summary><b>설정 예시 펼치기</b> (.claude/settings.json, 구현 세션 전용 설정, 보호 훅)</summary>

팀 공통 `.claude/settings.json`:
```json
{
  "permissions": {
    "defaultMode": "acceptEdits",
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(kubectl *)",
      "Bash(terraform apply *)"
    ],
    "ask": ["Bash(git push *)"],
    "allow": ["Bash(npm test)", "Bash(npm run lint)"]
  },
  "sandbox": { "enabled": true, "failIfUnavailable": true },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
```

구현 세션에만 거는 추가 잠금 `.claude/implement-settings.json` (명령줄 `--settings`는 프로젝트 설정보다 우선하고, deny 목록은 합쳐진다):
```json
{
  "permissions": {
    "deny": ["Edit(/specs/**)", "Edit(/tests/acceptance/**)"]
  }
}
```
실행: `claude --worktree login --settings .claude/implement-settings.json`

보호 훅 `.claude/hooks/protect-files.sh`:
```bash
#!/bin/bash
INPUT=$(cat)
FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
case "$FILE" in
  *.env*|*/migrations/*)
    echo "Blocked: $FILE 는 사람 승인이 필요한 파일입니다" >&2
    exit 2 ;;
esac
exit 0
```
exit 2만 차단한다. 커밋된 훅은 팀원 컴퓨터와 CI에서 실행되는 코드이므로 코드처럼 리뷰한다.

#### 6. 프로젝트 지식은 저장소에서 관리한다: 무슨 뜻?
**뜻.** 대화창에 길게 쓴 프롬프트는 세션이 끝나거나 대화가 압축(`/compact`)되면 사라진다. 다른 사람, 다른 세션, CI에서는 보이지도 않는다. 반면 저장소의 파일은 버전 관리되고, PR로 리뷰되고, 모든 세션이 같은 내용을 본다. 즉 **"AI에게 하는 말"을 코드처럼 다루자**는 뜻이다. 공식 문서도 대화로만 준 지시는 압축 뒤에 남지 않으니 CLAUDE.md에 적으라고 한다.

**두 종류로 나눠 본다**
- Claude Code가 **스스로 읽는 것:** CLAUDE.md, `.claude/rules/`, `.claude/skills/`, `.claude/agents/`, `.claude/settings.json`
- **가리켜 줘야 읽는 것:** `docs/architecture/`, `docs/adr/`, `specs/`, `policies/`, `tests/`

| 무엇 | 어디에 | 언제 로드되나 | 성격 |
|---|---|---|---|
| 공통 규칙 | CLAUDE.md (200줄 이하 권장) | 매 세션 | 요청 |
| 경로별 규칙 | .claude/rules/*.md (paths 패턴) | 맞는 파일을 읽거나 고칠 때 | 요청 |
| 구조·경계 | docs/architecture/ | 가리킬 때 | 요청 |
| 기술 결정 | docs/adr/ | 가리킬 때 | 요청 |
| 요구사항·설계 | specs/ | 작업할 때 지정 | 요청 (인수 테스트로 바꾸면 검증 가능) |
| 조직 정책 | policies/ (사람이 읽는 원문) | 가리킬 때 | 요청 (강제는 settings·hooks·관리자 설정) |
| 기대 동작 | tests/ | 실행할 때 | **검증** |
| 반복 절차 | .claude/skills/이름/SKILL.md | 설명이 맞을 때, /이름 | 요청 |
| 전문 작업자 | .claude/agents/이름.md | 위임할 때 | 요청 (단, 도구 목록은 강제) |
| 차단·자동화 | .claude/settings.json | 항상 | **강제** |
| 개인 학습 | auto memory (저장소 밖) | 매 세션 앞부분 | 요청, 공유 안 됨 |

**운영 요령**
- CLAUDE.md에 명세 전체를 `@import` 하지 않는다. import한 파일도 매 세션 통째로 로드된다. "명세는 `specs/<기능>/spec.md`에 있다"처럼 위치만 적는다.
- CLAUDE.md의 한 부분이 "사실"이 아니라 "절차"로 자라면 skill로 옮긴다. skill 본문은 쓸 때만 로드된다.
- CLAUDE.md 수정도 PR로 리뷰한다. 큰 모델 업데이트 뒤에는 다시 읽어 본다. 예전 모델의 한계를 피하려던 지시가 오히려 짐이 될 수 있기 때문이다.
- auto memory에서 쓸 만한 교훈을 발견하면 CLAUDE.md나 rule로 승격한다.
- 무엇이 로드됐는지는 `/memory`, `/context`, `/permissions`, `/hooks`로 확인한다.

#### 7. 운영 결과가 최종 피드백이다: 어떤 개념?
**뜻.** 성공의 기준을 "AI가 코드를 얼마나 빨리, 많이 만들었나"가 아니라 "운영에서 실제로 무슨 일이 일어났나"에 둔다. 그리고 문제가 생기면 코드만 고치지 않고, **같은 문제를 다시 만들지 않도록 명세·규칙·테스트를 고친다.** 저장소가 운영에서 배우는 구조다.

**왜 필요한가**
- DORA 2024 조사: AI 도입이 25% 늘 때 배포 처리량은 1.5% 줄고 안정성은 7.2% 떨어졌다. DORA는 코드가 빨리 나오면서 변경 단위가 커진 탓으로 본다.
- DORA 2025 조사: AI는 증폭기다 (주제 5). 작은 단위로 일하기와 버전 관리가 그 불안정성을 막는 안전망이라고 한다.
- DORA는 "받아들여진 코드 줄 수" 같은 생산량 지표를 그만 쓰라고 권한다. AI가 코드 양을 부풀리기 때문이다.

**무엇을 재나**
- **배포 성과(DORA 5개 지표).** 처리량은 변경 리드 타임, 배포 빈도, 실패 배포 복구 시간이다. 불안정성은 변경 실패율과 배포 재작업률이다. 흔히 말하는 "4대 지표"는 옛 모델이고, 2024년에 재작업률이 더해졌다.
- **SLO와 에러 버짓.** 예를 들어 목표가 99.9%면 4주 동안 요청 100만 건 중 1,000건까지 실패를 허용한다. 구글 SRE의 예시 정책은 이 버짓을 다 쓰면 긴급 수정(P0)과 보안 수정 말고는 배포를 멈춘다.
- **보안:** 취약점, 비밀 유출, 권한 사고
- **비용:** 인프라 비용, AI 토큰 비용
- **사용자 가치:** 명세의 성공 기준과 실제 사용 지표

**되먹임 고리: 장애 → 저장소**
- 장애가 나면 **비난 없는 포스트모템**(사람 탓이 아니라 원인에 집중)을 쓰고, 고칠 곳을 정한다.
  - 명세가 빠뜨렸다 → `specs/` 갱신 ("바꾸면 안 되는 것"에 추가)
  - 테스트가 못 잡았다 → `tests/`에 회귀 테스트 추가
  - Claude가 규칙을 어겼다 → CLAUDE.md나 rule 수정, 반복되면 훅으로 강제
  - 결정이 틀렸다 → 새 ADR (이전 ADR은 "대체됨"으로 표시)
  - 위험 등급을 낮게 잡았다 → permissions와 승인 규칙 강화
- 이 변경도 모두 PR로 리뷰한다.
- Claude Code가 도울 수 있는 일: 포스트모템 초안, 회귀 테스트 작성, CLAUDE.md 수정 제안. 공식 문서에는 Stop 훅이 세션 기록을 읽고 CLAUDE.md 수정을 제안하게 하는 예도 있다. 예약 실행되는 GitHub Actions로 정기 점검도 할 수 있다.
- 다만 운영 지표를 읽어 명세까지 자동으로 고쳐 주는 도구는 없다. 이 고리는 **팀의 절차**다.

**주의 (DORA)**
- 지표를 목표로 삼지 않는다. 목표가 된 지표는 지표 구실을 잃는다 (굿하트의 법칙).
- 서로 다른 팀이나 서비스끼리 비교하지 않는다.
- 토큰 사용량 같은 입력 지표로 사람을 평가하지 않는다. DORA는 회사 전체 합계는 의미가 없고, 개인 점수는 해롭다고 한다.

#### 작게 시작하는 순서
1. CLAUDE.md를 200줄 이하로 정리하고, settings.json에 deny(비밀 파일, 운영 명령)를 넣고, sandbox를 켠다.
2. `specs/` 템플릿을 만든다. 기능 하나를 plan 모드 → 명세 승인 → 새 세션 구현으로 해 본다.
3. 리뷰 에이전트, CI 테스트, 브랜치 보호를 붙인다.
4. 보호 훅과 편집 뒤 lint 훅을 걸고, 장애 → 명세·테스트 갱신을 습관으로 만든다.
5. 그다음에 Spec Kit 같은 도구를 쓰거나 auto 모드의 범위를 넓힌다.

#### 이 저장소에 비춰 보면
이 Daily_Think 저장소가 이미 원칙 6의 작은 예다. CLAUDE.md가 규칙이고, `index/memo.md`가 원문, `daily/`가 정리, `references/`가 근거다. 어제 CLAUDE.md에 "참조자료를 마지막에 정리" 한 줄을 넣자, 그다음 답부터 참조자료가 붙었다. 대화로 매번 부탁하지 않아도 저장소의 규칙이 일을 바꾼 것이다.

#### 앞 주제와 이어 보면
- 주제 5의 DORA "AI는 증폭기"와 7가지 역량(명확히 공유된 AI 방침, 버전 관리, 작은 단위로 일하기, 사용자 중심, 양질의 내부 플랫폼 등)이 이 방법론의 근거다.
- 주제 5에서 에이전트를 쓰는 기업 중 성숙한 거버넌스를 갖춘 곳은 21%였다 (딜로이트). 원칙 4와 5가 바로 그 거버넌스다.
- 주제 4 표의 "앞으로" 줄에 적은 "AI가 코드·배포를 돕고 사람이 검토"를 실제로 운영하는 방법이 이 주제다.
