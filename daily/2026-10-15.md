### Claude

#### 한 줄 답
가능하다. 핵심은 **요청**과 **강제**를 나누는 것이다. CLAUDE.md 같은 파일에 적은 글은 Claude에게 주는 context, 즉 **요청**이라 어겨질 수 있다. 꼭 지켜야 하는 것은 permission rule·hook·sandbox·CI처럼 Claude가 넘을 수 없는 장치로 막는다. 공식 문서도 CLAUDE.md는 강제 설정이 아니며, 무조건 막을 동작은 PreToolUse hook으로 막으라고 안내한다.

※ 적어 주신 목록의 이름 몇 개는 실제와 다르다 (`setting.json` → `settings.json`, `Claude.md` → `CLAUDE.md` 등). 자세한 건 6번에 있다.

#### 용어
- hook: 편집하기 전, 편집한 뒤, 끝내기 전처럼 정해진 순간에 자동으로 도는 script
- sandbox: Claude가 실행한 shell 명령이 정한 폴더 밖에 쓰거나 허락하지 않은 곳에 접속하지 못하게 OS 수준에서 막는 기능 (읽기는 기본으로 대부분 허용)
- session: Claude와 나누는 대화 하나. iPhone 앱 sidebar의 대화 하나가 session 하나다. Claude는 그 session에서 읽은 파일과 한 생각, 즉 context만 기억한다 (4-1)
- worktree: 같은 repository를 다른 폴더에 한 번 더 checkout하고, 그 폴더에서 다른 branch로 일하는 git 기능. working directory를 하나 더 만드는 것이다 (4-2)
- main checkout: 처음 clone한 원래 폴더(예: my-app/). worktree가 아닌 쪽이다. "main branch"라는 뜻이 아니다
- 인수 테스트: 명세의 인수 조건을 그대로 옮긴 테스트. "다 됐다"의 기준이다
- tag: commit 하나에 붙이는 이름표. branch는 새 commit을 따라 앞으로 가지만, tag는 누가 일부러 옮기지 않는 한 그 commit에 그대로 있다. 그래서 "승인한 그 시점"을 가리키는 데 쓴다 (4-3)
- subagent: Claude가 일을 떼어 맡기는 보조 Claude. 따로 context를 갖고 결과만 돌려준다
- fork: 지금 session의 context를 그대로 물려받아 갈라져 나온 subagent (GitHub repository fork와 다르다)
- CI: 코드를 push하면 server가 자동으로 build하고 테스트하는 장치 (주제 3의 CI/CD)
- branch protection: 정한 검사와 사람 승인을 통과해야만 main에 merge할 수 있게 하는 GitHub 설정
- lint: 코드 형식과 흔한 실수를 자동으로 찾는 검사
- diff: 바뀐 부분만 모아 보여 주는 것
- permission mode: Claude가 무엇을 묻고 무엇을 바로 할지 정하는 방식 (5번)

#### 전체 흐름

```
1. 사람: Why·What을 정리하고
   명세를 승인한다
2. Claude(plan mode): 구현 방법 조사,
   영향 분석, 대안 → 계획 → 사람 승인
3. 다른 session: 인수 테스트를 먼저 쓴다
4. 구현(새 session, 필요하면 worktree):
   코드·테스트,
   hook이 테스트 결과를 되돌려 준다
5. 검증(구현과 분리): CI 테스트,
   보안 검사, reviewer agent, 사람 review
6. 배포 승인(사람): branch protection,
   CI 배포 승인
7. 운영 측정: 장애·성능·보안·비용·가치
   → 명세·규칙·테스트를 고친다 → 1로
```

#### 1. 사람은 Why와 What을 소유한다
- 적어 주신 일곱 가지 질문(왜 필요한가, 누구의 문제인가, 무엇을 만드나, 무엇을 바꾸면 안 되나, 어떤 위험을 허용하나, 무엇이 완료인가, 누가 운영 반영을 승인하나)은 그대로 **명세의 앞부분 칸**이 된다 (3번의 template). 사람이 쓰고 사람이 승인한다.
- Claude가 도울 수 있는 일은 **빈칸 찾기**다. 큰 기능을 만들 때 공식 권장 방법은 이렇다. Claude가 사람을 **interview**한 뒤 명세(`specs/<기능>/spec.md`)로 정리하게 하고, 구현은 **새 session**에서 시작한다. 새 session의 구현자는 깨끗한 context에서 글로 된 명세만 보고 일한다.
- "운영 반영을 누가 승인하는가"를 위한 승인 기능은 Claude Code 안에 따로 없다. branch protection, CI의 배포 승인 단계, 그리고 Claude가 배포 명령을 실행하지 못하게 막는 deny rule을 조합해 만든다.

#### 2. Claude Code는 How의 탐색과 실행을 맡는다
- **조사·영향 분석·대안 제안 → plan mode.** 이 mode에서 Claude는 파일을 읽고 계획만 쓴다. 사람이 승인해야 수정을 시작한다. 시작할 때 `claude --permission-mode plan`으로 켜고, session 중에는 `Shift+Tab`이나 `/plan`으로 들어간다.
  - 주의: plan mode는 작업 방식이지 보안 장치가 아니다. bypassPermissions를 쓸 수 있는 interactive terminal session에서는 plan mode의 편집 차단이 강제되지 않는다. 꼭 막아야 하는 것은 deny rule이나 PreToolUse hook으로 막는다.
- **코드·테스트·문서 초안, build·테스트 실행, 오류 분석 → 구현 session.** 공식 권장 순서는 탐색 → 계획 → 구현 → commit이다. 무엇보다 먼저 "Claude가 직접 돌려 볼 수 있는 확인 방법(테스트, build)을 줘라"를 강조한다. 확인 방법이 없으면 Claude는 "다 된 것처럼 보이면" 멈추고, 결국 사람이 검증을 떠맡게 된다.
- **대규모 반복 변경 →** 일을 여러 subagent에게 나눠 맡기거나, `claude --worktree`로 session을 여러 개 열어 동시에 돌린다.
- **PR 설명과 변경 요약 →** commit·PR 단계에서 Claude가 쓴다.

#### 3. 명세가 구현의 기준이다 (가장 어려운 부분)
**이렇게 쓴다**
1. Claude가 나를 interview하게 해서, 아래 template의 칸을 채운다. 코드를 먼저 조사해야 하면 plan mode로 시작하고, 계획을 승인한 뒤 명세를 쓰게 한다 (4-3의 ①).
2. 답할 수 없는 곳은 `[NEEDS CLARIFICATION]`으로 남긴다.
3. 표시가 0개가 될 때까지 사람이 답한다.
4. 다른 session이 인수 조건을 테스트로 바꾼다 (4-3의 ②).
5. 사람이 승인한 뒤, 새 session에서 구현한다.

**왜 어려운가.** 사람 머릿속의 "당연한 것"은 글로 잘 나오지 않는다. AI는 그 빈칸을 그럴듯하게 채운다. 그래서 핵심은 빈칸을 없애는 게 아니라 **빈칸을 드러내 표시하는 것**이다.

**좋은 명세의 조건** (여러 도구·guide의 공통점)
- **관찰할 수 있는 행동으로 쓴다.** "큰 파일을 잘 처리한다" 대신 "10MB를 넘으면 error banner를 보여 준다"라고 쓴다. 기준은 코드를 본 적 없는 테스터도 통과 여부를 판단할 수 있느냐다 (OpenSpec guide).
- **요구사항 하나에 행동 하나.** "시스템은 ~해야 한다(MUST)"로 쓰고 번호를 붙인다 (FR-001).
- **인수 조건은 정해진 틀로 쓴다.** Given(상태) / When(행동) / Then(결과)이나 EARS("~인 동안, ~할 때, 시스템은 ~해야 한다")를 쓴다.
- **바꾸면 안 되는 것을 따로 적는다.** AWS Kiro의 bug 명세에는 "바뀌지 않아야 할 동작" 칸이 따로 있고, 그 내용을 회귀 테스트로 만든다.
- **모르는 것은 표시하고 묻는다.** GitHub Spec Kit은 범위·보안·UX에 크게 영향을 주는 빈칸에 `[NEEDS CLARIFICATION]`을 단다 (최대 3개). 사소한 것은 합리적 기본값을 가정으로 적는다. 표시가 남아 있으면 명세가 완성되지 않은 것으로 보고, 질문 단계에서 해결한다.
- **완료 조건은 확인할 수 있게 쓴다.** 측정 가능한 끝 상태 하나, 확인 방법(예: `npm test`가 0으로 끝남), 지켜야 할 제약을 적는다. `/goal`로 이 조건을 주면 별도 model이 매 turn 충족 여부를 판단한다. 다만 그 model은 명령을 직접 실행하지 않고 transcript에 남은 결과만 보고 판단한다. 그러니 Claude가 테스트를 직접 실행해 그 출력이 transcript에 남게 한다.
- **결정은 ADR로 남긴다.** 짧게, 번호를 붙여 쓴다. Nygard 형식(Title, Status, Context, Decision, Consequences)이나 MADR을 쓴다. 위치(`docs/adr/` 또는 `docs/decisions/`)는 하나로 정해 CLAUDE.md에 적는다.

**명세의 수준** (Thoughtworks 분류)
- spec-first: 작업 전에 명세를 쓴다.
- spec-anchored: 작업 뒤에도 명세를 유지하고, 기능을 바꿀 때 명세도 같이 고친다. ← **이 방법론의 목표**
- spec-as-source: 명세가 주된 source가 되고 코드는 거기서 나온다.

**도구** (처음엔 아래 template 하나로 충분하다)
- GitHub Spec Kit: 원칙 → 명세 → (선택) 질문 → 설계 → 작업 목록 → 구현 → converge. converge는 구현을 명세·계획과 대조해 남은 일을 추가하므로 4번의 검증과도 이어진다. Claude Code에는 `.claude/skills`에 skill로 설치된다.
- AWS Kiro: 요구사항·설계·작업 3개 문서, EARS 표기
- OpenSpec: 바뀐 부분만 delta로 기록

#### 4. 생성과 검증을 분리한다 (지금 Claude Code에서)
**짧게**
1. 인수 테스트는 구현 **전에**, **다른 session**이 쓴다.
2. 구현은 또 다른 새 session이 하고, 그 session은 테스트와 명세를 고치지 못하게 막는다. 다른 일과 동시에 할 때만 worktree에서 한다 (4-1).
3. 검증은 CI에서 다시 돌리는 테스트, read-only reviewer agent, 사람 review가 맡는다.

Claude Code에 "생성 → 검증" pipeline이 통째로 들어 있지는 않아서, 이미 있는 기능을 이렇게 조합한다.

**생성 경로: 승인된 명세 → 구현 agent → 자체 테스트**
- 승인된 명세를 가리키며 **새 session**을 연다. 순서대로 하나씩 하면 같은 폴더에서 새 session만 열면 된다. 다른 일과 동시에 하려면 worktree에서 연다 (4-1. 여는 법은 4-3의 "동시에 하고 싶을 때", 처음 쓸 때 걸리는 것은 4-2).
- 편집할 때마다 feedback을 받는다. PostToolUse hook으로 편집 뒤 lint와 빠른 테스트를 돌린다. 실패하면 script가 `exit 2`로 끝나야 stderr의 오류 내용이 Claude에게 전달된다 (`exit 0`이면 stderr는 전달되지 않는다. `exit 0`으로 끝내면서 JSON으로 `decision: "block"`과 `reason`을 출력하는 방법도 있다). PostToolUse는 이미 끝난 편집을 되돌리지는 못한다.
- 끝내기 전에 관문을 둔다. Stop hook으로 테스트가 통과하기 전에는 끝내지 못하게 막거나, `/goal`로 "npm test가 0으로 끝날 때까지"를 완료 조건으로 준다. 다만 Stop hook은 tool call 없이 8번 연속 막히면 Claude Code가 그냥 멈춘다. 그래서 최종 확인은 CI에서 한다.
- 한계: 여기까지는 구현자 **자신의** 검사다. 독립 검증이 아니다.

**검증 경로: 승인된 명세 → 독립 테스트·보안 검사 → reviewer agent → 사람 review**
- **독립 테스트.** 인수 테스트는 구현보다 먼저, 다른 session이 쓴다. 공식 문서도 한 방법으로 "한 session이 테스트를 쓰고, 다른 session이 그 테스트를 통과하는 코드를 쓰게 한다"를 소개한다.
  - 구현 session은 그 테스트 파일과 명세를 고치지 못하게 막는다 (5번의 설정 예시).
  - 막아야 하는 이유: Claude Code의 기본 protected path(`.git`, `.claude` 등)에 `tests/`와 `specs/`는 없다. 막지 않으면 구현 session이 자기 테스트나 명세를 고쳐서 "통과"시킬 수 있다.
- **CI에서 다시 돌리기.** 구현 session 밖에서 전체 테스트를 다시 돌린다. hook으로 돌린 테스트는 구현자 자신의 feedback일 뿐이다.
- **보안 검사.** `/security-review`(현재 branch와 default branch의 diff를 검사)에, CI의 정적 분석과 dependency 검사를 더한다.
- **reviewer agent.** 새 context에서 시작하는 reviewer를 둔다. 공식 문서도 방금 쓴 코드에 치우치지 않도록 새 context가 review에 낫다고 말한다.
  - `.claude/agents/`에 reviewer를 만들고, `tools`에는 read-only tool만 준다. 명세 경로와 diff만 넘긴다.
  - **fork는 reviewer로 쓰지 않는다.** fork는 구현자의 context와 추론을 그대로 물려받아, 같은 착각을 하기 쉽다.
  - 다른 선택지
    - `/code-review`: local diff나 PR을 review한다.
    - GitHub의 Claude Code Review: Team·Enterprise용 research preview다. repository root의 `REVIEW.md`를 review 기준으로 읽는다. local `/code-review`는 REVIEW.md를 읽지 않으니, 같은 기준을 local에도 쓰려면 CLAUDE.md에도 적는다.
    - GitHub Actions(`anthropics/claude-code-action`)
- **사람 review.** 마지막 관문이다. branch protection으로 사람이 승인하지 않으면 merge할 수 없게 한다.

**주의 세 가지**
- subagent는 context가 분리되지만, parent session의 permission mode가 auto·acceptEdits·bypassPermissions면 그 mode를 따르고 자기 `permissionMode` 설정은 무시된다. 그래서 read-only는 `tools` 목록으로 강제한다.
- Claude Code Review의 check는 **merge를 막지 않는다** (항상 neutral로 끝난다). 막으려면 CI에서 결과를 읽어 실패로 바꿔야 한다.
- reviewer도 같은 폴더의 파일을 본다. 구현자가 남긴 메모나 commit하지 않은 파일을 읽을 수 있으니, reviewer에게 넘기는 것은 **명세와 diff로 한정**한다. commit된 것만 보게 하려면 깨끗한 worktree의 새 session이나 CI에서 검증한다.

#### 4-1. "다른 세션"은 새 폴더를 만들라는 뜻일까? (추가 질문)
**한 줄 답:** 아니다. 독립 검증에 필요한 것은 새 폴더가 아니라 **새 session**이다. 같은 폴더에서 새 session을 열면 된다. 여기에 순서·권한·CI(아래 표)를 더하면 독립 검증이 되는데, 이것도 새 폴더 없이 갖출 수 있다. 새 폴더(worktree)는 두 session이 **동시에** 파일을 고칠 때 필요하다.

**session과 worktree는 나누는 대상이 다르다**
- **session = Claude와의 대화 하나.** iPhone 앱 sidebar에 보이는 대화 하나가 session 하나다. Claude는 그 session에서 읽은 파일과 한 생각만 기억한다. 새 session의 Claude는 앞 session에서 무슨 일이 있었는지 모른다.
- **worktree = working directory를 하나 더 만드는 git 기능.** 같은 repository를 다른 폴더에 한 번 더 checkout해서, 두 작업이 서로의 파일을 건드리지 않게 한다 (4-2).
- 정리하면 session은 **"무엇을 기억하나"**를, worktree는 **"어느 폴더의 파일을 고치나"**를 나눈다. 독립 검증에 중요한 것은 앞의 것이다.

**code review로 생각하면 쉽다**
- 작성자가 자기 코드를 다시 보면 같은 착각을 하기 쉽다. 그래서 코드를 처음 보는 동료에게 review를 맡긴다.
- 새 session의 Claude가 그 "처음 보는 동료"다. 동료가 review하려고 새 폴더가 필요하지는 않다.
- 거꾸로, 새 worktree를 만들어도 같은 session이 검증하면 독립이 아니다. 작성자가 자리만 옮겨 자기 코드를 다시 보는 셈이다.

**"독립"을 만드는 다섯 가지 분리**

| 분리 | Claude Code에서 | 막아 주는 문제 |
|---|---|---|
| context | 새 session, subagent (fork 말고) | 자기 코드에 너그러움, 같은 착각 |
| 순서 | 인수 테스트를 구현 **전에** commit | 코드에 맞춰 쓴 테스트 |
| 권한 | deny rule, `tools` 목록 | 테스트·명세를 고쳐서 "통과" |
| 실행 장소 | CI | "내 컴퓨터에선 됐다" |
| working directory | worktree | 동시 작업끼리 파일이 섞임 |

새 worktree는 다섯 가지 가운데 하나일 뿐이다. 나머지 넷은 폴더를 새로 만든다고 생기지 않는다.

**새 worktree가 필요한 때**
- session 두 개가 **동시에** 파일을 고칠 때. 한 폴더에서 동시에 고치면 서로의 변경이 같은 branch에 섞인다.
- 구현을 맡겨 둔 채 main checkout에서 다른 일을 계속하고 싶을 때.
- 검증하는 쪽이 **commit된 코드만** 보게 하고 싶을 때. 같은 폴더에는 구현자가 남긴 메모나 commit하지 않은 파일이 있을 수 있다. 가장 깨끗한 곳은 CI다.
- 내 작업을 건드리지 않고, PR로 올라온 코드만 따로 checkout해서 돌려 보고 싶을 때 (4-3의 ⑥).

**repository 안에 생기긴 하지만, commit해서 "관리"하는 폴더는 아니다**
- Claude Code가 만드는 worktree는 repository 안 `.claude/worktrees/` 아래에 생긴다. 이 폴더는 `.gitignore`에 넣어 commit하지 않는다.
- 코드를 복사해 만든 별도 프로젝트도 아니다. 같은 repository의 working directory를 하나 더 만든 것이다.
- 잠깐 쓰고 지운다. 결과는 branch → PR → main으로 돌아오고, 폴더는 정리한다.

**iPhone에서 쓰는 cloud session이라면**
- claude.ai/code의 cloud session은 session마다 별도의 virtual machine에서 돌고, repository도 session마다 새로 clone한다.
- 그래서 cloud에서는 새 session을 열면 context도 working directory도 저절로 따로다. session끼리는 git branch와 PR로 주고받는다.
- cloud session에서는 `/clear`를 쓸 수 없다. 새 context가 필요하면 sidebar에서 새 session을 연다.

#### 4-2. worktree란? (추가 질문)
**한 줄 정의:** repository 하나에 working directory를 여러 개 두는 git 기능이다. 폴더마다 다른 branch를 checkout해 두고, commit history는 하나를 같이 쓴다.

**왜 필요한가**
- 보통은 repository 하나에 working directory 하나다. 폴더 하나에는 한 번에 branch 하나만 checkout할 수 있다.
- 다른 branch를 보려면 `git switch`로 바꿔야 하고, 그러면 폴더의 파일이 그 branch 것으로 바뀐다. commit하지 않은 변경은 그대로 따라오고, 겹치는 파일이 있으면 git이 switch를 거부한다. 그래서 보통 먼저 commit하거나 `git stash`로 치워 둔다.
- worktree를 쓰면 branch마다 폴더가 따로 있다. 바꿀 필요 없이 두 branch를 나란히 열어 둔다.

**모양**
```
my-app/        ← main checkout (지금 main)
├── .git/      ← commit history는 여기 하나
├── src/
└── .claude/worktrees/
    ├── login/ ← worktree-login branch
    │   ├── .git  (주소만 적힌 파일)
    │   └── src/
    └── pr-12/ ← PR 12번 코드
```
worktree 안의 `.git`은 폴더가 아니라 파일이다. 이 worktree의 git 정보(HEAD, index)가 있는 my-app/.git/worktrees/login의 주소만 적혀 있다. commit history는 my-app/.git/ 하나를 같이 쓴다.

**복사, clone, worktree 비교**

| | 폴더 복사 | clone 한 번 더 | worktree |
|---|---|---|---|
| commit history | 따로 | 따로 | 하나를 같이 씀 |
| 한쪽 commit이 다른 쪽에 | 안 보임 | push·fetch 뒤 | 바로 보임 |
| 같은 branch를 두 곳에 | 막지 않음 | 됨 | git이 막는다 |
| 정리 | 폴더 삭제 | 폴더 삭제 | `git worktree remove` |

같은 branch를 두 곳에 checkout하는 것을 git이 막기 때문에, 두 worktree가 같은 branch를 동시에 고치다 꼬이는 일이 없다.

**git 명령으로 직접**
```bash
# 새 폴더 + 새 branch
git worktree add ../my-app-login -b login
# 이미 있는 branch를 checkout
git worktree add ../my-app-x login-lock
# 목록
git worktree list
# 정리
git worktree remove ../my-app-login
```
`remove`는 고친 파일이나 untracked 파일이 있거나 worktree가 lock되어 있으면 거부한다. 폴더를 지워도 branch는 남는다.

**Claude Code에서**
- `claude --worktree login` (줄여서 `-w`): `.claude/worktrees/login/` 폴더를 만들고 새 branch `worktree-login`에서 session을 시작한다. 이름을 빼면 이름을 지어 준다.
- **어디서 branch를 만드나:** 기본은 remote의 default branch(보통 main)다.
  - 지금 branch의 commit(아직 push하지 않은 것 포함)에서 시작하려면 settings에 `"worktree": {"baseRef": "head"}`를 넣는다.
  - branch 이름은 지정할 수 없다. 이미 있는 branch로 하려면 git으로 `.claude/worktrees/<이름>`에 먼저 checkout해 두고 `claude --worktree <이름>`으로 연다. 이미 있는 폴더 이름을 주면 새로 만들지 않고 그 worktree를 연다 (4-3에서 이렇게 쓴다).
- **PR 번호로도 만든다:** `claude --worktree "#12"`를 실행하면 `.claude/worktrees/pr-12`에 그 PR의 코드를 checkout한다. 따옴표를 붙여야 shell이 `#`를 comment로 읽지 않는다.
- session 중에 "worktree에서 작업해"라고 말해도 만들어 준다.
- subagent 설정에 `isolation: worktree`를 쓰면 그 subagent는 늘 임시 worktree에서 일한다. `/batch`도 subagent마다 worktree를 따로 쓴다.

**한 줄로: worktree는 파일만 나눈다. 보안 장치가 아니다.**

<details>
<summary><b>처음 쓸 때 걸리는 것, 지켜 주는 것과 못 지키는 것 펼치기</b></summary>

**처음 쓸 때 걸리는 것**
- `.claude/worktrees/`를 `.gitignore`에 넣는다. 그러지 않으면 main checkout에서 untracked 파일로 잔뜩 보인다.
- 새로 checkout한 폴더라서 `node_modules` 같은 dependency가 없다. 그 폴더에서 다시 설치한다.
- `.env`처럼 git에 없는 파일도 없다. project root의 `.worktreeinclude`에 적어 두면 Claude Code가 만드는 새 worktree에 복사해 준다 (gitignore된 파일만).
- hook이 현재 working directory를 알아야 하면 hook input JSON의 `cwd`를 읽는다. `$CLAUDE_PROJECT_DIR`는 `claude --worktree`로 시작했으면 worktree를 가리키지만, session 중에 worktree로 들어갔으면 main checkout을 가리킨다.
- **끝낼 때:** 바뀐 것(고친 파일, 새 파일, 새 commit)이 없으면 이름 없는 session은 worktree를 자동으로 지우고, 이름 붙인 session은 먼저 묻는다. 바뀐 것이 있으면 남길지 지울지 묻는다.
- `claude -p`로 돌린 것은 lock된 채 남는다. `git worktree unlock` → `git worktree remove`로 지우고, branch는 `git branch -D worktree-<이름>`으로 지운다.

**지켜 주는 것**
- Claude Code가 연 worktree session(`--worktree`로 시작, session 중에 worktree로 들어감, 그 session을 다시 엶)은 main checkout의 파일을 Edit·Write로 고치지 못한다. main checkout에서 도는 명령, main checkout을 대상으로 하는 git 명령(`git -C <main checkout 경로>` 등)도 막는다.
- git으로 만든 worktree 폴더에 `cd`로 들어가 그냥 `claude`를 실행하면 이 isolation check가 없다. 그때는 permission rule과 sandbox만 남는다.
- `cp`나 `>`처럼 shell 명령이 직접 쓰는 파일까지 쫓지는 않는다. 그건 permission rule과 sandbox 몫이다.

**같이 쓰는 것**
- `.git`(commit history)
- Bash 명령에 "Yes, and don't ask again"으로 허락한 permission. main checkout의 `.claude/settings.local.json`에 저장되어 모든 worktree에 적용된다 (v2.1.211 이상. Windows 등은 예외).
- project에 설치한 plugin
- auto memory (같은 repository면 하나)

**나누지 않는 것**
- 공식 문서는 worktree를 **파일 분리**로만 설명한다. 그러니 port, local DB, network, environment variable은 나뉘지 않는다고 보는 게 맞다 (문서에서 끌어낸 추론). 예를 들어 두 worktree에서 같은 port(3000)로 server를 띄우면 부딪친다.
- 위의 isolation check는 shell 명령의 쓰기를 쫓지 않으니 sandbox를 대신하지 못한다.

</details>

#### 4-3. 구체적으로: 기능 하나를 생성과 검증으로 나눠 돌려 보기 (추가 질문)
**한 줄 답:** 기준을 쓰는 session, 코드를 쓰는 session, 검사하는 session을 따로 둔다. 서로 다른 session이라서 앞 단계의 context를 물려받지 않는다. 기준은 구현 **전에** commit하고 tag로 표시해 두고, 구현하는 동안 바뀌지 않았는지 git으로 확인한다.
- 여기서 **기준**은 사람이 승인한 명세와 인수 테스트다.

예: "로그인을 5번 틀리면 15분 잠금" 기능. 명세는 3번의 template을 쓴다. 아래 명령은 노트북 terminal 기준이다. iPhone(cloud)에서 하는 법은 맨 끝에 있다.

**한눈에**

| 단계 | 누가 | 지키는 장치 |
|---|---|---|
| ① 명세 | 사람 + session A | 사람 승인 |
| ② 인수 테스트 | session B | 실패 확인, 승인 tag |
| ③ 구현 | session C | deny rule, hook |
| ④ 검증 | session D + reviewer | tag 비교, read-only |
| ⑤ CI | GitHub Actions | branch protection |
| ⑥ 사람 review | 사람 | branch protection |

- 생성 경로는 ③, 검증 경로는 ②④⑤⑥이다.
- session은 A, B, C, D 넷이지만 working directory는 ①~④ 모두 main checkout 하나다. 동시에 다른 일을 할 때만 ③④를 worktree로 보낸다 (아래 "동시에 하고 싶을 때").

**① 명세: session A**
```bash
git switch -c login-lock
claude
```
> 로그인 잠금 기능을 만들고 싶다. 질문을 하나씩 던져 나를 자세히 interview해라. 끝나면 specs/login-lock/spec.md에 명세만 써라. 코드는 쓰지 마라.

- 코드를 먼저 조사해야 하면 plan mode(`claude --permission-mode plan`)로 시작한다. plan mode에서는 파일을 고치지 못하니, 계획을 승인한 뒤 `spec.md`를 쓰게 한다.
- 사람이 `spec.md`를 읽고 고친 뒤 승인하고 commit한다.
- A의 context에는 interview에서 나눈 말이 다 들어 있다. 그래서 다음 단계는 A에게 맡기지 않는다.

**② 인수 테스트: session B (새 session)**
```bash
claude   # 새 terminal, 아니면 /clear
```
> specs/login-lock/spec.md의 인수 조건마다 tests/acceptance/login-lock.test.ts에 테스트를 하나씩 써라. 명세에 적힌 것만 근거로 한다. 구현 코드는 쓰지 마라. 테스트를 돌려 모두 실패하는 것까지 확인해라. 명세가 모호해서 테스트를 쓸 수 없는 곳은 목록으로 보고해라.

- **B를 따로 두는 이유:** B는 명세에 **글로 적힌 것**만 안다. 그래서 명세의 빈칸이 바로 드러난다. "모호해서 못 쓰겠다"는 보고가 곧 명세 검토다 (3번 template의 "확인 필요" 칸과 같은 역할). 이런 보고가 오면 ①로 돌아가 명세를 고친 뒤 ②를 다시 한다.
- **모두 실패해야 하는 이유:** 구현 전에 통과하는 테스트는 아무것도 검사하지 않는 테스트다. 실패 이유도 본다. "기능이 없어서" 실패해야 한다. 오타나 import 오류로 실패하는 것은 확인이 아니다.
- 사람이 "테스트가 인수 조건과 맞나"를 보고 commit한다.
- 승인한 commit에 tag를 달고 **바로 push한다**. 이 tag가 "승인된 기준"의 표시다. 내 컴퓨터에만 있는 tag는 shell을 쓰는 누구든(구현 session 포함) 옮길 수 있어서 바로 push한다.
```bash
git tag spec-approved/login-lock
git push origin spec-approved/login-lock
```

**③ 구현: session C (새 session, 기준은 못 고친다)**
```bash
claude --settings \
  .claude/implement-settings.json
```
> specs/login-lock/spec.md를 구현해라. tests/acceptance/login-lock.test.ts가 모두 통과해야 끝이다. 테스트와 명세는 고칠 수 없다. 테스트가 틀렸다고 생각되면 고치지 말고 이유를 보고해라.

- `implement-settings.json`은 5번 설정 예시에 있는 파일이다 (`specs/`와 `tests/acceptance/` 편집 금지).
- sandbox를 켜 두면 이 편집 금지 경로가 Bash 명령에도 적용된다. 그래서 `sed` 같은 명령으로 테스트를 고치는 길도 대부분 막힌다. 그래도 빈틈이 있을 수 있으니 ④에서 git으로 한 번 더 확인한다.
- 편집 뒤 lint hook, 끝내기 전 테스트 관문(Stop hook이나 `/goal`)은 4번 그대로 쓴다.
- 테스트가 모두 통과하면 commit한다 (C에게 시키거나 사람이 확인하고). commit하지 않으면 ④의 `git diff main...HEAD`에 구현이 잡히지 않는다.
- "테스트가 틀렸다"는 보고가 오면 사람이 판단한다. 기준을 바꿀지는 사람 몫이다 (원칙 1). 바꾸기로 했다면 ②로 돌아가 C가 아닌 새 session이 고치고, 새 이름으로 tag를 달아 바로 push한다 (예: `spec-approved/login-lock-2`). ④의 명령과 CI 기준 검사의 tag 이름도 새 tag로 바꾼다. 옛 tag와 비교하면 승인한 수정까지 "기준이 바뀌었다"로 잡혀 CI가 계속 실패한다.

**④ 검증: session D (새 session, 구현 과정을 모른다)**

먼저 기준이 그대로인지 본다. D에게 시키거나 사람이 직접 친다.
```bash
git fetch --force --tags origin
git diff --stat \
  spec-approved/login-lock \
  -- specs/login-lock/ \
     tests/acceptance/login-lock.test.ts
```
- 첫 줄은 push해 둔 tag를 다시 fetch해 내 컴퓨터의 tag를 덮어쓴다. 구현하는 동안 내 컴퓨터의 tag가 옮겨졌을 수 있어서다 (②). 이때 `[tag update]`가 나오면 누군가 tag를 옮긴 것이니 그것부터 확인한다.
- 둘째 명령은 아무것도 나오지 않아야 한다. 무언가 나오면 구현하는 동안 기준이 바뀐 것이다.
- `HEAD`를 붙이지 않아서 commit하지 않은 수정까지 잡힌다.

그다음 D에게 맡긴다.
> spec-reviewer agent에게 specs/login-lock/spec.md와 `git diff main...HEAD` 결과를 넘겨 검토하게 해라. 그리고 /security-review를 돌려라.

- **reviewer를 C가 아니라 D에서 부르는 이유:** 위임 prompt를 C가 쓰면 C의 설명("이건 이래서 이렇게 했다")이 섞인다. D는 구현 과정을 모르니 명세와 diff만 넘긴다.

**⑤ CI**
```bash
git push -u origin login-lock
```
- PR을 연다. CI가 깨끗한 server에서 전체 테스트, 정적 분석, dependency 검사를 다시 돌린다.
- ④의 기준 검사도 CI에 넣는다. 바뀐 게 있으면 1로 끝나 CI가 실패한다.
```bash
git diff --quiet \
  spec-approved/login-lock HEAD \
  -- specs/login-lock/ \
     tests/acceptance/login-lock.test.ts
```
- GitHub Actions의 `actions/checkout`은 기본으로 workflow를 실행시킨 commit 하나만 받는다. `fetch-depth: 0`으로 history와 tag를 다 받게 한다.
- 경로는 이 기능의 것으로 좁혀 둔다. PR에서 CI가 검사하는 commit은 PR을 main에 merge해 본 commit이라, 넓게 잡으면 main에서 바뀐 다른 명세까지 걸린다.

**⑥ 사람 review**
- branch protection으로 CI 통과와 사람 승인 없이는 merge가 안 되게 한다.
- **여기서 worktree가 쓸모 있는 때:** main checkout에서는 다음 기능을 하고 있는데 이 PR(예: 12번)을 내 컴퓨터에서 직접 돌려 보고 싶다면, `claude --worktree "#12"`로 PR 코드만 따로 worktree에 checkout한다. main checkout은 건드리지 않는다.

**동시에 하고 싶을 때 (여기서 worktree가 필요하다)**
- 예: C가 로그인 잠금을 구현하는 동안, 나는 main checkout에서 다음 기능(가입)의 명세를 쓰고 싶다. 한 폴더에서 동시에 하면 C의 변경과 내 변경이 섞인다.
- 그래서 main checkout은 다음 기능 branch로 switch하고, login-lock branch는 worktree로 checkout해 C에게 준다.
```bash
# ②까지 commit하고 tag를 push한 상태에서
git switch -c signup main
git worktree add \
  .claude/worktrees/login login-lock
claude --worktree login --settings \
  .claude/implement-settings.json
```
- 마지막 줄은 worktree를 새로 만들지 않고 방금 checkout한 것을 연다. branch 이름이 login-lock 그대로라 ④⑤ 명령을 바꾸지 않아도 된다.
- `--worktree`로 열어야 Claude Code의 isolation check가 켜진다 (4-2).
- `--settings` 경로는 명령을 친 main checkout(my-app/) 기준이다. 이 폴더는 이제 signup branch에 있으니, `implement-settings.json`은 main branch에 commit해 둬야 한다. login-lock에만 있으면 파일을 찾지 못해 멈춘다.
- ④의 session D도 같은 worktree에서 새로 연다: `claude --worktree login`. ④의 기준 검사를 사람이 직접 칠 때도 먼저 `cd .claude/worktrees/login`으로 들어간다. main checkout(지금 signup branch)에서 치면 기준 파일이 모두 지워진 것처럼 나온다.
- merge가 끝나면 직접 정리한다: `git worktree remove .claude/worktrees/login`
- 기능 두 개를 처음부터 동시에 시작할 때는 더 간단하다. terminal 두 개에서 `claude -w login`, `claude -w signup`을 실행하면 각자 remote의 main에서 새 branch(`worktree-login`, `worktree-signup`)를 만든다. 이때는 ①의 `git switch`가 필요 없고, ⑤의 push는 `git push -u origin worktree-login`으로 바꿔 친다.

**iPhone(cloud)에서 할 때**
- session A~D를 sidebar에서 하나씩 새로 연다. session마다 별도의 machine이라 폴더가 섞일 걱정은 없다.
- 단계가 끝날 때마다 login-lock branch에 push하고, 다음 session은 그 branch에서 시작한다.
- iPhone에서 여는 cloud session에는 `--settings` 같은 command line option을 줄 수 없다. cloud session은 repository에 commit된 `.claude/settings.json`을 읽는다.
- 그래서 ②의 승인 commit에, 이 기능의 기준을 막는 deny rule을 `.claude/settings.json`의 `permissions` 안에 함께 넣는 방법이 있다 (설계 제안).
```json
"permissions": {
  "deny": [
    "Edit(**/specs/login-lock/**)",
    "Edit(**/tests/acceptance/login-lock*)"
  ]
}
```
- 이미 `permissions`가 있으면 그 안 `deny` 목록에 두 줄만 더한다. `permissions`를 하나 더 붙이면 뒤의 것만 남아 기존 deny rule이 사라진다.
- 그 뒤 이 branch에서 여는 session은 모두 기준을 고치지 못한다. C, D뿐 아니라 ③에서 기준을 고치러 여는 새 session도 막힌다. 그래서 cloud에서 기준을 바꾸기로 했다면 사람이 GitHub에서 명세·테스트를 직접 고치고 새 tag를 단다. session에 맡기려면 이 deny rule을 잠시 빼는 commit을 하고, 고친 뒤 rule을 되돌리는 commit과 함께 새 tag를 단다.
- 이 rule은 main에 merge한 뒤에도 남는다. 그러면 "승인된 명세는 사람만 고친다"는 규칙이 된다.
- **cloud session은 tag를 push하지 못한다.** GitHub proxy가 branch가 아닌 push(tag 등)를 거부해서, ②의 `git push origin spec-approved/login-lock`이 실패한다. 그래서 ②의 승인 commit을 login-lock에 push한 뒤, ③을 시작하기 전에 사람이 tag를 만든다.
  - iPhone뿐이면: GitHub repository의 Releases → Draft a new release를 연다. tag 칸에 `spec-approved/login-lock`을 새로 쓰고, **Target을 login-lock branch로 바꾼 뒤** publish한다. Target을 기본값(main)으로 두면 엉뚱한 commit에 달리고, `Save draft`로 저장만 하면 tag가 생기지 않는다.
  - 노트북이 있으면: `git fetch origin` → `git tag spec-approved/login-lock origin/login-lock` → `git push origin spec-approved/login-lock`
- tag가 GitHub에 있어야 새로 받는 session(C, D)과 CI가 쓸 수 있다. 기준 검사(tag 비교)는 ⑤의 CI가 맡는다.

**이 문서도 이렇게 만들었다**
- 주제 1~6은 작성한 Claude가 초안을 쓰고, 새 context에서 시작한 검증 agent들이 공식 문서와 원문에 대조해 틀린 곳을 찾았다.
- 이번 4-1~4-3도 사실 확인 agent와 읽기 검토 agent가 두 번 봤고, 찾은 문제마다 반박 agent가 정말 문제인지 다시 따졌다. 틀린 곳(hook의 `$CLAUDE_PROJECT_DIR`, cloud에서 tag push)과 순서가 어긋난 곳 여럿을 고쳤다.
- 다만 검증 agent를 작성한 Claude가 직접 불렀으니, 4-3 기준으로는 "반쯤 독립"이다. 마지막 관문은 사람(당신)의 확인과 merge다.

#### 5. 자율성은 위험에 비례한다

| 위험 | 예 | 설정 |
|---|---|---|
| 낮음 (되돌릴 수 있음) | 문서, 테스트 | acceptEdits + sandbox |
| 중간 | 업무 로직, API | 하나씩 묻는 default mode + sandbox, diff 확인 |
| 높음 | 고객 데이터, 권한, 결제, 운영 | deny로 금지, 배포는 사람 승인 뒤 CI에서만 |

**장치별 역할**
- **permission mode:** default(화면에는 Manual), acceptEdits, plan, auto, dontAsk, bypassPermissions가 있다.
  - acceptEdits: working directory 안의 파일 편집은 묻지 않고 허용한다.
  - auto: 사람 대신 classifier가 판단한다. 운영 배포·migration, 권한 부여, force push 등은 기본으로 막는다. 그래도 classifier는 사람이 아니다.
  - dontAsk: 물어봐야 하는 것은 모두 거부한다. CI용이다.
  - bypassPermissions: 격리된 container나 VM에서만 쓰라고 안내돼 있다.
  - auto와 bypassPermissions는 project의 `settings.json`이나 `settings.local.json`에 써도 **무시된다.** user settings(`~/.claude/settings.json`), managed settings, command line(`--permission-mode`, `--settings`)에서 정한다.
- **permission rule:** deny → ask → allow 순서로 검사하고, 처음 맞는 rule이 이긴다. 어느 scope의 deny든 allow보다 앞선다.
- **Bash rule은 보안 경계가 아니다.** `Bash(rm *)`로 막아도 `/bin/rm`이나 `bash -c 'rm ...'`은 막지 못한다. OS 수준으로 막으려면 sandbox를 쓴다.
  - sandbox는 기본으로 꺼져 있다. 켜도 설치가 안 된 환경에서는 sandbox 없이 그냥 실행된다. 그래서 `failIfUnavailable`을 켜 둔다.
- **hook이 오류로 끝나도 작업은 막히지 않는다.** 막으려면 `exit 2`로 끝내야 한다. `exit 1`은 경고만 남기고 그대로 진행된다.
- **조직 정책은 managed settings로 둔다.** 개발자가 덮어쓸 수 없다.

구현 session에만 거는 추가 잠금 `.claude/implement-settings.json`. command line의 `--settings`는 project settings보다 우선하고, deny 목록은 합쳐진다. 주의: 이 파일에서 `/specs/**`처럼 `/`로 시작하는 경로는 **이 파일이 있는 `.claude/` 기준**으로 풀린다. 그래서 `**/`로 쓴다.
```json
{
  "permissions": {
    "deny": ["Edit(**/specs/**)", "Edit(**/tests/acceptance/**)"]
  }
}
```
실행: `claude --settings .claude/implement-settings.json`. 다른 일과 동시에 돌리려면 worktree로 연다 (4-3의 "동시에 하고 싶을 때").

보호 hook `.claude/hooks/protect-files.sh`:
```bash
#!/bin/bash
INPUT=$(cat)
FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
case "$FILE" in
  *.env*|*/migrations/*)
    echo "Blocked: $FILE 는 사람 승인이 필요한 파일입니다" >&2
    exit 2 ;;
esac
exit 0
```
그다음 `chmod +x .claude/hooks/protect-files.sh`로 실행 권한을 준다. 실행 권한이 없으면 hook이 시작조차 못 하는데, 이때도 편집은 그대로 통과한다. `exit 2`만 차단한다. commit된 hook은 팀원 컴퓨터와 CI에서 실행되는 코드이므로 코드처럼 review한다.

#### 6. 프로젝트 지식은 저장소에서 관리한다: 무슨 뜻?
**뜻.** 대화창에 길게 쓴 prompt는 session이 끝나거나 context가 compact(`/compact`)되면 사라진다. 다른 사람, 다른 session, CI에서는 보이지도 않는다. repository의 파일은 버전 관리되고, PR로 review되고, 모든 session이 같은 내용을 본다. 즉 **"AI에게 하는 말"을 코드처럼 다루자**는 뜻이다. 공식 문서도 대화로만 준 지시는 compaction 뒤에 남지 않으니 CLAUDE.md에 적으라고 한다.

**가까운 예: 이 repository.** Daily_Think가 이미 원칙 6의 작은 예다. CLAUDE.md가 규칙이고, `index/memo.md`가 원문, `daily/`가 정리, `references/`가 근거다. 어제(10/14) CLAUDE.md에 "참조자료가 있으면 마지막에 정리" 한 줄이 들어가자, 그다음 답부터 참조자료가 붙었다. 대화로 매번 부탁하지 않아도 repository의 규칙이 일을 바꾼 것이다. 다만 빈틈도 보인다. CLAUDE.md의 폴더 구조에 `references/`가 없고, `.claude/settings.json`도 없다. 그래서 이 repository의 규칙은 아직 모두 "요청"이다.

**두 종류로 나눠 본다**
- Claude Code가 **스스로 읽는 것:** CLAUDE.md, `.claude/rules/`, `.claude/skills/`, `.claude/agents/`, `.claude/settings.json`
- **가리켜 줘야 읽는 것:** `docs/architecture/`, `docs/adr/`, `specs/`, `policies/`, `tests/`

※ 표가 넓어서 휴대폰에서는 옆으로 밀어서 본다.

| 무엇 | 어디에 | 언제 load되나 | 성격 |
|---|---|---|---|
| 공통 규칙 | CLAUDE.md (200줄 이하 권장) | 매 session | 요청 |
| 경로별 규칙 | .claude/rules/*.md | 맞는 파일을 읽거나 고칠 때 | 요청 |
| 구조·경계 | docs/architecture/ | 가리킬 때 | 요청 |
| 기술 결정 | docs/adr/ | 가리킬 때 | 요청 |
| 요구사항·설계 | specs/ | 작업할 때 지정 | 요청, 테스트로 바꾸면 검증 |
| 조직 정책 | policies/ | 가리킬 때 | 요청, 강제는 설정으로 |
| 기대 동작 | tests/ | 실행할 때 | **검증** |
| 반복 절차 | .claude/skills/ | 맞을 때, /이름 | 요청 |
| 전문 작업자 | .claude/agents/ | 위임할 때 | 요청, tool 목록은 강제 |
| 차단·자동화 | .claude/settings.json | 항상 | **강제** |
| 개인 학습 | auto memory (repository 밖) | 매 session 앞부분 | 요청, 공유 안 됨 |

**운영 요령**
- CLAUDE.md에 명세 전체를 `@import` 하지 않는다. import한 파일도 매 session 통째로 load된다. "명세는 `specs/<기능>/spec.md`에 있다"처럼 위치만 적는다.
- CLAUDE.md의 한 부분이 "사실"이 아니라 "절차"로 자라면 skill로 옮긴다. skill 본문은 쓸 때만 load된다.
- CLAUDE.md 수정도 PR로 review한다. 큰 model update 뒤에는 다시 읽어 본다. 예전 model의 한계를 피하려던 지시가 오히려 짐이 될 수 있다.
- auto memory에서 쓸 만한 교훈을 발견하면 CLAUDE.md나 rule로 옮겨 적는다("승격").
- 무엇이 load됐는지는 `/memory`, `/context`, `/permissions`, `/hooks`로 확인한다.

<summary><b>적어 주신 목록에서 고칠 점 펼치기</b></summary>

- `.claude/setting.json` → **`.claude/settings.json`** (팀 공유, commit). 개인용은 `.claude/settings.local.json`이다. 우선순위는 managed settings > command line `--settings` > `settings.local.json` > `settings.json` > user `~/.claude/settings.json`이다.
- `Claude.md` → **`CLAUDE.md`** (대문자). repository root나 `.claude/CLAUDE.md`에 둔다.
- `.claude/rules/`는 **있다**. 다만 언어를 고르는 칸은 없고, 파일 경로 pattern(`paths:`)으로 범위를 정한다. 그래서 언어별 규칙도 `**/*.py`처럼 만든다. `paths`가 없는 rule은 매 session 통째로 load된다.
- `docs/architecture/`, `docs/adr/`, `specs/`, `policies/`, `tests/`는 Claude Code가 이름을 보고 알아서 읽거나 강제하는 폴더가 **아니다**. 평범한 폴더라서 CLAUDE.md, rule, skill에서 가리켜 줘야 읽는다.
- `policies/`에 정책 문서를 두는 것만으로는 아무것도 막지 못한다. 막아야 하는 정책은 deny rule, hook, managed settings로 옮긴다.
- auto memory는 repository **밖**(`~/.claude/projects/<프로젝트>/memory/`)에 있다. 내 컴퓨터에만 있고 버전 관리도 안 돼서 팀 지식이 될 수 없다.

</details>

#### 7. 운영 결과가 최종 피드백이다: 어떤 개념?
**뜻.** 성공의 기준을 "AI가 코드를 얼마나 빨리, 많이 만들었나"가 아니라 "운영에서 실제로 무슨 일이 일어났나"에 둔다. 그리고 문제가 생기면 코드만 고치지 않고, **같은 문제를 다시 만들지 않도록 명세·규칙·테스트를 고친다.** repository가 운영에서 배우는 구조다.

**왜 필요한가**
- DORA 2024 조사: AI 도입 정도가 25% 높아질 때마다 delivery throughput은 약 1.5%, delivery stability는 약 7.2% 낮아지는 것으로 추정됐다. DORA는 코드가 빨리 나오면서 batch size가 커진 탓으로 본다.
- DORA 2025 조사(주제 5): throughput은 오르는 쪽으로 바뀌었지만 instability는 여전히 늘었다. AI는 amplifier라서, 작은 batch로 일하기와 version control이 그 instability를 막는 안전망이 된다.
- DORA는 "받아들여진 코드 줄 수" 같은 생산량 지표가 도구를 얼마나 쓰는지 보는 데는 쓸 만하지만, 실제 생산성의 척도로 기대지는 말라고 권한다. AI가 코드 양을 쉽게 부풀리기 때문이다.

**무엇을 재나**
- **배포 성과(DORA 5개 지표).** throughput은 change lead time, deployment frequency, failed deployment recovery time이다. instability는 change fail rate와 deployment rework rate이다. 흔히 말하는 "4대 지표"는 옛 모델이고, 2024년에 rework rate가 더해졌다.
- **SLO(서비스가 지켜야 할 품질 목표)와 error budget(그 목표 안에서 허용되는 실패량).** 예를 들어 목표가 99.9%면, 4주 동안 요청 100만 건 중 1,000건까지 실패를 허용한다. Google SRE의 예시 정책은 이 budget을 다 쓰면 긴급 수정(P0)과 보안 수정 말고는 배포를 멈춘다.
- **보안:** 취약점, secret 유출, 권한 사고
- **비용:** infra 비용, AI token 비용
- **사용자 가치:** 명세의 성공 기준과 실제 사용 지표

**feedback loop: 장애 → repository**
- 장애가 나면 **blameless postmortem**(장애 뒤에 쓰는 회고 문서. 사람 탓이 아니라 원인에 집중한다)을 쓰고, 고칠 곳을 정한다.
  - 명세가 빠뜨렸다 → `specs/` 갱신 ("바꾸면 안 되는 것"에 추가)
  - 테스트가 못 잡았다 → `tests/`에 회귀 테스트 추가
  - Claude가 규칙을 어겼다 → CLAUDE.md나 rule 수정, 반복되면 hook으로 강제
  - 결정이 틀렸다 → 새 ADR (이전 ADR은 "superseded"로 표시)
  - 위험 등급을 낮게 잡았다 → permission rule과 승인 절차 강화
- 이 변경도 모두 PR로 review한다.
- Claude Code가 도울 수 있는 일: postmortem 초안, 회귀 테스트 작성, CLAUDE.md 수정 제안. 예약 실행되는 GitHub Actions(schedule trigger)로 정기 점검을 돌릴 수도 있다.
- 다만 운영 지표를 읽어 명세까지 자동으로 고쳐 주는 도구는 없다. 이 loop는 **팀의 절차**다.

**주의 (DORA)**
- 지표를 목표로 삼지 않는다. 목표가 된 지표는 지표 구실을 잃는다 (Goodhart's law).
- 서로 다른 팀이나 서비스끼리 비교하지 않는다.
- token 사용량 같은 입력 지표로 사람을 평가하지 않는다. DORA는 회사 전체 합계는 의미가 없고, 개인 점수는 해롭다고 한다.

#### 작게 시작하는 순서
1. CLAUDE.md를 200줄 이하로 정리하고, `settings.json`에 deny(secret 파일, 운영 명령)를 넣고, sandbox를 켠다.
2. `specs/` template을 만든다. 기능 하나를 명세 승인 → 다른 session이 인수 테스트 → 새 session 구현(필요하면 plan mode로 계획부터)으로 해 본다 (4-3). 명세를 쓰기 전에 코드를 조사해야 하면 그때도 plan mode로 시작한다.
3. reviewer agent, CI 테스트, branch protection을 붙인다.
4. 보호 hook과 편집 뒤 lint hook을 걸고, 장애가 나면 명세·테스트를 고치는 습관을 들인다.
5. 그다음에 Spec Kit 같은 도구를 쓰거나 auto mode의 범위를 넓힌다.

#### 앞 주제와 이어 보면
- 주제 5의 DORA 2025 "AI는 amplifier"와 7가지 역량(clear and communicated AI stance, healthy data ecosystems, AI-accessible internal data, strong version control practices, working in small batches, user-centric focus, quality internal platforms)이 이 방법론을 뒷받침한다. 특히 "AI-accessible internal data"가 원칙 6이다.
- 주제 5에서 Deloitte 조사 기업 가운데 agent governance 체계가 성숙한 곳은 21%였다 (agent를 어느 정도 이상 쓰는 곳은 23%, 2년 뒤 예상 74%). 원칙 4와 5가 바로 그 governance다.
- 주제 4 표의 "앞으로" 줄에 적은 "AI가 코드·배포를 돕고 사람이 검토"를 실제로 운영하는 방법이 이 주제다.
