### Claude

#### 한 줄 요약
JSP는 **server**에서 실행되어 HTML을 만들고, JavaScript는 그 HTML을 받은 **browser**에서 실행된다. WAS는 JSP 같은 server 프로그램을 실행해 주는 server다.

#### 요청 하나가 처리되는 순서
1. 사용자가 browser에서 `list.jsp` 주소를 연다.
2. WAS가 요청을 받아 JSP를 실행한다. 이때 Java 코드가 돌고, 필요하면 DB도 조회한다.
3. 실행 결과로 **HTML 문서(텍스트)** 가 만들어져 browser로 간다. JSP 코드 자체는 browser로 가지 않는다.
4. browser가 HTML을 위에서부터 읽으며 화면을 그리다가, `<script>`를 만나면 그 JavaScript를 실행한다.
5. 그 뒤 버튼 클릭 같은 사용자 동작은 browser 안의 JavaScript가 처리한다. server의 데이터가 다시 필요하면 새로 요청을 보낸다.
   - 페이지 이동: JSP가 다시 실행되어 새 HTML 전체가 온다.
   - `fetch`/AJAX: 보통 데이터(JSON)만 받아서, JavaScript가 새로고침 없이 화면 일부만 바꾼다.

#### JSP
- Java Server Pages. HTML 사이에 Java 코드를 섞어 쓰는 **server 쪽** 기술이다.
- 처음 요청이 오면 WAS가 JSP를 **순수 Java 프로그램(servlet)으로 바꾸고 compile**한다. 이후엔 그것을 바로 실행하고, JSP를 고치면 (개발 설정에서는 보통) 이 과정을 다시 한다.
- 결과물은 HTML 텍스트일 뿐이다. browser에서 "페이지 소스 보기"를 하면 JSP 코드는 없고 HTML만 보인다.

#### JavaScript
- 주로 browser 안에서 실행되는 언어다. (server에서도 돌릴 수 있다 → 아래 Node.js)
- server가 HTML을 보낸 **뒤에** browser에서 실행된다. 화면 요소(DOM)를 바꾸고, 클릭·입력에 반응하고, server에 추가 요청을 보낸다.
- 이름이 비슷하지만 Java와는 전혀 다른 언어다.

#### 가장 헷갈리는 지점: 실행 순서
```jsp
<% String name = "홍길동"; %>
<script>
  var name = "<%= name %>";
  alert(name);
</script>
```
- `<% %>` 안은 server에서 도는 Java 코드, `<%= %>`는 그 값을 그 자리에 찍는 표시다.
- server에서 JSP가 먼저 실행되어 `<%= name %>` 자리에 `홍길동`이 들어간다.
- browser가 받는 것은 `var name = "홍길동";` 이라는 JavaScript 코드일 뿐이다.
- 그래서 JSP는 JavaScript **코드를 만들어낼** 수는 있지만, 반대로 JavaScript가 JSP 변수를 직접 바꿀 수는 없다. server에서 실행이 이미 끝났고, 그 변수도 응답을 보낼 때 사라졌기 때문이다.
- 반대 방향(browser → server)은 **새 요청**에 값을 실어 보낸다. 예: `list.jsp?name=김철수`, form 전송, `fetch`. 그러면 JSP가 처음부터 다시 실행되고 `request.getParameter("name")`으로 그 값을 읽는다.
- 참고: 사용자 입력을 이렇게 그대로 넣으면 따옴표 때문에 코드가 깨지거나, 남이 넣은 script가 실행될 수 있다(XSS). 그래서 특수문자를 안전한 글자로 바꿔 넣는다(escape). 바꾸는 방법은 넣는 위치에 따라 다르다 (HTML 안인지, 여기처럼 JavaScript 문자열 안인지).

#### WAS (Web Application Server)
- 요청이 올 때마다 **프로그램을 실행해서** 응답을 만들어 주는 server다. 예: Tomcat(가장 많이 씀), JEUS, WebLogic, JBoss(WildFly)
- **web server**(Apache, Nginx)와 비교하면:
  - web server: 이미 만들어진 파일(HTML, 이미지, CSS, JS)을 그대로 돌려준다 → 정적
  - WAS: JSP·servlet을 실행해서 상황마다 다른 결과를 만든다 → 동적
- WAS가 하는 일:
  - JSP·servlet을 실행하고 관리한다 (이 역할을 "servlet container"라고 부른다)
  - 요청마다 thread를 하나씩 붙여, 여러 사람의 요청을 동시에 처리한다
  - 요청 사이에 "누가 로그인했는지" 같은 사용자별 정보를 기억한다 (session)
  - DB 연결을 미리 만들어 두고 나눠 쓰게 해 준다 (connection pool)
- 실무에서는 앞에 web server를 두고, 정적 파일은 web server가, 동적 요청은 WAS가 처리하도록 나누는 경우가 많다.

#### 다시 정리: 네 가지의 관계 (추가 질문)

**먼저 둘로 나누기**
- **코드**: JSP, JavaScript → 누군가 실행해 줘야 하는 프로그램
- **server**: web server, WAS → 요청을 기다렸다가 응답하는 프로그램 (server 컴퓨터에서 돈다)

**짝으로 기억하기**
- JSP는 **WAS**가 실행한다. WAS 없이는 JSP가 돌지 않는다.
- JavaScript는 **browser**가 실행한다. web server·WAS는 JS 파일을 실행하지 않고 보내기만 한다.
- **web server**는 이 구조에서 코드를 실행하지 않는다. 이미 있는 파일은 바로 보내고, JSP 요청은 WAS로 넘긴다.

**그림**
```
browser (JavaScript 실행)
   ↕
web server (파일 전달, JSP는 WAS로)
   ↕
WAS (JSP 실행 → HTML)
   ↕
DB
```
※ web server는 빼도 된다. Tomcat 같은 WAS가 파일 전달도 할 수 있어서, 연습할 땐 WAS 하나면 충분하다.

**요청 따라가 보기**
- `list.jsp`: web server가 WAS로 넘김 → JSP 실행(DB 조회) → HTML이 browser로
- 그 HTML 속 `app.js`, `logo.png`: browser가 다시 요청 → web server가 파일 그대로 보냄 (WAS는 쉼) → `app.js`는 browser에서 실행

**식당으로 비유하면**
- web server = 카운터: 미리 만들어 둔 것은 바로 건네고, 요리 주문은 주방으로 넘긴다
- WAS = 주방
- JSP = 주방의 레시피: 손님은 레시피를 볼 수 없고, 완성된 요리(HTML)만 받는다
- JavaScript = 손님에게 주는 "자리에서 이렇게 하세요" 안내 카드: 따라 하는 건 손님 자리(browser)다. 레시피와 달리 손님도 볼 수 있다. 요리에 끼워 오기도 하고(HTML 속 `<script>`), 카운터에서 따로 받기도 한다(`app.js`). 더 필요하면 다시 주문(새 요청)한다

**web server와 WAS를 왜 나누나**
- 이미 있는 파일은 web server가 빨리 보내고, WAS는 JSP 실행에만 집중한다.
- WAS가 인터넷에 직접 노출되지 않아 더 안전하다.
- WAS를 여러 대 두면 web server가 요청을 골고루 나눠 준다 (load balancing).

#### Node.js (추가 질문: 원래 궁금했던 것)

**한 줄 요약**
Node.js는 언어가 아니라, JavaScript를 **browser 밖에서** 실행해 주는 프로그램이다. 덕분에 JavaScript로 **server**도 만들 수 있다.

**앞의 짝에 넣어 보면**
- JSP(Java) → **WAS**가 실행
- JavaScript → **browser**가 실행
- JavaScript → **Node.js**가 실행 ← 새 짝

단, Node.js는 켜기만 해서는 server가 아니다. 내 server 코드를 실행해야 server가 된다. (아래 "Node.js와 NestJS" 참고)

**같은 JavaScript, 할 수 있는 일은 다르다**
Chrome 안에서 JavaScript를 실행하던 부분(V8 engine)을 떼어 내고, 파일·network 기능을 붙여 browser 없이 돌게 만든 것이 Node.js다. 그래서 누가 실행하느냐에 따라 쓸 수 있는 기능이 다르다.
- browser의 JavaScript: 화면을 바꿀 수 있다 (`document.getElementById` 같은 `document` 기능). server의 파일이나 DB에는 직접 손대지 못한다.
- Node.js의 JavaScript: 파일 읽기·쓰기, DB 연결, 요청 받기가 된다. 대신 화면이 없어서 `document`는 쓸 수 없다.

**Node.js가 쓰이는 두 가지**
1. **server 만들기**: JSP + Tomcat 자리를 JavaScript + Node.js가 대신한다. Tomcat은 켜기만 하면 요청을 기다리는 server라 JSP만 넣으면 되지만, Node.js는 내 server 코드를 실행해야 server가 된다. 그 코드가 요청을 받아 HTML이나 데이터(JSON)를 돌려준다 (보통 Express·NestJS 같은 framework로 짠다). 그래서 Tomcat 같은 WAS를 따로 설치하지 않는다.
2. **개발 도구 돌리기**: server를 만들지 않아도 Node.js를 설치하는 경우가 많다. `npm`(남이 만든 코드를 내려받는 도구)과, React·Vue로 짠 화면 코드를 browser용 JS 파일로 묶어 주는 도구(Vite 등)가 Node.js로 돌기 때문이다. React·Vue 자체는 browser에서 돈다.

**그림 (Node.js로 server를 만든 경우)**
```
browser (화면용 JS 실행)
   ↕
web server (Nginx, 없어도 됨)
   ↕
Node.js + 내 server 코드
(server용 JS 실행 → HTML/JSON)
   ↕
DB
```
※ Node.js server도 browser용 JS 파일(앞의 `app.js`)은 실행하지 않고 그대로 보낸다. Node.js가 실행하는 것은 server용 JS 파일뿐이다.

**헷갈리지 않기: 둘 다 JavaScript여도 따로 돈다**
server용 JavaScript(Node.js)와 화면용 JavaScript(browser)는 같은 언어지만 따로 도는 별개의 프로그램이다. 내 컴퓨터 한 대에서 둘 다 띄워 연습해도 마찬가지다. JSP 때와 똑같이, browser JavaScript가 server의 변수를 직접 바꿀 수 없고 **요청**으로 주고받는다.

**왜 Node.js를 쓰나**
- 화면과 server를 한 언어(JavaScript)로 만들 수 있다.
- WAS는 요청마다 thread를 붙이지만, Node.js는 thread 하나가 DB 응답을 기다리는 동안 다른 요청을 먼저 처리한다. 그래서 기다림이 많은 요청(DB 조회, 채팅 등)을 많이 받는 데 강하다.

#### Node.js와 NestJS (추가 질문)

**정리하면**
- **NestJS는 Node.js 안에 없다.** `npm`으로 따로 설치하는 framework다. Node.js 안에 처음부터 있는 것은 요청을 받는 기본 module(`http`)뿐이다.
- **Node.js는 켜기만 해서는 server가 아니다.** JS를 실행하는 runtime이라서, 내 코드가 "요청을 기다려라"(`listen`)라고 해야 server가 된다.
- Tomcat은 다르다. 켜기만 해도 내 코드 없이 8080번 port에서 요청을 기다린다.
- 그래서 Node.js가 내 코드(NestJS 등)를 실행하고 있을 때, 그 실행 중인 프로그램이 server다.

**Node.js 안에 있는 것: 기본 module**
```js
const http = require('http');
http.createServer((req, res) => {
  res.end('hello');
}).listen(3000);
```
`require`로 module을 불러오고, 요청(req)이 오면 응답(res)으로 hello를 보낸다. 이 코드를 `server.js`로 저장해 `node server.js`로 실행하면, 3000번 port(server의 문 번호)에서 요청을 기다리는 server가 된다. 마지막 `listen(3000)`이 없으면 아무 요청도 기다리지 않는다.

**NestJS, Express: 따로 설치하는 framework**
- 기본 module만으로 server를 짜기엔 번거로워서 만든 **framework**다. 둘 다 `npm`으로 설치한다.
- Express는 주소별로 할 일 나누기를 쉽게 해 주는 단순한 framework다.
- NestJS는 그 위에 입력값 검사, DB 연결 같은 것을 정해진 구조로 붙이게 해 주는 큰 framework다.

**층으로 보면** (1~4는 위가 바로 아래를 쓰고, 5가 전부를 실행한다)
1. 내 코드: NestJS 규칙대로 작성
2. NestJS: 큰 framework (npm 설치)
3. Express: 단순한 framework. NestJS가 기본으로 안에서 쓴다 (npm 설치)
4. `http` module: Node.js에 처음부터 들어 있음
5. Node.js: 1~4를 모두 실행하는 runtime

**NestJS 앱의 자리**
NestJS로 만든 앱은 처음 그림의 **WAS 자리**에 들어간다 (Node.js 그림의 "Node.js + 내 server 코드" 칸). Tomcat 같은 WAS를 따로 설치하지 않을 뿐, 하는 일은 WAS와 같다. session, DB 연결 관리처럼 WAS가 해 주던 일은 NestJS나 다른 npm package로 붙인다.

일상에서는 이것도 "web server"라고 부르지만, 이 노트에서 web server는 파일 전달과 요청 중계(HTTPS, load balancing)를 맡는 Nginx 같은 것을 뜻한다.

**Java 쪽과 나란히**
- 요청 받기: Tomcat ↔ Node.js의 `http` module
- server 코드 framework: Spring ↔ Express, NestJS

NestJS는 구조가 Spring과 많이 닮았다. 요즘 Spring Boot는 Tomcat을 앱 안에 넣어 함께 실행해서, Node.js + NestJS와 모양이 비슷하다.

#### WAS가 필요한 세상일까? (추가 질문)

**반은 맞다.**
- 요즘 서비스는 로그인, 검색, 결제처럼 요청마다 결과가 달라진다. 그래서 **WAS 역할**(코드를 실행해 결과를 만드는 일)이 없는 서비스는 거의 없다.
- 그런데 **web server도 사라지지 않았다.** Nginx 같은 web server는 지금도 많은 서비스의 맨 앞에서 암호화(HTTPS), 파일 전달, 요청 나눠 주기(load balancing)를 맡는다. 이미지·JS 파일은 CDN(세계 곳곳에 복사본을 두고 가까운 곳에서 보내 주는 서비스)이 맡기도 한다.
- 바뀐 것은 **WAS의 모양**이다. 예전엔 Tomcat·JEUS 같은 WAS를 따로 설치하고 그 안에 내 코드를 넣었다. 지금은 Spring Boot나 Node.js처럼 **WAS 역할이 내 앱 안에 들어가** 앱 하나로 실행하는 경우가 많다.
- 화면을 만드는 곳도 옮겨 갔다. 예전엔 server(JSP)가 HTML을 다 만들었지만, 요즘은 server는 데이터(JSON)만 주고 browser의 JavaScript(React 등)가 화면을 그리는 경우가 많다. 다만 Next.js처럼 Node.js server가 다시 HTML을 만들어 보내는 방식(SSR)도 많이 쓴다.

정리: "WAS만 필요한 세상"이라기보다, **WAS 역할은 어디에나 있고(이제는 앱 안에), web server는 맨 앞 카운터로 남은 세상**이다.

#### WAS의 역사 (추가 질문)

**큰 흐름 먼저**
파일 전달(web server) → 요청마다 프로그램 실행(CGI) → 프로그램을 띄워 두기(servlet·JSP) → 크고 표준화된 WAS(J2EE) → 가볍게(Spring) → WAS가 앱 안으로(Node.js, Spring Boot)

※ 앞 단계가 사라진 게 아니라 위에 쌓였다. web server도, Tomcat·JEUS 같은 전통 WAS도 지금 함께 쓰인다.

**1. 파일만 보내던 시절 (1990~)**
- 첫 web server(CERN httpd)는 미리 만든 HTML 파일을 보내 주기만 했다. 누가 와도 같은 페이지였다.

**2. CGI: 요청마다 프로그램 실행 (1993~)**
- web server가 요청을 바깥 프로그램(C, Perl 등)에 넘겨 실행시키고, 그 출력(HTML)을 받아 돌려준다. 이 방식을 공통 규칙(CGI)으로 정해서, 어느 web server에서나 요청마다 다른 결과를 만들 수 있게 됐다.
- 문제: 요청이 올 때마다 프로그램을 새로 켰다 껐다 해서 느리고 무거웠다.

**3. 프로그램을 띄워 두기 (1995~1999)**
- 배경: 1995년에 Apache web server, PHP(처음엔 CGI 방식), Java, JavaScript(browser용)가 나왔다.
- 1996: Microsoft ASP. HTML 속에 코드를 넣는 방식이다.
- 1997: Java **servlet**. 프로그램을 한 번 띄워 두고 요청마다 thread만 붙이는, CGI의 느림에 대한 Java 쪽 해결책이다. (비슷한 때 FastCGI 같은 다른 해결책도 나왔다.)
- 1999: **JSP** 1.0. servlet에서 HTML을 한 줄씩 찍어 내던 불편을 줄이고 ASP에 맞서려고, HTML 속에 Java를 넣는 방식이 나왔다. 같은 해 Sun이 servlet·JSP 실행 코드를 공개해 **Tomcat**이 나왔다.

**4. application server 전성기 (1999~2000년대)**
- 1999: **J2EE**. Java로 기업용 시스템을 만드는 표준 묶음(servlet, JSP, EJB, DB 연결 등)이다. 이 중 EJB(업무 로직을 server가 관리해 주는 component)가 크고 무거운 부분이었다.
- 이 표준을 모두 갖춘 큰 server가 **application server**다. 상용으로 WebLogic(BEA, 지금은 Oracle), WebSphere(IBM), 국산 JEUS(TmaxSoft), 무료 open source로 JBoss(지금 WildFly)가 있다.
- Tomcat은 이 중 servlet·JSP 부분만 갖춘 가벼운 server(앞에서 말한 servlet container)다. 한국에서는 Tomcat도 WAS라고 부르지만, 영어권에서는 servlet container와 application server를 나눠 부르는 일이 많다. (영어로 "WAS"라고 하면 보통 IBM WebSphere Application Server를 뜻한다.)
- 한국에서는 은행·공공기관을 중심으로 "web server + WAS" 구성(예: WebtoB + JEUS, Apache + Tomcat)이 널리 쓰였고, "WAS"라는 말도 특히 많이 쓴다.

**5. 가벼워지는 시대 (2004~)**
- 2004: **Spring** 1.0. 무거운 component(EJB) 없이도 기업용 기능을 쓰게 해 줘서 Tomcat만으로 충분해졌다. "Tomcat + Spring"이 널리 쓰이기 시작했다.
- 2004: **Nginx**. 동시 접속이 많아도 가볍게 버티는 web server.
- 2005: **AJAX**라는 이름이 붙으며 널리 퍼졌다 (기술 자체는 1999년부터 있었다). 이후 server가 HTML 대신 데이터만 주는 방식이 크게 늘었다.

**6. WAS가 앱 안으로 (2009~)**
- 왜? 서비스를 작은 앱 여러 개로 나누고 cloud에 자주 배포하게 되면서, server마다 WAS를 따로 설치·설정하기보다 앱 하나에 넣어 실행하는 편이 간단해졌다.
- 2009: **Node.js**. 원래 기다림 많은 요청을 thread 하나로 처리하려고 만들어졌다. 처음부터 WAS를 따로 두지 않고, 내 코드가 `http` module로 직접 요청을 받는 방식이었다.
- 2014: **Spring Boot** 1.0. Tomcat을 앱 안에 넣어, 앱 파일 하나만 실행하면 server가 뜬다. Java 쪽도 WAS를 따로 설치하지 않아도 되게 됐다 (기존 WAS에 올리는 방식도 여전히 쓴다).
- 2017: **NestJS**.

**7. 지금 (2020년대)**
- 지금 모습은 위 "WAS가 필요한 세상일까?" 참고.
- JEUS·WebLogic 같은 전통 WAS도 은행·공공기관 같은 큰 시스템에서 지금도 쓰인다.

**오늘 질문과 이어 보면**
JSP를 실행하던 Tomcat(3~4단계)과 NestJS 앱을 실행하는 Node.js(6단계)는 **같은 WAS 자리의 다른 세대**다. 다만 JSP는 HTML을 만들고, NestJS 앱은 보통 데이터(JSON)만 준다.

#### web server의 역사 (추가 질문)

**큰 흐름 먼저**
문서 공유(CERN) → 누구나 쓰는 web server(Apache) → 동시 접속 문제 → Nginx → cloud용 새 server(Caddy 등) → CDN이 맨 앞에 서는 시대

※ 여기서도 앞 세대가 사라진 게 아니라 함께 쓰인다.

**1. 왜 시작됐나 (1989~1993)**
- 1989: CERN(유럽 입자물리연구소)의 Tim Berners-Lee가 web을 제안했다. 여러 컴퓨터에 흩어진 연구 문서를 링크로 잇자는 아이디어였다.
- 링크를 누르면 그 문서가 있는 컴퓨터가 문서를 보내 줘야 한다. 그래서 컴퓨터마다 "요청을 기다렸다가 문서를 건네주는 프로그램"이 필요했다. 이것이 web server다.
- 1990: 첫 web server(CERN httpd)와 첫 browser를 만들었다. 주고받는 규칙(HTTP)과 문서 형식(HTML)도 이때 함께 나왔다.
- 1993: CERN이 web 기술을 누구나 무료로 쓰게 공개했다. 같은 해 쓰기 쉬운 그림 화면의 browser(NCSA Mosaic)도 나와, web이 빠르게 퍼졌다.

**2. NCSA → Apache: 누구나 쓰는 web server (1993~)**
- 1993: 미국 대학 연구소(NCSA)가 web server NCSA HTTPd를 만들었다. 앞에서 본 CGI도 여기서 나왔다.
- 1995: NCSA HTTPd 개발이 멈추자, 이를 쓰던 관리자들이 각자 고친 코드를 모아 **Apache**를 만들었다. 무료 open source다. 같은 해 Microsoft IIS도 나와 Windows 쪽에서 많이 쓰였다.
- 1996년부터 Apache가 가장 많이 쓰는 web server가 되어 오랫동안 1위를 지켰다.
- 강점은 module(나중에 끼워 넣는 추가 기능)을 붙이기 쉽다는 것이다. 예: mod_php를 붙이면 PHP를 Apache 안에서 바로 실행한다.
- 그래서 앞에서 "web server는 이 구조에서 코드를 실행하지 않는다"고 한 것은 web server와 WAS를 나눈 구조(Apache + Tomcat, Nginx + Tomcat) 이야기다. Apache에 mod_php를 붙이면 web server가 WAS 역할까지 한 몸에 맡는다 (카운터 안에 작은 주방이 있는 셈). Nginx도 module로 코드를 실행할 수 있다.

**3. 문제: 동시 접속 (1999, C10K)**
- 초기 Apache는 접속 하나마다 worker 하나를 붙였다.
- 인터넷이 느린 사용자가 연결을 오래 잡고 있으면 worker가 그만큼 묶였다. worker마다 메모리를 차지해서 많이 늘릴 수 없었고, 정해 둔 최대 수에 닿으면 새 접속은 기다려야 했다.
- 1999: Dan Kegel이 "server 한 대로 동시 접속 1만 개를 어떻게 버틸까?"라는 문제를 정리했다. 이름은 C10K(10K = 1만).

**4. Nginx: worker 몇 개가 수천 연결을 처리 (2004~)**
- 러시아 개발자 Igor Sysoev가 포털 Rambler의 많은 접속을 감당하려고 만들었다. 2004년에 공개했다.
- 방식: worker를 CPU 수만큼만 두고, worker 하나가 수천 개 연결을 번갈아 처리한다. 기다리는 연결에 worker를 붙잡아 두지 않으니 메모리를 적게 쓴다.
  - 앞의 카운터 비유로 치면, 초기 Apache는 손님 한 명마다 직원 한 명이 붙어 손님이 메뉴를 고르는 동안에도 옆에서 기다린다. 손님이 몰리면 직원을 계속 늘려야 한다.
  - Nginx는 직원 몇 명이 여러 손님을 번갈아 응대하고, 고민 중인 손님은 두고 준비된 손님부터 처리한다.
- 대세가 된 이유:
  - 파일 전달이 빠르고 가볍다.
  - WAS 앞에서 요청을 대신 받아 뒤의 Tomcat·Node.js로 넘기는 역할(**reverse proxy**)에 딱 맞았다. HTTPS 처리와 load balancing도 같이 맡는다.
- 요즘 새로 만드는 서비스에서는 web server 자리에 Nginx가 가장 흔하다 (한국 은행·공공기관에서는 WebtoB·Apache도 여전히 많다). 2020년 전후로 사용 점유율에서 Apache를 앞섰다 (조사마다 다름).
- Apache도 2005년 실험적으로, 2012년 정식으로 비슷한 방식(event)을 넣었다. 다만 처리 중인 요청에는 여전히 worker가 하나씩 붙는 절충형이다.

**5. 그 이후 세대: cloud 시대 (2015~)**
- 배경 1: container(앱을 상자처럼 포장해 어디서나 바로 띄우는 기술, 예: Docker)와 이를 자동으로 관리하는 Kubernetes로 server가 수시로 생기고 사라졌다. 사람이 설정을 고쳐서는 따라갈 수 없었다.
- 배경 2: HTTPS에 필요한 인증서(사이트가 진짜임을 증명하는 파일)를 Let's Encrypt가 무료로 주면서, 모든 사이트가 HTTPS로 갔다.
- **Caddy** (2015): HTTPS 인증서를 자동으로 받아 붙여 준다. 설정이 아주 짧다.
- **Traefik** (2016): container가 뜨고 지는 것을 보고 스스로 설정을 바꾼다.
- **Envoy** (2016): 맨 앞문(web server 자리)으로도, 작은 앱 여러 개로 나눈 구조(WAS 역사 6단계)에서 앱끼리 주고받는 요청의 중계로도 쓰인다. Kubernetes에 들어 있는 건 아니지만 그 환경에서 많이 쓰인다.
- **cloud load balancer** (AWS ALB 등): cloud 회사가 대신 운영해 주는 앞문. Nginx를 직접 두지 않고 이것을 맨 앞에 두는 경우도 많다.

**6. edge: CDN이 맨 앞으로**
- CDN은 1999년(Akamai)부터 있었지만, 2010년대부터 Cloudflare 등이 사이트 전체의 맨 앞문을 맡는 경우가 많아졌다.
- CDN은 세계 곳곳에 둔 server 중 사용자와 가장 가까운 곳에서 응답한다. 이렇게 사용자 가까이 있는 server를 **edge**라고 한다.
- 그래도 내 Nginx와 WAS는 그 뒤에 그대로 있다: browser → CDN → Nginx → WAS.
- Cloudflare는 Nginx로 하던 일을 직접 만든 프로그램으로 단계적으로 바꿨다 (2022년 Pingora 발표 등). 주된 이유는 Nginx 구조의 한계였고, 새 프로그램은 메모리 실수(보안 구멍의 흔한 원인)를 막아 주는 언어 Rust로 만들었다.
- edge에서 코드도 실행한다 (2017년 Cloudflare Workers 등). 앞의 Apache module처럼, web server(카운터)와 WAS(주방)의 경계가 다시 흐려지고 있다.
- 주고받는 규칙(HTTP)도 HTTP/2(2015), HTTP/3(2022)로 발전해 더 빨라졌고, web server들이 이를 지원해 가고 있다.

**오늘 질문과 이어 보면**
- web server의 역할은 "파일을 보내는 곳"에서 "WAS 앞에서 요청을 받아 나눠 주는 카운터"로 넓어졌다.
- Nginx와 Node.js는 같은 방식(기다리는 연결에 묶이지 않고 다른 연결을 먼저 처리)을 쓴다. Nginx가 처음 만든 방식은 아니지만, Node.js를 만든 Ryan Dahl은 2009년 첫 발표에서 Apache와 Nginx를 비교하며 이 방식을 설명했다. 다만 Nginx는 worker가 여러 개, Node.js는 기본이 thread 하나다. web server의 역사와 WAS의 역사가 여기서 만난다.

#### web의 발전 단계 (추가 질문)

자료의 6단계에 "그다음"을 붙였다. 질문 세 개는 3·4·5단계에서 답한다.

**큰 흐름 먼저**
정적 문서(1990~) → CGI(1993~) → 서버 내장형 실행(1996~) → WAS·기업용(1999~) → 브라우저 애플리케이션(2005~) → API 클라우드(2006~) → 그다음(edge, AI)

※ 시기는 대략 처음 나온 때. 여기서도 앞 단계는 함께 쓰인다.

**1. 정적 문서 제공**
- 미리 만든 HTML 파일을 그대로 보낸다. 누가 와도 같은 페이지. (web server의 역사 1단계)

**2. CGI 동적 처리**
- 요청이 오면 web server가 바깥 프로그램을 실행하고 그 결과를 돌려준다. 요청마다 다른 페이지가 가능해졌지만, 매번 프로그램을 새로 켜서 느렸다. (WAS의 역사 2단계)

**3. 서버 내장형 실행 환경: 영어 약자는?**
- 답: 딱 하나로 정해진 약자는 없다. "내장형"을 어떻게 읽느냐에 따라 떠올릴 약자가 다르다.
- **HTML 속에 코드를 넣는다**로 읽으면: 이 단계의 대표 약자가 **ASP**(Active Server Pages), **JSP**(Java Server Pages), **PHP**다. 오늘 공부한 JSP가 바로 이 단계다.
- **web server 안(또는 옆)에 실행 환경을 띄워 둔다**로 읽으면: CGI처럼 매번 켜지 않는 방식들의 이름이다.
  - 안에 끼우기: Apache의 **mod_php**(앞의 "카운터 안의 작은 주방"), IIS의 **ISAPI**
  - 옆에 띄워 두기: **FastCGI**(1996). 요즘 PHP(PHP-FPM)도 이렇게 돈다.
  - Java 쪽: **servlet container**(Tomcat). 한국에서는 Tomcat도 WAS라고 부르지만, 이 분류의 4단계 "WAS"는 J2EE 전체를 갖춘 WebLogic·JEUS 같은 큰 server를 말한다 (WAS의 역사 4단계 참고).
- 영어로 이 시대를 넓게 부를 때는 **server-side scripting**이라고 한다 (약자 없음). 다만 2단계 CGI의 Perl script도 여기 들어가서 3단계만 가리키는 말은 아니다.
- ※ JSP·PHP처럼 server에서 HTML을 만드는 것을, SPA가 나온 뒤에는 SSR(Server-Side Rendering)이라고 부르기도 한다 (7단계).

**4. WAS와 엔터프라이즈 플랫폼: 왜 "엔터프라이즈"인가?**
- 엔터프라이즈(enterprise) = **기업**. 이름에 그대로 들어 있다: J2EE = Java 2 Platform, **Enterprise Edition**. Java는 용도별로 판을 나눴다: SE(보통 프로그램), EE(기업 시스템), ME(휴대폰 같은 작은 기기).
- 왜 "기업용"이라는 큰 말을 붙였나: 이 단계의 목표가 홈페이지가 아니라 **회사 업무 전체**(주문, 결제, 재고, 인사)를 web으로 옮기는 것이었기 때문이다. 기업 시스템에는 홈페이지에 없는 요구가 있었다.
  - 돈이 오가는 일은 "전부 성공 아니면 전부 취소"(transaction)가 보장돼야 한다
  - 수많은 직원·고객이 동시에 써도 멈추지 않아야 한다 (server 여러 대로 묶기)
  - 보안, 권한 관리
  - 이미 있던 옛 시스템(은행 등의 대형 컴퓨터, mainframe)과 연결
- 회사들의 뿌리도 기업 쪽이다. WebLogic을 판 BEA와 JEUS를 만든 TmaxSoft는 원래 transaction 처리 소프트웨어(TP monitor: Tuxedo, Tmax)를 팔았다. mainframe의 거래 처리를 더 싼 Unix server로 옮기던 기술이다. 그 경험을 Java·web으로 넓힌 것이 이런 상용 WAS다.
- "플랫폼"인 이유: server 한 개가 아니라 **표준 규격 묶음**이다. 원칙적으로는 같은 앱을 WebLogic에도 JEUS에도 올릴 수 있다. 다만 server마다 따로 쓰는 설정 파일과 고유 기능이 있어서, 실제로 옮길 때는 손볼 곳이 꽤 있었다.

**5. 브라우저 애플리케이션: 이것이 script인가?**
- 반은 맞다. **재료는 script**(여기서는 browser의 JavaScript. 3단계의 PHP도 "script"지만 server에서 돈다), 만든 결과가 **애플리케이션**이다.
  - 1995~: script는 HTML에 조금 덧붙이는 코드였다. 입력값 검사, 간단한 효과 정도.
  - 1990년대 후반~2000년대: Java applet(1995), Flash(1996)처럼 browser에 추가 프로그램(plugin)을 깔아 앱을 돌리는 방식도 있었다 (2002년부터 RIA, Rich Internet Application이라고 불렀다). 지금은 browser에서 아예 돌지 않는다 (Flash는 2020년 지원 종료).
  - 2005~: AJAX (WAS의 역사 5단계). Gmail·Google 지도가 "web page인데 프로그램 같다"는 느낌을 줬다.
  - 2010~: **SPA**(Single Page Application). 페이지를 한 번 받은 뒤, 화면 전체를 browser의 JavaScript가 그리고 관리한다. AngularJS, React, Vue.
- 그래서 같은 JavaScript라도 "script"는 HTML 위의 작은 코드, "브라우저 애플리케이션"은 화면 전체를 책임지는 프로그램이다. 앞에서 본 "React·Vue는 browser에서 돈다"가 이 단계다.

**6. API 클라우드 구조**
- server는 화면(HTML) 대신 **데이터만 내주는 창구(API)**가 된다. 데이터는 보통 JSON(`{"name":"홍길동"}`처럼 값만 담은 글)으로 준다.
- 왜?
  - 5단계처럼 browser가 화면을 직접 그리니, server는 데이터만 주면 된다.
  - 2008년 iPhone App Store 이후 스마트폰 앱이 폭발적으로 늘었다 (휴대폰 앱 자체는 그 전에도 Java ME 등으로 있었다). web과 앱이 같은 데이터를 쓰려면 server가 화면이 아니라 데이터를 줘야 했다.
- 어디서 돌리나: 2006년 AWS 이후 server를 cloud에서 빌려 쓴다. 작은 서비스 여러 개(microservice)로 나눠 container(web server의 역사 5단계)로 띄우거나, server 관리 없이 코드만 올리면 요청이 올 때 cloud가 실행해 주는 방식(serverless)을 쓴다.
- WAS의 역사 6단계(WAS가 앱 안으로, NestJS 앱은 보통 JSON을 줌)가 이 단계다.

**7. 그다음은? (예측이라 정답은 없다. 지금 보이는 흐름 세 가지)**
- **실행 위치가 사용자 가까이로: edge.** 코드 일부가 내 server뿐 아니라 사용자와 가까운 CDN server에서도 돈다. (web server의 역사 6단계)
- **server와 browser가 일을 다시 나눈다.** 화면 만들기가 server(JSP) → browser(SPA)로 갔다가, 다시 server로 일부 돌아오고 있다 (Next.js의 SSR 등). 또 WebAssembly(2017~)로 C·C++·Rust로 짠 프로그램도 **plugin 없이** browser에서 빠르게 돈다. applet과 달리 browser에 들어 있는 기능이다.
- **API를 부르는 쪽에 AI가 더해진다.** 지금까지 API를 부르는 쪽은 주로 사람이 쓰는 browser와 앱이었다. 이제 AI agent가 사람 대신 API를 부르고 일을 처리하기 시작했다. AI를 여러 서비스에 연결하는 표준(예: MCP, 2024)도 나왔다. 얼마나 커질지는 지켜볼 일이다.

**흐름을 꿰는 두 개의 질문**
- **화면을 만드는 코드는 어디서 도는가?** server(CGI, JSP) → browser(SPA) → 일부 다시 server(SSR)와 edge로. 데이터를 처리하는 코드는 내내 server에서 돈다.
- **누가 server에 요청하는가?** 사람이 쓰는 browser → 모바일 앱, 서비스끼리의 요청이 더해짐 → AI agent도 더해지는 중. (검색 로봇처럼 사람 아닌 요청자는 처음부터 있었다.)

## 주제 2: C/S (client/server)와 프로그래밍의 역사

### 질문
- C/S(client/server) 언어 개발의 역사: 프로그래밍의 처음부터 지금, 그리고 미래까지
- web을 공부하며 느낀 점이 "막힌 것에 대한 이해"였다면, C/S에서는 과거부터 미래까지 다시 고민해 보기
- BO가 C/S에서 web으로 넘어간 계기는?

### Claude

※ BO는 백오피스(직원이 쓰는 사내 관리 시스템: 주문, 재고, 정산, 회원 관리 등)로 이해했다.

#### 먼저 두 개의 축
역사를 두 줄로 놓고 보면 흐름이 보인다.
- **축 1. 계산을 어디서 하나**: 중앙(mainframe) → 각자 PC → 나눠서(C/S: 화면과 로직은 PC, 데이터는 DB server) → 다시 중앙(web: 로직은 WAS) → 화면만 다시 client로(SPA, 모바일 앱), 업무 로직과 데이터는 중앙(cloud API)에 그대로 → ? 시계추처럼 오간다.
- **축 2. 사람이 기계에 말하는 수준**: 기계어 → assembly → 고급 언어 → 객체지향 → 그려서 만드는 도구(RAD) → 자연어(AI)? 대체로 사람 말 쪽으로 올라왔다. 다만 화면 만들기는 web 초기에 한 칸 내려갔다가 framework·low-code로 다시 올라왔다 (5·6장). 아래 단계도 계속 쓰인다.

#### 1. 기계에 직접 말하던 시절 (1940~50년대)
- 첫 컴퓨터들은 전선을 꽂거나, 0과 1로 된 명령(기계어)으로 프로그램했다.
- assembly: 0과 1 대신 `ADD`, `MOV` 같은 짧은 단어로 바꿔 쓴 것.
- client/server라는 생각은 아직 없었다. 컴퓨터 한 대가 전부였다.

#### 2. mainframe과 고급 언어 (1950년대 후반~1970년대)
- 1957 **FORTRAN**(IBM): 과학 계산용. 수식을 거의 그대로 쓰는, 널리 쓰인 첫 고급 언어(사람 말에 가까운 언어).
- 1959 **COBOL**: 회사 업무(급여, 회계)용. 영어 문장처럼 쓴다. 지금도 은행 같은 큰 시스템에서 돈다.
- 1964 IBM System/360: 회사마다 중앙 컴퓨터(mainframe)를 두는 시대.
- 처음(1950~60년대)에는 구멍 뚫은 카드 묶음을 맡기고 결과 인쇄물을 기다리는 일괄 처리가 보통이었다.
- 1970년대에는 직원 책상의 단말기(terminal, 예: IBM 3270)가 퍼졌다. 계산은 전부 중앙의 mainframe이 하고, 단말기는 글자 화면을 보여 주고 키보드 입력을 보내기만 했다. 스스로 계산하지 못해서 "dumb terminal"이라고 불렀다.
- 1972 **C** 언어(벨 연구소, Unix와 함께): 기계 가까이에서 빠르게 돌면서도 사람이 읽을 수 있는 언어. 이후 수많은 OS와 DB의 바탕이 됐다.

#### 3. PC와 DB: 계산은 책상 위로, 데이터는 한곳으로 (1970~1980년대)
- 1977 Apple II, 1981 IBM PC: 개인이 컴퓨터를 가졌다.
- 문제: 데이터가 PC마다 흩어졌다. 함께 쓰려면 연결이 필요해서 사내 network(LAN)가 퍼졌다.
- 한편 PC와 별개로, 큰 컴퓨터 쪽에서 관계형 DB가 나왔다. 1970년 E. F. Codd(IBM)가 이론을 내놓았고, 1979년 Oracle(당시 회사 이름은 Relational Software)이 SQL로 다루는 상용 DB를 내놓았다. 데이터를 표로 저장하고, SQL이라는 질의 언어로 꺼낸다.
- LAN으로 PC가 이어지자, 이 DB가 모두가 붙는 **DB server** 자리를 맡았다 (예: Sybase SQL Server, 1987).
- 1984 Macintosh, 1990 Windows 3.0: 마우스로 누르는 그림 화면(GUI)이 퍼졌다.
- 1985 **C++**: 객체지향(프로그램을 "물건(객체)" 단위로 나눠 짜는 방식)을 널리 퍼뜨린 언어. 객체지향 자체는 Simula(1967)에서 시작했다.

#### 4. C/S 전성기 (1980년대 후반~1990년대)
- 앞의 것들이 만났다: **PC의 그림 화면 + 사내 network + DB server** = client/server.
- **client**: 직원 PC에 설치한 Windows 프로그램. 화면과 업무 로직 대부분을 가진다 (fat client).
- **server**: Oracle, Sybase, MS SQL Server 같은 DB server. 일부 로직은 DB 안에 저장해 둔 프로그램(저장 프로시저)으로 둔다.
- client가 server에 SQL을 직접 보낸다. 둘 사이의 공용어가 SQL이었다. 이것이 **2계층(2-tier)** 구조다.
- 언어·도구: 화면을 그림 그리듯 배치하고 버튼에 코드를 붙이는 **RAD 도구**가 주인공이었다 (PowerBuilder, Oracle Forms 같은 일부는 "4GL"이라고도 불렀다).
  - PowerBuilder (1991): 데이터를 표로 다루는 DataWindow가 강력했다. 한국에서도 기업 사내 시스템에 많이 쓰였다고 알려져 있다.
  - Visual Basic (1991), Delphi (1995), Oracle Forms
- 이 시기 백오피스(ERP, 회계, 인사, 병원·관공서 업무)가 대부분 이렇게 만들어졌다.
- **3계층(3-tier)**: client와 DB 사이에 업무 로직을 맡는 중간 server를 두는 방식. 거래 처리 전문 소프트웨어(TP monitor: Tuxedo, Tmax)가 이 자리에 섰다.
  - web 시대에는 이 자리를 주로 WAS가 맡게 됐다 (주제 1, web의 발전 단계 4단계: Tuxedo·Tmax를 팔던 회사들이 WebLogic·JEUS를 팔게 됐다).
  - 은행 같은 큰 시스템에서는 지금도 WAS 뒤에 TP monitor를 함께 둔다.

#### 5. BO가 C/S에서 web으로 넘어간 계기 (2000년 전후~2010년대)
C/S의 아픈 점과, web이 그것을 어떻게 풀었는지:
- **설치·업데이트**: C/S는 PC 수백 대마다 새 버전을 깔아야 했고, 버전이 섞이면 오류가 났다. → web은 server만 고치면 모두에게 바로 반영된다.
- **PC 환경**: C/S는 Windows 버전, 여러 프로그램이 함께 쓰는 부품 파일(DLL)의 충돌("DLL 지옥")에 시달렸다. → web은 browser만 있으면 된다.
- **밖에서 접속**: C/S는 사내망 밖(지점, 집, 협력사)에서 DB에 직접 붙기 어렵고 위험했다. → web은 인터넷으로 어디서나 쓰고, DB는 안쪽에 숨긴다.
- **DB 연결**: 2계층 C/S는 PC마다 DB 연결을 하나씩 잡아서, 사람이 늘면 DB가 버거웠다. 3계층으로 풀 수 있었지만 비싸고 어려웠다. → web은 처음부터 3계층이라 WAS가 연결을 나눠 쓴다 (주제 1의 connection pool).
- **때도 맞았다**: 2000년 전후 인터넷이 퍼지고, J2EE(주제 1)가 표준 도구를 줬다. 예를 들어 Salesforce(1999)는 "설치하는 소프트웨어는 그만(No Software)"을 내걸고, 설치형 C/S 영업관리 프로그램을 web 서비스로 대체했다.
- **언어도 바뀌었다**: 화면 도구 언어(PowerBuilder, VB) + SQL → server는 Java(servlet·JSP)나 C#(.NET, 2002), 화면은 HTML + JavaScript. 주제 1의 세계가 여기서 시작된다.
- **다른 길도 있었다**: C/S 프로그램을 server에서 돌리고 화면만 보내는 terminal server(Citrix 등), 값싼 단말인 "network 컴퓨터"(1990년대 후반). BO에서는 이미 모든 PC에 깔려 있던 browser가 대개 이겼다. browser는 똑똑해진 단말, WAS는 mainframe 자리인 셈이다.

그런데 처음 web BO는 C/S보다 **불편했다.** 엑셀 같은 표(grid), 빠른 키보드 입력, 즉시 반응이 잘 안 됐다.
- 그래서 한국에서는 X-Internet·RIA 도구(TOBESOFT MiPlatform, 2003 등)를 많이 썼다. web으로 배포하지만 화면은 C/S처럼 움직이는 방식이다. 다만 PC에 전용 실행 engine을 ActiveX(IE에 프로그램을 깔게 하는 기술)로 설치해야 해서, IE 의존과 설치 문제가 일부 남았다.
- 이 도구들은 AJAX·SPA와 함께 2010년대까지 쓰였다. 그러다 스마트폰과 Chrome 같은 IE 밖 browser가 퍼지고 ActiveX·plugin이 퇴출되면서, HTML5(plugin 없이 browser만으로 풍부한 화면을 만드는 web 표준) 기반으로 넘어갔다. 같은 회사의 도구도 HTML5판(Nexacro 등)으로 바뀌었다.

정리: BO가 web으로 간 것은 화면이 더 좋아서가 아니라 **배포·관리·접속** 때문이었다. 화면 품질은 나중에 따라잡았다.

#### 6. 지금 (2010년대~)
- 화면은 다시 client 쪽으로 왔다: SPA로 만든 BO 화면, 모바일 앱.
- C/S와 다른 점: SPA·앱은 DB에 SQL을 직접 보내지 않고 API만 부른다. 업무 로직과 DB 연결은 server에 남는다 (주제 1: 데이터를 처리하는 코드는 내내 server).
- 설치·업데이트도 쉬워졌다: SPA는 web처럼 바로 바뀌고, 앱은 스토어가 깔아 준다. 다만 앱은 옛 버전이 한동안 섞여서, 이 점은 C/S를 닮았다.
- PC 프로그램도 돌아왔다: VS Code, Slack은 web 기술로 만든 PC 프로그램이다 (Electron, 2013).
- BO를 만드는 방식: 직접 만들기, SaaS(남이 만든 서비스를 빌려 쓰기, Salesforce 등), low-code 도구(코드를 적게 쓰고 화면을 조립해 만드는 도구, Retool 등). low-code는 1990년대 PowerBuilder·VB의 "그려서 만든다"는 생각이 돌아온 것이다.
- 언어: client는 TypeScript(2012, web), Swift(2014)·Kotlin(모바일). server는 Java·C#에 Go(2009), Node.js(TypeScript), Python이 더해졌다. Rust(2015)는 속도와 안전이 중요한 아래층에 쓰인다. COBOL도 여전히 돈다.

#### 7. 미래 (예측이라 정답은 없다)
- **축 2의 다음 칸, 자연어?** AI가 코드를 써 주면서, 사람은 "무엇을 원하는지"를 말로 설명하는 쪽으로 올라가고 있다. 기계어 → 고급 언어 때처럼 코드를 직접 쓰는 일은 줄어들 수 있다. 다만 compiler는 같은 코드를 늘 같은 결과로 바꾸지만 AI는 그렇지 않아서, 만든 코드를 사람이 읽고 확인하는 일은 남는다.
- **화면 대신 대화?** BO의 많은 일(조회, 보고서, 간단한 수정)을 메뉴를 찾아 누르는 대신 AI에게 말로 시키는 방식이 시도되고 있다. 이때 API를 부르는 쪽(client)은 AI이고, server는 지금처럼 API다. 다만 큰 AI model은 대부분 cloud에서 돌아서, 사용자 화면은 대화창만 남는다. 축 1로는 중앙 쪽이다.
- **반대 방향도 있다**: 계산이 다시 사용자 기기로 오는 흐름(기기 안에서 도는 작은 AI, 인터넷이 끊겨도 되는 앱). server도 사용자 가까이로 흩어진다(edge, 주제 1 web server의 역사 6단계). 시계추가 어느 쪽으로 갈지는 아직 모른다.

#### 과거에서 미래로: 바뀐 것과 남은 것
- **매번 바뀐 것**: 계산을 어디서 하나(축 1), 얼마나 사람 말에 가깝게 쓰나(축 2).
- **C/S 이후 줄곧 남은 것**: 데이터는 server(DB)에 모은다. PC 시대에 흩어졌던 데이터를 DB server로 모은 뒤로는 C/S의 DB server, web의 WAS+DB, cloud API가 모두 같다. 다만 인터넷이 끊겨도 되는 앱처럼 원본을 기기에 두는 설계도 나오고 있어서, 이것도 바뀔 수 있다.
- **사라지지 않고 쌓인 것**: COBOL, Oracle, TP monitor처럼 오래된 것도 아래층에서 계속 돈다.

## 주제 3: 기술 조합으로 보는 BO의 발전 (C/S → web → cloud → 미래)

### 질문
- 주제 2에 이어, C/S에서 web BO로 발전하는 과정을 따로 정리하기
- C/S 프로젝트의 대표 기술부터 web/server까지, 그리고 cloud 이후 미래 기술의 대표 기술 조합은?

### Claude

주제 2가 "왜 바뀌었나"였다면, 여기서는 **그때 프로젝트를 하면 무엇을 조합해 썼나**를 본다. 두 방향으로 정리한다.
- 세대별 조합: 그 시대 BO 프로젝트 하나를 층별로 펼쳐 본다
- 층별 변천: 화면, 업무 로직, 데이터, 배포가 각각 어떻게 바뀌었나

※ "대표 조합"은 흔했던 예다. 실제 프로젝트는 회사마다 달랐고, 한국 기업 기준의 예를 함께 적었다.
※ 세대는 차례로 끝나지 않고 겹친다. 2000년대에도 C/S는 .NET(WinForms)으로 계속 만들어졌고, 지금도 PowerBuilder·MiPlatform으로 만든 BO가 돈다 (주제 1·2: 앞 단계는 함께 쓰인다).
※ 직접 만들기 옆에는 늘 "사서 쓰기"(ERP 패키지)가 있었다. cloud에서는 "빌려 쓰기"(SaaS)가 됐다.

#### 세대별 대표 조합

**1세대. C/S 2계층 (1990년대)**
- 화면: PowerBuilder, Visual Basic, Delphi, Oracle Forms (PC에 설치하는 Windows 프로그램)
- 업무 로직: 화면 프로그램 안 + DB의 저장 프로시저 (주제 2. Oracle에서는 PL/SQL이라는 전용 언어로 짠다)
- DB: Oracle, Sybase, MS SQL Server, Informix
- 연결: client가 DB에 SQL을 직접 보낸다. 통로는 DB 회사가 주는 연결 프로그램(driver)이나 ODBC(여러 DB에 같은 방식으로 붙게 해 주는 Microsoft 표준)
- server OS: Unix(HP-UX·AIX·Solaris: HP·IBM·Sun의 Unix), Windows NT
- 출력(보고서·서식): PowerBuilder의 DataWindow, Crystal Reports
- 배포: 설치 디스켓·CD, 사내 file server
- 한 줄: 화면과 로직이 PC에, 데이터는 DB server에.

**2세대. C/S 3계층 (1990년대 후반)**
- 화면: 1세대와 같은 도구
- 업무 로직: 가운데 server로 옮긴다. TP monitor(Tuxedo, Tmax), 분산 객체(다른 컴퓨터에 있는 프로그램 부품을 내 것처럼 부르는 기술: CORBA, Microsoft DCOM)
- 또는 ERP 패키지를 사서 쓰기: SAP R/3(1992)가 대표적인 3계층 C/S다 (PC의 SAP GUI + 업무 server + DB).
- DB: Oracle 등
- 한 줄: 로직이 PC에서 가운데 server로. web WAS 구조의 바로 앞 단계. 다만 비싸고 어려워서 은행·통신 같은 큰 시스템 위주였고, 많은 BO는 2계층에서 바로 web으로 갔다 (주제 2).

**3세대. 초기 web BO (2000년대 초)**
- 화면: HTML + 약간의 JavaScript, server에서 만든 페이지(JSP, ASP, PHP). 대부분 IE 전용.
- 업무 로직: WAS에서 Java(J2EE) 또는 .NET(C#, 2002)
  - Java 쪽 흔한 조합: Struts(요청을 어느 코드·JSP로 보낼지 정해 주는 틀) + EJB(무거운 업무 로직 부품, 주제 1) + JDBC(Java에서 SQL을 직접 써서 DB에 붙는 표준)
  - EJB는 WebLogic·JEUS 같은 큰 WAS에서만 돌았다. Tomcat에서는 EJB 없이 Struts + JDBC로 짰다 (주제 1).
- web server(Apache, WebtoB) + WAS(Tomcat, WebLogic, WebSphere, JEUS)
- DB: Oracle, MS SQL Server
- 배포: server에 앱 묶음(WAR 파일, EJB를 쓰면 EAR 파일)을 올리면 끝. PC 설치가 없어졌다.
- 한 줄: 설치는 사라졌지만, 화면은 C/S보다 불편했다.

**4세대. 화면을 다시 풍부하게: RIA와 AJAX (2000년대 초중반~2010년대, 3세대와 겹침)**
- 화면은 두 갈래였다.
  - 한국에서 특히 많이: X-Internet/RIA 도구. Gauce(2001), MiPlatform(2003)·XPLATFORM(TOBESOFT). browser에 실행 engine(ActiveX)을 깔아 C/S 같은 grid(엑셀 같은 표) 화면을 낸다. 해외에서는 Flash 기반의 Adobe Flex도 쓰였다.
  - 해외와 많은 한국 기업: server 페이지(JSP, ASP.NET) + jQuery(2006)·AJAX + grid component. plugin 없이 화면 일부를 새로고침 없이 바꾼다.
- 업무 로직: Spring + iBATIS(SQL을 따로 적어 두고 Java에서 불러 쓰는 도구, 2010년에 MyBatis로 이름이 바뀜) + WAS. 공공 쪽은 Spring 기반의 전자정부 표준프레임워크(2009~)가 표준처럼 쓰였다.
- 출력: 한국 web BO는 OZ Report, Crownix(RD), UbiReport 같은 리포트 도구를 함께 썼다.
- DB: Oracle
- 한국 공공 BO의 교과서 같은 조합: RIA + 리포트 도구 + 전자정부 프레임워크 + WebtoB·JEUS + Oracle
- 한 줄: 배포는 web, 화면 느낌은 C/S. RIA는 대신 IE·ActiveX나 Flash 같은 plugin에 묶였다.

**5세대. 현대 web BO (2010년대 중반~)**
- 화면: HTML5 + SPA(React, Vue, Angular) + TypeScript(자료형을 적는 JavaScript) + grid component. 한국 기업은 Nexacro(TOBESOFT), WebSquare(Inswave) 같은 HTML5 UI 도구도 많이 쓴다.
- 업무 로직: Spring Boot(Tomcat 내장) 앱 하나 + MyBatis(SQL을 직접 쓴다) 또는 JPA(SQL 대신 Java 객체로 DB를 다루는 Java 표준). 또는 Node.js(NestJS).
- 화면에는 데이터만 준다 (React·Vue는 보통 JSON, Nexacro는 자체 XML 형식 등).
- web server: Nginx (맨 앞에서 요청을 받는 문, 주제 1)
- DB: Oracle, MySQL, PostgreSQL
- 배포: Jenkins 같은 도구로 build(실행 파일 만들기)·테스트·배포를 자동화한다 (CI/CD: 코드를 올리면 검사부터 server 반영까지 자동으로)
- 한 줄: 화면은 browser가 그리고, server는 데이터만. plugin 없이 C/S만큼 편해졌다.

**6세대. cloud BO (2010년대 후반~지금)**
- 화면: React·Vue·Next.js, 또는 low-code 도구(Retool 등)
- 또는 통째로 빌리기: SaaS(Salesforce 등. 1999년부터 있었고, 이 시기에 BO에 널리 퍼졌다)
- 업무 로직: Spring Boot·NestJS 앱 하나를 container로 띄우는 경우가 많다. 큰 시스템은 작은 서비스 여러 개(microservice)로 나누고, 앞에 API gateway(요청 입구를 하나로 모으는 것)를 둔다.
- 실행 환경: container(Docker) + Kubernetes(container를 자동으로 띄우고 관리), 일부는 serverless(AWS Lambda 등). 주제 1 참고.
- 데이터: cloud가 관리해 주는 DB(AWS RDS 등), cache(자주 쓰는 값을 메모리에 두고 빨리 꺼내는 곳, Redis). 큰 시스템은 메시지 전달(서비스끼리 할 일을 줄 세워 주고받는 통로, Kafka)도 쓴다.
- 배포·운영: CI/CD(GitHub Actions 등), server·network 설정을 코드 파일로 적어 두고 자동으로 만들기(Terraform), monitoring(server 상태 지켜보기)
- 로그인: cloud 로그인 서비스(Okta, Microsoft Entra ID 등). 한 번 로그인으로 여러 시스템을 쓰는 SSO는 2000년대 사내 포털 때부터 썼고, 이제 SaaS까지 넓어졌다. 비밀번호를 넘기지 않고 권한을 빌려주는 표준(OAuth)도 함께 쓴다.
- 한 줄: server를 사지 않고 빌리며, 자주 배포한다.

**7세대. 미래 (예측이라 정답은 없다, 지금 시도되는 조합)**
- 화면: 기존 grid 화면 + 대화창(AI에게 말로 시키기). 필요할 때 AI가 화면을 만들어 보여 주는 방식도 시도된다.
- 업무 로직: AI agent가 기존 API를 "도구"로 불러 일을 처리한다.
  - LLM: 글을 읽고 쓰는 큰 AI model. API로 빌려 쓴다 (Claude 등)
  - MCP: AI가 사내 시스템을 도구로 쓰게 이어 주는 표준 (주제 1)
  - RAG: 사내 문서를 먼저 찾아, 그 내용으로 답하게 하는 방식
- 데이터: 기존 DB + vector search(글을 숫자 묶음으로 바꿔 두고, 글자가 달라도 뜻이 비슷한 문서를 찾는 것. RAG가 문서를 찾을 때 쓴다). 전용 vector DB도 있고, Oracle·PostgreSQL에 붙은 vector 기능도 있다.
- 실행 환경: cloud·serverless 그대로, 일부 계산은 edge와 기기 안으로
- 개발·운영: AI 코딩 도구가 코드를 쓰고 사람이 검토한다. low-code에도 AI가 붙는다. 장애 분석 같은 운영에도 AI를 쓰기 시작했다.
- 꼭 필요해지는 것: AI가 무엇을 했는지 남기는 기록(audit log), 권한 관리, 중요한 일은 사람이 승인하기
- 한 줄: 화면을 누르는 대신 말로 시키고, server의 API는 AI의 도구가 된다.

#### 층별로 보면

- **화면**: 1·2세대 PowerBuilder·VB (PC 설치) → 3세대 JSP·HTML (server가 만든 페이지) → 4세대 MiPlatform (plugin) 또는 JSP + jQuery·AJAX → 5·6세대 React·Nexacro (HTML5) → 7세대 + 대화창·AI가 만드는 화면
- **업무 로직**: 1세대 화면 프로그램 + 저장 프로시저 → 2세대 TP monitor → 3세대 WAS(Struts, EJB) → 4세대 Spring(전자정부 프레임워크) → 5세대 Spring Boot·NestJS 앱 하나 → 6세대 큰 시스템은 microservice로 나눔 → 7세대 + AI agent
- **데이터**: 1~4세대 Oracle(·Sybase 등) → 5세대 + MySQL·PostgreSQL → 6세대 cloud가 관리해 주는 DB + Redis(·Kafka) → 7세대 + vector search
- **배포**: 1·2세대 설치 CD → 3·4세대 WAR를 WAS에 올리기 → 5세대 CI/CD 자동화 → 6세대 container·cloud → 7세대 + AI가 코드·운영을 돕기
- **만드는 방식**: 1·2세대 그려서 만들기(RAD) → 3세대 화면은 HTML 손코딩 → 4·5세대 한국은 RIA·Nexacro 같은 그려서 만드는 도구, 해외는 framework → 6세대 low-code·SaaS → 7세대 AI와 함께 만들기

#### 이어 보면
- 세대가 바뀔 때마다 앞 세대의 아픈 점을 푸는 조합이 나왔다: 설치 문제는 web이, 불편한 web 화면은 RIA와 AJAX가, plugin 의존은 HTML5가, server 관리 부담은 cloud가 풀었다.
- "그려서 만들기"(PowerBuilder)는 한국에서는 RIA·HTML5 도구의 화면 편집기로 먼저 돌아왔고, 최근엔 low-code로 넓어졌다. 이제 "말로 만들기"(AI)를 시도한다 (주제 2의 축 2).
- DB, 특히 Oracle은 1세대부터 지금까지 남아 있다 (주제 2, 바뀐 것과 남은 것).

## 주제 4: 연대별 대표 기술 조합 (1950~2026, 그리고 앞으로)

### 질문
- 연대별 대표 기술 조합을 시대, 대표 아키텍처, client·front-end, server·back-end, database와 통합, 대표 배포 기술, 대표 제품 기술, 실행 환경으로 나눠 1950~2026년과 앞으로의 방향성까지 정리하기

### Claude

주제 2·3을 한 장의 표로 모은 것이다. 시대마다 "그때 시스템 하나를 만들면 각 칸에 무엇이 들어갔나"를 적었다.

※ 표가 넓어서 휴대폰에서는 옆으로 밀어서 본다. 표 속 용어 풀이는 표 바로 아래에 있다.
※ 시대 칸은 대략 널리 퍼진 때이고, 괄호 속 연도는 처음 나온 해라서 시대 칸보다 이를 수 있다. 각 칸은 대표적인 예이고, 앞 시대 기술은 사라지지 않고 함께 쓰인다 (주제 1~3).
※ 1950~70년대(초기 컴퓨터·mainframe)는 client와 server가 아직 나뉘지 않았다. client 칸에는 사람이 쓰던 입출력 장치를, server 칸에는 중앙 컴퓨터에서 프로그램을 짜고 돌리던 언어·소프트웨어를 적었다.
※ "database와 통합" = DB, 그리고 시스템끼리 잇는 방법. "대표 제품 기술" = 그 시대를 상징하는 제품·서비스.

#### 표 속 용어
- 일괄 처리(batch): 일을 모아 한꺼번에 돌리고, 결과는 나중에 받는 방식
- 첫 OS(1956): IBM 704용 batch monitor(GM-NAA I/O). 그 전에는 사람이 기계를 직접 조작했다
- 시분할: 컴퓨터 한 대를 여러 사람이 아주 짧게 번갈아 써서, 각자 혼자 쓰는 듯하게 하는 방식
- JCL: mainframe에 "이 프로그램을 이 파일로 돌려라"를 적는 작업 지시서
- 온라인 처리: 단말에서 넣으면 바로 처리해 답하는 방식 (일괄 처리의 반대). 호스트 = 중앙 mainframe
- TP monitor: 수많은 단말의 거래를 동시에 처리하는 소프트웨어. mainframe의 CICS(1969)가 먼저였고, 뒤에 Tuxedo·Tmax가 Unix로 옮겼다
- 계층형·망형 DB: 관계형(표) 이전의 DB. 데이터를 나무·그물 모양으로 잇는다
- minicomputer: mainframe보다 작고 싼 부서용 컴퓨터 (PDP-11 등)
- GUI: 마우스로 누르는 그림 화면. 처음은 Xerox Alto(1973)였고, Macintosh(1984)가 대중화했다
- ODBC·JDBC: 프로그램이 여러 DB에 같은 방식으로 붙게 해 주는 표준 (ODBC는 Microsoft, JDBC는 Java)
- LAMP: Linux + Apache + MySQL + PHP. 2000년대 web의 대표 조합
- EAI: 사내 여러 시스템을 가운데 중계 server 하나로 잇는 소프트웨어
- SOAP: XML 문서로 다른 시스템의 기능을 부르는 약속 (REST의 앞 세대)
- SOA·ESB: 기능을 "서비스"로 나눠 서로 부르게 하는 설계(SOA)와 그 공용 통로(ESB)
- REST: web 주소(URL)와 HTTP로 데이터(보통 JSON)를 주고받는 API 방식. 2000년에 정의됐다
- VM(virtual machine): server 한 대를 여러 대처럼 나눠 쓰는 기술
- PaaS: 코드만 올리면 server 준비·실행은 cloud가 해 주는 서비스
- NoSQL: 표 대신 문서나 "키-값"으로 저장하는 DB. 관계형 DB를 대신했다기보다 옆에 더해졌다 (Redis는 주제 3의 cache)
- GitOps: Git에 적어 둔 설정대로 server가 자동으로 맞춰지는 배포 방식
- GPU: AI 계산을 빠르게 하는 칩. 비싸서 cloud에서 빌려 쓴다
- MCP, vector search, SSR, serverless, container: 주제 1·3 참고

#### 칸마다 한 줄로 보면
- **대표 아키텍처**: 컴퓨터 한 대 → mainframe 중앙 집중 → PC로 흩어짐 → C/S로 나눔 → 3계층 web → cloud·microservice → AI 연동
- **client·front-end**: 카드·인쇄물 → 글자 단말 → PC GUI → browser(server가 만든 화면) → SPA·모바일 앱 → + AI 대화창
- **server·back-end**: assembly·FORTRAN → COBOL·CICS(mainframe TP monitor) → 저장 프로시저 → Unix TP monitor → WAS(J2EE) → Spring → Spring Boot·Node.js API → + AI agent
- **database와 통합**: 테이프 파일 → 계층형 DB → 관계형 DB(SQL) → message queue → EAI·ESB → + NoSQL·빅데이터 → 관리형 DB·Kafka → + vector search·MCP. 관계형 DB는 1980년대부터 지금까지 중심에 남아 있다.
- **대표 배포 기술**: 카드 묶음 → 운영자 일괄 처리 → 디스켓·CD → WAR 파일 → VM → CI/CD·container → GitOps·AI 보조
- **대표 제품 기술**: IBM 704 → System/360 → PDP·VAX → IBM PC → Windows → WebLogic·JEUS → AWS → ChatGPT·Claude
- **실행 환경**: 진공관 컴퓨터 → 트랜지스터 mainframe → minicomputer·Unix → PC → Unix·Linux server → VM → cloud·container → edge·GPU

#### 앞으로의 방향성 (예측이라 정답은 없다)
- **계산 위치**: 중앙(cloud GPU)과 기기·edge 양쪽이 함께 커지고 있다. 시계추가 어느 쪽에 설지는 아직 모른다 (주제 2의 축 1).
- **화면**: 누르는 화면은 남고, 그 옆에 말로 시키는 창이 붙을 것으로 보인다 (주제 3의 7세대).
- **server**: API가 사람의 화면뿐 아니라 AI agent의 도구로도 쓰이기 시작했다. 그래서 API를 잘 정리해 두는 일이 더 중요해질 것으로 보인다.
- **데이터와 통합**: 표로 된 데이터와 문서(글)를 함께 찾는 일이 늘고 있다. 누가 무엇을 볼 수 있는지(권한), AI가 무엇을 했는지(기록)를 관리하는 일이 핵심 과제로 꼽힌다.
- **배포·개발**: 자동화가 늘고 AI가 코드를 쓰기 시작했다. 사람은 검토하고 승인하는 쪽으로 무게가 옮겨 갈 것으로 보인다.
- **실행 환경**: GPU가 비싼 핵심 자원이 되면서, mainframe 시절처럼 비싼 계산 자원을 나눠 쓰는 모습이 다시 보인다.

#### 이어 보면
- 70여 년 동안 바뀐 것은 대체로 두 가지다: 계산을 어디서 하나, 사람이 얼마나 쉬운 말로 기계에 시키나 (주제 2의 두 축).
- 매 시대 앞 시대의 불편을 푼 기술이 다음 대표가 됐다: 카드 일괄 처리는 온라인 단말이, 중앙 집중은 PC가, 흩어진 데이터는 DB server가, 설치는 web이, server 관리는 cloud가 풀었다.
- COBOL, mainframe, 관계형 DB처럼 오래된 칸의 기술도 아래층에서 계속 돈다.

### 스스로 확인해보기
- 1970년대 글자 화면 단말과 2020년대 browser는 무엇이 닮았고, 무엇이 다를까?
- "database와 통합" 칸에서 SQL이 나온 뒤로 계속 남아 있는 것은 무엇일까?

- 앞으로 칸에서 API를 부르는 쪽은 누구일까?

#### 공통 메시지 다섯 줄
1. **쓰는 사람은 이미 많다. 문제는 깊이다.** 대부분 요약·글쓰기·번역 같은 기초 활용에 머문다.
2. **개인도 회사도 효율이 올랐다고 답하지만, 이익·매출로 이어진 곳은 아직 소수다.** 성과를 낸 소수는 대개 일하는 방식을 다시 짰다. 다만 다시 짰다고 모두 성과를 낸 것은 아니다.
3. **agent는 빨리 오고 있지만, 관리 체계는 뒤처져 있다.**
4. **일자리 변화는 신입과 사무직에서 먼저 보인다.** 대량 대체의 증거는 아직 없고, 새로 생기는 자리도 있다.
5. **기반이 결과를 가른다.** 데이터·플랫폼·교육·governance, 개도국은 전기·인터넷까지. DORA의 말로는 "AI는 amplifier"다.

#### 용어
- ROI: 투자한 돈 대비 벌어들인 돈
- EBIT: 이자·세금을 빼기 전의 영업이익
- 고성과 기업(McKinsey): 이익(EBIT)의 5% 이상이 AI 덕분이고 그 효과가 크다고 답한 곳
- pilot: 작게 시험해 보는 사업
- governance: 누가 무엇을 허락하고 감독하는지 정한 규칙과 체계
- token: AI가 글을 잘게 나누는 단위. AI 사용료를 매기는 기준이 된다
- sovereign AI: 자기 나라의 법·infra·데이터로 AI를 만들고 운영하는 것
- 순효과 포인트(S&P): "AI 때문에 늘었다"는 기업 비율에서 "줄었다"는 기업 비율을 뺀 값. 실제 일자리 수가 아니다
- 노출: 일자리 안에 AI가 닿을 수 있는 업무가 있다는 뜻. 없어진다는 뜻이 아니다

#### 주제별로 엮어 보기

**1. 도입: 넓게 퍼졌지만, 얕고 고르지 않다**
- 개인 (분모가 서로 다르다)

  - DORA 설문의 기술 전문가: 90%가 업무에 AI를 쓴다 (DORA p. 4)
- 기업
  - EU 10인 이상 기업의 20.0%가 AI를 쓴다. 2023년보다 11.9%p 늘었다 (Eurostat p. 15)
  - 싱가포르는 23.5%이고, 10인 이상 기업만 보면 34.6%로 OECD 평균 20.3%보다 높다 (SGDE p. 3, 12)

  - 나이: EU 16~24세 63.8%, 65~74세 6.5% (Eurostat p. 42)

  - 쓰임새가 정보 검색·글쓰기·번역에 머문다 (세계은행 p. 20)

  - 싱가포르 도입 기업의 89.6%는 기성 도구를 그대로 쓴다 (SGDE p. 15)

**2. 효율은 올랐지만, 이익·매출(ROI)은 아직**
- 개인: AI로 생산성이 올랐다는 응답이 McKinsey 80% (p. 11), DORA 80% 이상 (p. 30), AI를 쓰는 싱가포르 근로자의 72.9% (p. 19)다.
- 회사의 효율: Deloitte 응답 기업의 66%가 효율·생산성 향상을 이미 얻고 있다 (p. 10). S&P의 생산성 순효과는 2025년 +40포인트다 (p. 3).
- 회사의 돈: AI가 이익(EBIT)에 조금이라도 기여했다는 응답은 37%로 작년과 같고, 고성과 기업은 응답자의 약 6%로 그대로다 (McKinsey p. 3, 12). AI로 매출을 늘린 곳은 20%이고 74%는 바라는 단계다 (Deloitte p. 10). pilot의 40% 이상을 실제 운영으로 옮긴 기업은 25%다 (Deloitte p. 8). 12개월 안에 ROI를 낼 것으로 보이는 AI 사업은 평균 46%다 (S&P p. 12).
- 무엇이 갈랐나: McKinsey 고성과 기업의 거의 4분의 3은 workflow를 근본부터 다시 설계했다. 다른 응답자는 4분의 1이다 (p. 18). 재설계는 성과와 함께 가지만, 재설계했다고 모두 성과를 낸 것은 아니다. Deloitte에서는 37%가 기존 방식을 거의 그대로 두고 겉핥기로 쓴다 (p. 11).
- 실제로 재 보면: 여러 실험을 모은 결과 통제된 실험에서는 대개 20~60%, 실제 업무 현장에서는 15~30% 빨라졌다 (국제 AI 안전 보고서 p. 87). 반대 사례도 있다. DORA가 소개한 외부 연구(METR)에서는 AI 때문에 19% 느려진 개발자가 오히려 20% 빨라졌다고 믿었다 (DORA p. 35).

**3. 일자리: 대량 대체는 아직, 하지만 신호가 바뀌었다**
- S&P (순효과 포인트)
  - 실제: 이전 보고서의 2024년 값은 0(중립)이었는데, 2025년(11월 조사) 지난 12개월은 -5포인트로 돌아섰다 (p. 2-3). 대기업만 보면 지난 1년 -8포인트다 (p. 6).
  - 전망: 내년 전체 -2포인트, 2026년 대기업 -13포인트, 소기업 +3포인트다 (p. 2, 4).
  - 보고서는 이것을 대규모 대체의 증거로 보지 말라고 한다.
- McKinsey: 작년 32%가 인력 감소를 예상했지만, 실제로 줄었다는 답은 14%였다. 올해는 39%가 내년 감소를 예상한다 (p. 25).
- Deloitte: 82%가 3년 안에 일자리의 10% 이상이 자동화될 것으로 보지만, 84%는 직무를 다시 설계하지 않았다 (p. 12).
- 신입이 먼저
  - AI 영향을 많이 받는 직업에서 2022년 말 이후 경력 초기 청년층 고용이 줄었다는 연구가 여럿 있다 (국제 AI 안전 보고서 p. 85)
  - 중국·인도에서 신입·초급 구인공고가 줄었다 (세계은행 p. 48)
  - Deloitte interview에서 리더들은 데이터 입력·1차 고객지원 같은 신입급 업무가 먼저 자동화돼 경력 사다리가 끊길까 걱정했다 (p. 12)
- 사무직이 먼저
  - 행정·사무 지원, 번역, 고객 서비스 자리가 줄었다 (S&P p. 4)
  - 인도에서는 AI로 대체되기 쉬운 사무직 구인이 줄었다 (세계은행 p. 48)
- 새로 생기는 자리
  - 줄어든 자리 일부는 AI 사업을 관리하는 기술·소프트웨어·디지털 직무가 메웠다 (S&P p. 4)
  - 글쓰기·번역 수요는 줄고, machine learning·chatbot 개발 같은 보완 기술 수요는 늘었다 (국제 AI 안전 보고서 p. 85)
- 노출과 자동화는 다르다
  - 선진국 일자리의 약 60%, 신흥국의 약 40%가 AI에 노출돼 있다 (국제 AI 안전 보고서 p. 85)
  - 저·중소득국에서 생성형 AI로 자동화될 수 있는 일자리는 4.5%로 고소득국(14.2%)보다 훨씬 적고, AI가 도와줄 수 있는 일자리는 16.2%다 (세계은행 p. 48)

**4. agent: 기대는 크고, 관리는 뒤처진다**
- 아래 숫자는 이미 AI를 쓰거나 투자한 조직 안의 비율이다. 기업 전체로 보면 더 낮다.
- agent를 어느 정도 이상 쓰는 곳은 23%이고, 2년 뒤 74%가 될 전망이다. 성숙한 governance를 갖춘 곳은 21%다 (Deloitte p. 17, 20).
- 연매출 10억 달러 이상 대기업의 40%가 agent를 확산 중이다 (작년 27%). 작은 기업은 22%로 그대로다 (McKinsey p. 3).
- AI에 투자한 조직 중 agent를 조직 전체에 완전히 통합한 곳은 18%이고, 12개월 뒤 32%로 예상된다 (S&P p. 11). 완전 자율을 목표로 하는 AI 프로젝트는 22%뿐이다 (S&P p. 2).
- 개발 현장에서는 AI가 스스로 코드를 바꾸는 "agent mode"를 61%가 한 번도 써 보지 않았다 (DORA p. 29). coding agent가 안정적으로 해내는 일은 1년 사이 사람 기준 10분 미만에서 약 30분짜리로 늘었다 (국제 AI 안전 보고서 p. 11).

**5. 소프트웨어 개발: AI는 amplifier (DORA)**
- 설문에 답한 기술 전문가의 90%가 AI를 쓰고, 하루 사용 시간은 중앙값 2시간이다 (p. 4, 25). 70%는 AI 결과물을 어느 정도 믿고, 30%는 조금만 믿거나(23%) 전혀 믿지 않는다(7%) (p. 31).
- AI가 delivery throughput은 높이는 쪽으로 바뀌었지만, delivery instability(실패, 계획에 없던 재작업)는 여전히 늘린다 (p. 4, 42).
- 핵심 메시지: AI는 잘하는 조직의 강점도, 어려운 조직의 문제도 함께 키운다 (p. 3). 내부 플랫폼 품질이 낮으면 AI 효과가 거의 없고, 높으면 강하게 긍정적이다 (p. 71).
- McKinsey에서는 응답자의 32%가 coding agent로 직접 만들 수 있어서 소프트웨어 구매를 하나 이상 포기했다 (p. 9).

**6. 위험과 안전: 실제 증거가 늘었다**
- 가짜 콘텐츠: 한 연구에서 사람들은 AI가 쓴 글을 77%의 경우 사람이 쓴 글로 착각했다 (국제 AI 안전 보고서 p. 46).
- 사이버: 한 해킹 대회에서 AI agent가 실제 소프트웨어 취약점의 77%를 찾아 400여 팀 중 상위 5%에 들었다 (p. 58).
- 생물: 최신 model이 바이러스 실험 절차 문제 해결에서 해당 분야 전문가의 94%보다 나았다 (p. 65).
- 시험의 한계: model이 시험 상황을 알아채거나 평가의 허점을 이용하는 일이 잦아져, 위험한 능력을 출시 전에 놓칠 수 있다 (p. 11).
- 기댈수록 약해지는 실력: AI 도움으로 몇 달 진단한 의사들은 AI 없이 종양을 찾는 능력이 약 6% 떨어졌다 (p. 90).
- 기업의 걱정: 데이터 프라이버시·보안이 1위다 (Deloitte 73%, p. 21). 외부 AI model을 "완전히 신뢰"한다는 답은 2023년 24%에서 2026년 16%로 줄었다 (S&P p. 13). EU에서 AI를 검토하고도 안 쓴 기업은 법적 결과가 불분명해서(53.6%), 데이터 보호가 걱정돼서(52.7%)를 이유로 꼽았다 (Eurostat p. 37).
- 대응: 안전장치를 여러 겹 쌓는 "defense in depth"와, 사고가 나도 버티는 사회의 회복력이 제시된다 (국제 AI 안전 보고서 p. 14).

**7. 시장·infra·주권: 기반은 소수에게 몰린다**
- 학습용 반도체는 NVIDIA가, AI cloud는 AWS·Azure·Google Cloud가 우위를 이어 갈 것으로 봤다 (일본 공정위 본문 p. 8-11). 다만 응용 서비스와 추론 쪽은 경쟁이 활발하다고 봤다 (요약 p. 4).
- 미국 대형 AI 기업들이 2026년 한 해 AI infra에 쓸 것으로 예상되는 돈은 7,500억 달러가 넘어, 많은 개도국의 연간 GDP보다 크다 (세계은행 p. 45).
- 가장 큰 model의 학습 계산량은 2030년까지 125배 늘 수 있다 (국제 AI 안전 보고서 p. 33).
- 기업의 83%가 sovereign AI를 전략에서 어느 정도 이상 중요하게 보고, 77%는 AI 솔루션의 원산지를 따진다 (Deloitte p. 15-16).
- 비용: token 비용 등 운영비 때문에 AI 사용을 줄인 조직이 20%다 (McKinsey p. 15).
- 경쟁 정책: 일본 공정위는 모바일 OS의 전용 소프트웨어 접근 제한, 검색·오피스·OS에 AI를 끼워 파는 행위를 독점금지법의 핵심 쟁점으로 정리했다 (요약 p. 5-6). 특정 기업이 위반했다는 판단은 아니다.

**8. 격차와 준비: 얻을 것이 많은 곳이 가장 덜 준비돼 있다**
- 2026년 6월 기준 80개국 이상이 국가 AI 전략을 냈지만, 저소득국 25곳 중에서는 르완다뿐이다 (세계은행 p. 58).
- 사하라 이남 아프리카 농촌 학교의 32%는 전기를, 68%는 인터넷을 안정적으로 쓰지 못한다. 10세 아동의 89%는 간단한 글을 읽고 이해하지 못한다 (세계은행 p. 45).
- 그래도 현지에 맞춘 "작은 AI"는 효과를 냈다. 가나의 Rori는 기본 휴대폰 문자로 수학을 가르쳐 거의 1년치 학습 효과를 냈고, 비용은 학생당 약 5달러였다 (세계은행 p. 47).
- 역량이 가장 큰 벽이다: EU에서 AI를 검토하고도 안 쓴 기업의 70.3%가 전문성 부족을 꼽았다 (Eurostat p. 37). 인재 준비가 "매우 잘 됐다"는 기업은 20%다 (Deloitte p. 29). 싱가포르 근로자 3분의 2 이상이 AI 교육이 필요하다고 했지만 실제로 받은 사람은 36.7%다 (SGDE p. 21).
- 무엇을 가르칠까: DORA는 "AI를 많이 써라"가 아니라 AI 결과물을 지시하고 평가하고 **검증하는 법**을 가르치라고 한다 (p. 5).

#### 읽을 때 주의할 점
- **전망은 부풀기 쉽다.** McKinsey 응답자는 작년에 32%가 인력 감소를 예상했지만 실제로 줄었다는 답은 14%였다 (p. 3, 25). 74%, 82% 같은 전망도 그렇게 읽는다.
- **누가 만들었는지 본다.** Deloitte와 McKinsey는 AI 컨설팅을, Google Cloud(DORA)는 AI 도구를 판다.
- **같은 "도입률"도 대상이 다르다.** EU와 싱가포르의 10인 이상 기업 비교는 같은 OECD 기준이다. 반면 Deloitte는 이미 AI를 매일 쓰는 "선도 조직"만, S&P의 agent 수치는 AI에 투자한 조직만 조사했다. 개인 사용률도 전 세계 주간 사용자, EU 성인, 싱가포르 근로자, 기술 전문가로 분모가 다르다.
- **고용 숫자도 무엇을 쟀는지 다르다.** S&P의 -5포인트는 기업들이 스스로 답한 인원 증감(늘린 곳 비율에서 줄인 곳 비율을 뺀 값)이다. 국제 AI 안전 보고서가 인용한 미국·덴마크 연구는 나라 전체 고용 자료로 AI 노출과 고용을 비교했고, 관계를 찾지 못했다 (p. 85). 그래서 둘은 모순이 아니다.
- **시점이 다르다.** Deloitte는 2025년 8~9월 설문, McKinsey는 2026년 5~6월 설문, 국제 AI 안전 보고서는 2025년 12월 이전에 발표된 연구를 모은 것이다.
- **국제 AI 안전 보고서는 정책을 권고하지 않는다**고 스스로 밝힌다 (p. 10). 아는 것과 모르는 것을 정리한 보고서다.

#### 앞 주제와 이어 보면
- 주제 4 표의 "2020~2026" 줄에 적은 "AI agent(시도 중)"가 숫자로 확인된다. AI를 이미 쓰는 조직 안에서도 agent를 어느 정도 이상 쓰는 곳은 23%(Deloitte), 조직 전체에 통합한 곳은 18%(S&P)다.
- 주제 3의 "사서 쓰기 대 직접 만들기": AI는 대개 사서 쓴다 (AI를 쓰는 EU 기업의 57.9%가 상용 AI 소프트웨어를 구매, 2024년, Eurostat p. 33). 한편 McKinsey 응답자의 32%는 coding agent로 만들 수 있어서 소프트웨어 구매를 하나 이상 접었다. "직접 만들기"가 다시 힘을 얻는 신호다.
- 주제 2의 축 1(계산을 어디서 하나)에 "누구의 땅에서 하나"가 더해졌다. 계산 자원은 소수 기업에 몰리고, 기업은 sovereign AI를 따진다.

**① 국제 AI 안전 보고서 2026** (2026.2, 의장 Yoshua Bengio)
- 무엇: 30여 개국·국제기구가 추천한 전문가 자문단과 100명 넘는 전문가가 2025년 12월 이전에 발표된 연구를 모아 정리한 두 번째 판. 범용 AI의 최첨단 위험에 집중했다.
- 한 줄: AI 능력은 많은 전문가의 예상보다 빨리 좋아지고 위험의 실제 증거도 늘었지만, 위험관리 기법은 아직 충분하지 않다.
- 핵심: coding agent 10분→30분 작업 (p. 11), 매주 7억 명 이상 사용 (p. 11), 2030년 전망은 정체부터 가속까지 모두 가능할 만큼 불확실 (p. 33), deepfake·사이버·생물 위험의 증거 (p. 46, 58, 65), 시험을 알아채는 model (p. 11), 12개 기업의 안전 framework (p. 14).
- 한계: 정책 권고를 하지 않는다. 편향·환경·개인정보·저작권은 이번 판에서 빠졌다 (p. 10).

**② 세계은행 세계개발보고서 2026: AI의 약속**
- 무엇: 저·중소득국 68억 명에게 AI가 무슨 의미인지 다룬 첫 종합 평가. 7개국 기업 설문, 60개국 정부 설문 등을 썼다.
- 한 줄: AI는 개도국에 큰 기회지만, 최첨단 model 경쟁보다 이미 있는 AI를 도입해 현지에 맞게 고쳐 쓰고(Adopt·Adapt), 전기·인터넷·기초교육에 투자하는 것이 핵심이다.
- 핵심: 증기기관이 저소득국에 닿기까지 80년, 전기 40년, 인터넷 20년 걸린 것보다 빠른 확산 (p. 35), 소득별 사용 격차 (p. 42), 개도국 자동화 가능 일자리 4.5% (p. 48), 미국 대형 AI 기업의 2026년 infra 투자 예상액 7,500억 달러 이상 (p. 45), 국가 AI 전략의 격차 (p. 58), 현지형 "작은 AI"의 효과 (p. 47).
- 권고: 아날로그 토대 투자, 싼 컴퓨팅과 현지 언어 데이터, 사람보다 자동화가 유리해지는 세금 피하기.
- 한계: AI가 성장과 좋은 일자리를 늘린다는 확정적 증거는 아직 찾기 어렵다고 스스로 밝힌다 (p. 39).

**③ Deloitte State of AI in the Enterprise** (2026.1)
- 무엇: 24개국 리더 3,235명 설문 (2025년 8~9월), 이미 AI를 매일 쓰는 조직 대상. 15명 interview를 더했다.
- 한 줄: 도구 보급과 생산성은 늘었지만 대부분 효율화 단계이고, 일의 재설계·governance·인재가 뒤처져 있다.
- 핵심: 허가된 AI 도구를 쓸 수 있는 직원 비율 40% 미만→약 60% (p. 4, 8), "근본적으로 바뀌는 중" 12%→25% (p. 10), agent 23%→2년 뒤 74%, governance 21% (p. 17, 20), sovereign AI 83% (p. 15), physical AI 58%→80% (p. 22).
- 권고: 도구 보급에서 활용으로, 규모를 키우기 전에 governance부터, agent는 위험이 낮은 업무부터.

**④ McKinsey The state of AI in 2026: ROI로 가는 길** (2026.8)
- 무엇: 97개국 1,719명 설문 (2026년 5~6월).
- 한 줄: agent와 coding agent는 퍼지고 있지만, 회사 이익 효과는 37%로 제자리다. 이익의 5% 이상을 AI 덕으로 보는 고성과 기업(응답자의 약 6%)이 길을 보여 주고, 이들의 거의 4분의 3은 업무를 다시 짰다.
- 핵심: 확산 단계 38%→44% (p. 5), 대기업 agent 확산 27%→40% (p. 3), coding agent로 구매 포기 32% (p. 9), token 비용으로 사용 축소 20% (p. 15), 인력 감소 예상 32% 대 실제 14% (p. 25).
- 권고: 효율만이 아니라 성장도 목표로, workflow 재설계, 운영비를 처음부터 설계 조건으로.

**⑤ S&P Global AI와 노동 2026** (2026.6)
- 무엇: 구매관리자지수(PMI) 특별 설문, 451 Research 기업 설문, S&P Global 1200 기업 인원 데이터.
- 한 줄: 투자와 생산성 효과는 커지는데, 고용 효과는 "약간 부정"으로 돌아섰다. 당분간은 대체보다 재배치가 주된 흐름이다.
- 핵심: 도입 목적은 효율 64%·생산성 59% 대 인력 감축 24% (p. 2), 고용 순효과 지난 1년 -5포인트·내년 전망 -2포인트 (p. 2), 2026년 전망 대기업 -13 대 소기업 +3 (p. 4), 38개 활용 사례 평균 도입률 50% (p. 8), 외부 model "완전 신뢰" 24%→16% (p. 13).
- 한계: 대기업 인원 감소를 AI 탓만으로 볼 수 없다고 스스로 밝힌다 (p. 6).

**⑥ 유럽연합 통계청 EU의 AI 기술 이용 2026**
- 무엇: EU 회원국 통계청이 같은 설문지로 조사한 기업 약 15.7만 곳(2025년)과 개인 약 33만 명.
- 한 줄: EU 기업의 20.0%가 AI를 쓰며 빠르게 늘지만, 규모·업종·나라별 격차가 크고 가장 큰 벽은 전문성 부족이다.
- 핵심: 기업 도입률 20.0% (p. 15), 대기업 55.0%·소기업 17.0% (p. 16), 정보통신업 62.5%·건설업 10.8% (p. 18), AI를 쓰는 기업의 가장 많은 용도는 마케팅·영업 34.7% (p. 27), 개인 생성형 AI 32.7% (p. 40).
- 한계: 10인 이상 기업과 정해진 업종만 다룬다.

**⑦ 싱가포르 디지털 경제 보고서 2026** (IMDA)
- 무엇: 싱가포르 디지털 경제의 규모, 기업 디지털화, 기업·근로자의 AI 사용, 기술 인력을 다룬 네 번째 판.
- 한 줄: 기업 AI 도입률이 1년 만에 14.7%에서 23.5%로 뛰었고 근로자 85.7%가 AI를 쓰지만, 대부분 기초 수준이라 교육이 다음 과제다.
- 핵심: 10인 이상 기업 34.6%로 OECD 상위권 (p. 12-13), 안 쓰는 이유 1위 "규모가 작아 필요 없다" 54.7% (p. 14), AI 사용 근로자 중 매일 쓰는 비율 35.6% (p. 17), 시간 절약을 답한 AI 사용 근로자 중 하루 1시간 이상 절약 27.4% (p. 19), AI 기술을 1개 이상 요구하는 기술직 구인공고 14.0%→16.7% (p. 24).

**⑧ 일본 공정거래위원회 생성형 AI 보고서 ver.2.0** (2026.4)
- 무엇: 경쟁 정책 관점의 시장 조사. infra·model·application 3개 층으로 정리하고, 자율주행을 새로 넣었다.
- 한 줄: 층마다 경쟁은 활발하지만 반도체와 cloud는 강자 우위가 이어진다. 모바일 OS 접근 제한과 기존 서비스에 AI를 끼워 넣는 행위가 핵심 쟁점이다.
- 핵심: 일본 생성형 AI 시장 2025년 약 6,653억 엔에서 2029년 약 1조 9,791억 엔 전망 (민간 추정 인용, 본문 p. 39), 학습 데이터 고갈 우려 (본문 p. 11), 범용 model 성능 차 축소 (본문 p. 15), 일본어 능력 격차 축소와 일본 기업의 분야 특화 (요약 p. 4), 업무에 생성형 AI를 쓰는 일본 응답자 55.2%로 미·독·중보다 낮음 (총무성 백서 인용, 본문 p. 18).
- 다음 행동: 자기우대, AI를 통한 가격 동조, 제휴를 통한 인재 확보를 계속 지켜본다 (요약 p. 6).
- 한계: 영문 본문은 임시 번역이다. 쟁점은 가상 사례이고, 특정 기업의 위반 판단이 아니다.

**⑨ DORA AI 지원 소프트웨어 개발 현황 2025** (Google Cloud)
- 무엇: 100여 개국 기술 전문가 4,867명 설문과 78명 심층 interview.
- 한 줄: AI는 개발 조직의 강점과 약점을 함께 키우는 amplifier라서, 도구보다 플랫폼·데이터·workflow에 투자해야 성과가 난다.
- 핵심: 사용 90%·하루 2시간 (p. 4, 25), 신뢰 70% (p. 31), throughput 상승과 instability 증가 (p. 42), AI 효과를 키우는 7가지 역량 (p. 50), 내부 플랫폼 90% 도입 (p. 66).
- 한계: 관찰 데이터라서 인과 효과가 아니라 비교로 읽어야 한다고 스스로 밝힌다 (p. 123).
