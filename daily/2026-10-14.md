### Claude

#### 한 줄 요약
JSP는 **서버**에서 실행되어 HTML을 만들고, JavaScript는 그 HTML을 받은 **브라우저**에서 실행된다. WAS는 JSP 같은 서버 프로그램을 실행해 주는 서버다.

#### 요청 하나가 처리되는 순서
1. 사용자가 브라우저에서 `list.jsp` 주소를 연다.
2. WAS가 요청을 받아 JSP를 실행한다. 이때 Java 코드가 돌고, 필요하면 DB도 조회한다.
3. 실행 결과로 **HTML 문서(텍스트)** 가 만들어져 브라우저로 간다. JSP 코드 자체는 브라우저로 가지 않는다.
4. 브라우저가 HTML을 위에서부터 읽으며 화면을 그리다가, `<script>`를 만나면 그 JavaScript를 실행한다.
5. 그 뒤 버튼 클릭 같은 사용자 동작은 브라우저 안의 JavaScript가 처리한다. 서버의 데이터가 다시 필요하면 새로 요청을 보낸다.
   - 페이지 이동: JSP가 다시 실행되어 새 HTML 전체가 온다.
   - `fetch`/AJAX: 보통 데이터(JSON)만 받아서, JavaScript가 새로고침 없이 화면 일부만 바꾼다.

#### JSP
- Java Server Pages. HTML 사이에 Java 코드를 섞어 쓰는 **서버 쪽** 기술이다.
- 처음 요청이 오면 WAS가 JSP를 **순수 Java 프로그램(서블릿)으로 바꾸고 컴파일**한다. 이후엔 그것을 바로 실행하고, JSP를 고치면 (개발 설정에서는 보통) 이 과정을 다시 한다.
- 결과물은 HTML 텍스트일 뿐이다. 브라우저에서 "페이지 소스 보기"를 하면 JSP 코드는 없고 HTML만 보인다.

#### JavaScript
- 주로 브라우저 안에서 실행되는 언어다. (서버에서도 돌릴 수 있다 → 아래 Node.js)
- 서버가 HTML을 보낸 **뒤에** 브라우저에서 실행된다. 화면 요소(DOM)를 바꾸고, 클릭·입력에 반응하고, 서버에 추가 요청을 보낸다.
- 이름이 비슷하지만 Java와는 전혀 다른 언어다.

#### 가장 헷갈리는 지점: 실행 순서
```jsp
<% String name = "홍길동"; %>
<script>
  var name = "<%= name %>";
  alert(name);
</script>
```
- `<% %>` 안은 서버에서 도는 Java 코드, `<%= %>`는 그 값을 그 자리에 찍는 표시다.
- 서버에서 JSP가 먼저 실행되어 `<%= name %>` 자리에 `홍길동`이 들어간다.
- 브라우저가 받는 것은 `var name = "홍길동";` 이라는 JavaScript 코드일 뿐이다.
- 그래서 JSP는 JavaScript **코드를 만들어낼** 수는 있지만, 반대로 JavaScript가 JSP 변수를 직접 바꿀 수는 없다. 서버에서 실행이 이미 끝났고, 그 변수도 응답을 보낼 때 사라졌기 때문이다.
- 반대 방향(브라우저 → 서버)은 **새 요청**에 값을 실어 보낸다. 예: `list.jsp?name=김철수`, 폼 전송, `fetch`. 그러면 JSP가 처음부터 다시 실행되고 `request.getParameter("name")`으로 그 값을 읽는다.
- 참고: 사용자 입력을 이렇게 그대로 넣으면 따옴표 때문에 코드가 깨지거나, 남이 넣은 스크립트가 실행될 수 있다(XSS). 그래서 특수문자를 안전한 글자로 바꿔 넣는다(이스케이프). 바꾸는 방법은 넣는 위치에 따라 다르다 (HTML 안인지, 여기처럼 JavaScript 문자열 안인지).

#### WAS (Web Application Server)
- 요청이 올 때마다 **프로그램을 실행해서** 응답을 만들어 주는 서버다. 예: Tomcat(가장 많이 씀), JEUS, WebLogic, JBoss(WildFly)
- **웹 서버**(Apache, Nginx)와 비교하면:
  - 웹 서버: 이미 만들어진 파일(HTML, 이미지, CSS, JS)을 그대로 돌려준다 → 정적
  - WAS: JSP·서블릿을 실행해서 상황마다 다른 결과를 만든다 → 동적
- WAS가 하는 일:
  - JSP·서블릿을 실행하고 관리한다 (이 역할을 "서블릿 컨테이너"라고 부른다)
  - 요청마다 일꾼(스레드)을 하나씩 붙여, 여러 사람의 요청을 동시에 처리한다
  - 요청 사이에 "누가 로그인했는지" 같은 사용자별 정보를 기억한다 (세션)
  - DB 연결을 미리 만들어 두고 나눠 쓰게 해 준다 (커넥션 풀)
- 실무에서는 앞에 웹 서버를 두고, 정적 파일은 웹 서버가, 동적 요청은 WAS가 처리하도록 나누는 경우가 많다.

#### 다시 정리: 네 가지의 관계 (추가 질문)

**먼저 둘로 나누기**
- **코드**: JSP, JavaScript → 누군가 실행해 줘야 하는 프로그램
- **서버**: 웹 서버, WAS → 요청을 기다렸다가 응답하는 프로그램 (서버 컴퓨터에서 돈다)

**짝으로 기억하기**
- JSP는 **WAS**가 실행한다. WAS 없이는 JSP가 돌지 않는다.
- JavaScript는 **브라우저**가 실행한다. 웹 서버·WAS는 JS 파일을 실행하지 않고 보내기만 한다.
- **웹 서버**는 이 구조에서 코드를 실행하지 않는다. 이미 있는 파일은 바로 보내고, JSP 요청은 WAS로 넘긴다.

**그림**
```
브라우저 (JavaScript 실행)
   ↕
웹 서버 (파일 전달, JSP는 WAS로)
   ↕
WAS (JSP 실행 → HTML)
   ↕
DB
```
※ 웹 서버는 빼도 된다. Tomcat 같은 WAS가 파일 전달도 할 수 있어서, 연습할 땐 WAS 하나면 충분하다.

**요청 따라가 보기**
- `list.jsp`: 웹 서버가 WAS로 넘김 → JSP 실행(DB 조회) → HTML이 브라우저로
- 그 HTML 속 `app.js`, `logo.png`: 브라우저가 다시 요청 → 웹 서버가 파일 그대로 보냄 (WAS는 쉼) → `app.js`는 브라우저에서 실행

**식당으로 비유하면**
- 웹 서버 = 카운터: 미리 만들어 둔 것은 바로 건네고, 요리 주문은 주방으로 넘긴다
- WAS = 주방
- JSP = 주방의 레시피: 손님은 레시피를 볼 수 없고, 완성된 요리(HTML)만 받는다
- JavaScript = 손님에게 주는 "자리에서 이렇게 하세요" 안내 카드: 따라 하는 건 손님 자리(브라우저)다. 레시피와 달리 손님도 볼 수 있다. 요리에 끼워 오기도 하고(HTML 속 `<script>`), 카운터에서 따로 받기도 한다(`app.js`). 더 필요하면 다시 주문(새 요청)한다

**웹 서버와 WAS를 왜 나누나**
- 이미 있는 파일은 웹 서버가 빨리 보내고, WAS는 JSP 실행에만 집중한다.
- WAS가 인터넷에 직접 노출되지 않아 더 안전하다.
- WAS를 여러 대 두면 웹 서버가 요청을 골고루 나눠 준다 (로드 밸런싱).

#### Node.js (추가 질문: 원래 궁금했던 것)

**한 줄 요약**
Node.js는 언어가 아니라, JavaScript를 **브라우저 밖에서** 실행해 주는 프로그램이다. 덕분에 JavaScript로 **서버**도 만들 수 있다.

**앞의 짝에 넣어 보면**
- JSP(Java) → **WAS**가 실행
- JavaScript → **브라우저**가 실행
- JavaScript → **Node.js**가 실행 ← 새 짝

단, Node.js는 켜기만 해서는 서버가 아니다. 내 서버 코드를 실행해야 서버가 된다. (아래 "Node.js와 NestJS" 참고)

**같은 JavaScript, 할 수 있는 일은 다르다**
Chrome 안에서 JavaScript를 실행하던 부분(V8 엔진)을 떼어 내고, 파일·네트워크 기능을 붙여 브라우저 없이 돌게 만든 것이 Node.js다. 그래서 누가 실행하느냐에 따라 쓸 수 있는 기능이 다르다.
- 브라우저의 JavaScript: 화면을 바꿀 수 있다 (`document.getElementById` 같은 `document` 기능). 서버의 파일이나 DB에는 직접 손대지 못한다.
- Node.js의 JavaScript: 파일 읽기·쓰기, DB 연결, 요청 받기가 된다. 대신 화면이 없어서 `document`는 쓸 수 없다.

**Node.js가 쓰이는 두 가지**
1. **서버 만들기**: JSP + Tomcat 자리를 JavaScript + Node.js가 대신한다. Tomcat은 켜기만 하면 요청을 기다리는 서버라 JSP만 넣으면 되지만, Node.js는 내 서버 코드를 실행해야 서버가 된다. 그 코드가 요청을 받아 HTML이나 데이터(JSON)를 돌려준다 (보통 Express·NestJS 같은 틀로 짠다). 그래서 Tomcat 같은 WAS를 따로 설치하지 않는다.
2. **개발 도구 돌리기**: 서버를 만들지 않아도 Node.js를 설치하는 경우가 많다. `npm`(남이 만든 코드를 내려받는 도구)과, React·Vue로 짠 화면 코드를 브라우저용 JS 파일로 묶어 주는 도구(Vite 등)가 Node.js로 돌기 때문이다. React·Vue 자체는 브라우저에서 돈다.

**그림 (Node.js로 서버를 만든 경우)**
```
브라우저 (화면용 JS 실행)
   ↕
웹 서버 (Nginx, 없어도 됨)
   ↕
Node.js + 내 서버 코드
(서버용 JS 실행 → HTML/JSON)
   ↕
DB
```
※ Node.js 서버도 브라우저용 JS 파일(앞의 `app.js`)은 실행하지 않고 그대로 보낸다. Node.js가 실행하는 것은 서버용 JS 파일뿐이다.

**헷갈리지 않기: 둘 다 JavaScript여도 따로 돈다**
서버용 JavaScript(Node.js)와 화면용 JavaScript(브라우저)는 같은 언어지만 따로 도는 별개의 프로그램이다. 내 컴퓨터 한 대에서 둘 다 띄워 연습해도 마찬가지다. JSP 때와 똑같이, 브라우저 JavaScript가 서버의 변수를 직접 바꿀 수 없고 **요청**으로 주고받는다.

**왜 Node.js를 쓰나**
- 화면과 서버를 한 언어(JavaScript)로 만들 수 있다.
- WAS는 요청마다 일꾼(스레드)을 붙이지만, Node.js는 일꾼 하나가 DB 응답을 기다리는 동안 다른 요청을 먼저 처리한다. 그래서 기다림이 많은 요청(DB 조회, 채팅 등)을 많이 받는 데 강하다.

#### Node.js와 NestJS (추가 질문)

**정리하면**
- **NestJS는 Node.js 안에 없다.** `npm`으로 따로 설치하는 틀이다. Node.js 안에 처음부터 있는 것은 요청을 받는 기본 부품(`http`)뿐이다.
- **Node.js는 켜기만 해서는 서버가 아니다.** JS를 실행하는 실행기라서, 내 코드가 "요청을 기다려라"(`listen`)라고 해야 서버가 된다.
- Tomcat은 다르다. 켜기만 해도 내 코드 없이 8080번 포트에서 요청을 기다린다.
- 그래서 Node.js가 내 코드(NestJS 등)를 실행하고 있을 때, 그 실행 중인 프로그램이 서버다.

**Node.js 안에 있는 것: 기본 부품**
```js
const http = require('http');
http.createServer((req, res) => {
  res.end('hello');
}).listen(3000);
```
`require`로 부품을 불러오고, 요청(req)이 오면 응답(res)으로 hello를 보낸다. 이 코드를 `server.js`로 저장해 `node server.js`로 실행하면, 3000번 포트(서버의 문 번호)에서 요청을 기다리는 서버가 된다. 마지막 `listen(3000)`이 없으면 아무 요청도 기다리지 않는다.

**NestJS, Express: 따로 설치하는 틀**
- 기본 부품만으로 서버를 짜기엔 번거로워서 만든 **틀(프레임워크)** 이다. 둘 다 `npm`으로 설치한다.
- Express는 주소별로 할 일 나누기를 쉽게 해 주는 단순한 틀이다.
- NestJS는 그 위에 입력값 검사, DB 연결 같은 것을 정해진 구조로 붙이게 해 주는 큰 틀이다.

**층으로 보면** (1~4는 위가 바로 아래를 쓰고, 5가 전부를 실행한다)
1. 내 코드: NestJS 규칙대로 작성
2. NestJS: 큰 틀 (npm 설치)
3. Express: 단순한 틀. NestJS가 기본으로 안에서 쓴다 (npm 설치)
4. `http` 부품: Node.js에 처음부터 들어 있음
5. Node.js: 1~4를 모두 실행하는 실행기

**NestJS 앱의 자리**
NestJS로 만든 앱은 처음 그림의 **WAS 자리**에 들어간다 (Node.js 그림의 "Node.js + 내 서버 코드" 칸). Tomcat 같은 WAS를 따로 설치하지 않을 뿐, 하는 일은 WAS와 같다. 세션, DB 연결 관리처럼 WAS가 해 주던 일은 NestJS나 다른 npm 패키지로 붙인다.

일상에서는 이것도 "웹 서버"라고 부르지만, 이 노트에서 웹 서버는 파일 전달과 요청 중계(HTTPS, 로드 밸런싱)를 맡는 Nginx 같은 것을 뜻한다.

**Java 쪽과 나란히**
- 요청 받기: Tomcat ↔ Node.js의 `http` 부품
- 서버 코드 틀: Spring ↔ Express, NestJS

NestJS는 구조가 Spring과 많이 닮았다. 요즘 Spring Boot는 Tomcat을 앱 안에 넣어 함께 실행해서, Node.js + NestJS와 모양이 비슷하다.

#### WAS가 필요한 세상일까? (추가 질문)

**반은 맞다.**
- 요즘 서비스는 로그인, 검색, 결제처럼 요청마다 결과가 달라진다. 그래서 **WAS 역할**(코드를 실행해 결과를 만드는 일)이 없는 서비스는 거의 없다.
- 그런데 **웹 서버도 사라지지 않았다.** Nginx 같은 웹 서버는 지금도 많은 서비스의 맨 앞에서 암호화(HTTPS), 파일 전달, 요청 나눠 주기(로드 밸런싱)를 맡는다. 이미지·JS 파일은 CDN(세계 곳곳에 복사본을 두고 가까운 곳에서 보내 주는 서비스)이 맡기도 한다.
- 바뀐 것은 **WAS의 모양**이다. 예전엔 Tomcat·JEUS 같은 WAS를 따로 설치하고 그 안에 내 코드를 넣었다. 지금은 Spring Boot나 Node.js처럼 **WAS 역할이 내 앱 안에 들어가** 앱 하나로 실행하는 경우가 많다.
- 화면을 만드는 곳도 옮겨 갔다. 예전엔 서버(JSP)가 HTML을 다 만들었지만, 요즘은 서버는 데이터(JSON)만 주고 브라우저의 JavaScript(React 등)가 화면을 그리는 경우가 많다. 다만 Next.js처럼 Node.js 서버가 다시 HTML을 만들어 보내는 방식(SSR)도 많이 쓴다.

정리: "WAS만 필요한 세상"이라기보다, **WAS 역할은 어디에나 있고(이제는 앱 안에), 웹 서버는 맨 앞 카운터로 남은 세상**이다.

#### WAS의 역사 (추가 질문)

**큰 흐름 먼저**
파일 전달(웹 서버) → 요청마다 프로그램 실행(CGI) → 프로그램을 띄워 두기(서블릿·JSP) → 크고 표준화된 WAS(J2EE) → 가볍게(Spring) → WAS가 앱 안으로(Node.js, Spring Boot)

※ 앞 단계가 사라진 게 아니라 위에 쌓였다. 웹 서버도, Tomcat·JEUS 같은 전통 WAS도 지금 함께 쓰인다.

**1. 파일만 보내던 시절 (1990~)**
- 첫 웹 서버(CERN httpd)는 미리 만든 HTML 파일을 보내 주기만 했다. 누가 와도 같은 페이지였다.

**2. CGI: 요청마다 프로그램 실행 (1993~)**
- 웹 서버가 요청을 바깥 프로그램(C, Perl 등)에 넘겨 실행시키고, 그 출력(HTML)을 받아 돌려준다. 이 방식을 공통 규칙(CGI)으로 정해서, 어느 웹 서버에서나 요청마다 다른 결과를 만들 수 있게 됐다.
- 문제: 요청이 올 때마다 프로그램을 새로 켰다 껐다 해서 느리고 무거웠다.

**3. 프로그램을 띄워 두기 (1995~1999)**
- 배경: 1995년에 Apache 웹 서버, PHP(처음엔 CGI 방식), Java, JavaScript(브라우저용)가 나왔다.
- 1996: 마이크로소프트 ASP. HTML 속에 코드를 넣는 방식이다.
- 1997: Java **서블릿**. 프로그램을 한 번 띄워 두고 요청마다 일꾼(스레드)만 붙이는, CGI의 느림에 대한 Java 쪽 해결책이다. (비슷한 때 FastCGI 같은 다른 해결책도 나왔다.)
- 1999: **JSP** 1.0. 서블릿에서 HTML을 한 줄씩 찍어 내던 불편을 줄이고 ASP에 맞서려고, HTML 속에 Java를 넣는 방식이 나왔다. 같은 해 Sun이 서블릿·JSP 실행 코드를 공개해 **Tomcat**이 나왔다.

**4. 애플리케이션 서버 전성기 (1999~2000년대)**
- 1999: **J2EE**. Java로 기업용 시스템을 만드는 표준 묶음(서블릿, JSP, EJB, DB 연결 등)이다. 이 중 EJB(업무 로직을 서버가 관리해 주는 부품)가 크고 무거운 부분이었다.
- 이 표준을 모두 갖춘 큰 서버가 **애플리케이션 서버**다. 상용으로 WebLogic(BEA, 지금은 Oracle), WebSphere(IBM), 국산 JEUS(티맥스소프트), 무료 오픈소스로 JBoss(지금 WildFly)가 있다.
- Tomcat은 이 중 서블릿·JSP 부분만 갖춘 가벼운 서버(앞에서 말한 서블릿 컨테이너)다. 한국에서는 Tomcat도 WAS라고 부르지만, 영어권에서는 servlet container와 application server를 나눠 부르는 일이 많다. (영어로 "WAS"라고 하면 보통 IBM WebSphere Application Server를 뜻한다.)
- 한국에서는 은행·공공기관을 중심으로 "웹 서버 + WAS" 구성(예: WebtoB + JEUS, Apache + Tomcat)이 널리 쓰였고, "WAS"라는 말도 특히 많이 쓴다.

**5. 가벼워지는 시대 (2004~)**
- 2004: **Spring** 1.0. 무거운 부품(EJB) 없이도 기업용 기능을 쓰게 해 줘서 Tomcat만으로 충분해졌다. "Tomcat + Spring"이 널리 쓰이기 시작했다.
- 2004: **Nginx**. 동시 접속이 많아도 가볍게 버티는 웹 서버.
- 2005: **AJAX**라는 이름이 붙으며 널리 퍼졌다 (기술 자체는 1999년부터 있었다). 이후 서버가 HTML 대신 데이터만 주는 방식이 크게 늘었다.

**6. WAS가 앱 안으로 (2009~)**
- 왜? 서비스를 작은 앱 여러 개로 나누고 클라우드에 자주 배포하게 되면서, 서버마다 WAS를 따로 설치·설정하기보다 앱 하나에 넣어 실행하는 편이 간단해졌다.
- 2009: **Node.js**. 원래 기다림 많은 요청을 일꾼 하나로 처리하려고 만들어졌다. 처음부터 WAS를 따로 두지 않고, 내 코드가 `http` 부품으로 직접 요청을 받는 방식이었다.
- 2014: **Spring Boot** 1.0. Tomcat을 앱 안에 넣어, 앱 파일 하나만 실행하면 서버가 뜬다. Java 쪽도 WAS를 따로 설치하지 않아도 되게 됐다 (기존 WAS에 올리는 방식도 여전히 쓴다).
- 2017: **NestJS**.

**7. 지금 (2020년대)**
- 지금 모습은 위 "WAS가 필요한 세상일까?" 참고.
- JEUS·WebLogic 같은 전통 WAS도 은행·공공기관 같은 큰 시스템에서 지금도 쓰인다.

**오늘 질문과 이어 보면**
JSP를 실행하던 Tomcat(3~4단계)과 NestJS 앱을 실행하는 Node.js(6단계)는 **같은 WAS 자리의 다른 세대**다. 다만 JSP는 HTML을 만들고, NestJS 앱은 보통 데이터(JSON)만 준다.

#### 웹 서버의 역사 (추가 질문)

**큰 흐름 먼저**
문서 공유(CERN) → 누구나 쓰는 웹 서버(Apache) → 동시 접속 문제 → Nginx → 클라우드용 새 서버(Caddy 등) → CDN이 맨 앞에 서는 시대

※ 여기서도 앞 세대가 사라진 게 아니라 함께 쓰인다.

**1. 왜 시작됐나 (1989~1993)**
- 1989: CERN(유럽 입자물리연구소)의 팀 버너스리가 웹을 제안했다. 여러 컴퓨터에 흩어진 연구 문서를 링크로 잇자는 아이디어였다.
- 링크를 누르면 그 문서가 있는 컴퓨터가 문서를 보내 줘야 한다. 그래서 컴퓨터마다 "요청을 기다렸다가 문서를 건네주는 프로그램"이 필요했다. 이것이 웹 서버다.
- 1990: 첫 웹 서버(CERN httpd)와 첫 브라우저를 만들었다. 주고받는 규칙(HTTP)과 문서 형식(HTML)도 이때 함께 나왔다.
- 1993: CERN이 웹 기술을 누구나 무료로 쓰게 공개했다. 같은 해 쓰기 쉬운 그림 화면의 브라우저(NCSA Mosaic)도 나와, 웹이 빠르게 퍼졌다.

**2. NCSA → Apache: 누구나 쓰는 웹 서버 (1993~)**
- 1993: 미국 대학 연구소(NCSA)가 웹 서버 NCSA HTTPd를 만들었다. 앞에서 본 CGI도 여기서 나왔다.
- 1995: NCSA HTTPd 개발이 멈추자, 이를 쓰던 관리자들이 각자 고친 코드를 모아 **Apache**를 만들었다. 무료 오픈소스다. 같은 해 마이크로소프트 IIS도 나와 Windows 쪽에서 많이 쓰였다.
- 1996년부터 Apache가 가장 많이 쓰는 웹 서버가 되어 오랫동안 1위를 지켰다.
- 강점은 모듈(나중에 끼워 넣는 추가 기능)을 붙이기 쉽다는 것이다. 예: mod_php를 붙이면 PHP를 Apache 안에서 바로 실행한다.
- 그래서 앞에서 "웹 서버는 이 구조에서 코드를 실행하지 않는다"고 한 것은 웹 서버와 WAS를 나눈 구조(Apache + Tomcat, Nginx + Tomcat) 이야기다. Apache에 mod_php를 붙이면 웹 서버가 WAS 역할까지 한 몸에 맡는다 (카운터 안에 작은 주방이 있는 셈). Nginx도 모듈로 코드를 실행할 수 있다.

**3. 문제: 동시 접속 (1999, C10K)**
- 초기 Apache는 접속 하나마다 일꾼 하나를 붙였다.
- 인터넷이 느린 사용자가 연결을 오래 잡고 있으면 일꾼이 그만큼 묶였다. 일꾼마다 메모리를 차지해서 많이 늘릴 수 없었고, 정해 둔 최대 수에 닿으면 새 접속은 기다려야 했다.
- 1999: 댄 케겔이 "서버 한 대로 동시 접속 1만 개를 어떻게 버틸까?"라는 문제를 정리했다. 이름은 C10K(10K = 1만).

**4. Nginx: 일꾼 몇 명이 수천 연결을 처리 (2004~)**
- 러시아 개발자 이고르 시소예프가 포털 Rambler의 많은 접속을 감당하려고 만들었다. 2004년에 공개했다.
- 방식: 일꾼을 CPU 수만큼만 두고, 일꾼 하나가 수천 개 연결을 번갈아 처리한다. 기다리는 연결에 일꾼을 붙잡아 두지 않으니 메모리를 적게 쓴다.
  - 앞의 카운터 비유로 치면, 초기 Apache는 손님 한 명마다 직원 한 명이 붙어 손님이 메뉴를 고르는 동안에도 옆에서 기다린다. 손님이 몰리면 직원을 계속 늘려야 한다.
  - Nginx는 직원 몇 명이 여러 손님을 번갈아 응대하고, 고민 중인 손님은 두고 준비된 손님부터 처리한다.
- 대세가 된 이유:
  - 파일 전달이 빠르고 가볍다.
  - WAS 앞에서 요청을 대신 받아 뒤의 Tomcat·Node.js로 넘기는 역할(**리버스 프록시**)에 딱 맞았다. HTTPS 처리와 로드 밸런싱도 같이 맡는다.
- 요즘 새로 만드는 서비스에서는 웹 서버 자리에 Nginx가 가장 흔하다 (한국 은행·공공기관에서는 WebtoB·Apache도 여전히 많다). 2020년 전후로 사용 점유율에서 Apache를 앞섰다 (조사마다 다름).
- Apache도 2005년 실험적으로, 2012년 정식으로 비슷한 방식(event)을 넣었다. 다만 처리 중인 요청에는 여전히 일꾼이 하나씩 붙는 절충형이다.

**5. 그 이후 세대: 클라우드 시대 (2015~)**
- 배경 1: 컨테이너(앱을 상자처럼 포장해 어디서나 바로 띄우는 기술, 예: Docker)와 이를 자동으로 관리하는 Kubernetes로 서버가 수시로 생기고 사라졌다. 사람이 설정을 고쳐서는 따라갈 수 없었다.
- 배경 2: HTTPS에 필요한 인증서(사이트가 진짜임을 증명하는 파일)를 Let's Encrypt가 무료로 주면서, 모든 사이트가 HTTPS로 갔다.
- **Caddy** (2015): HTTPS 인증서를 자동으로 받아 붙여 준다. 설정이 아주 짧다.
- **Traefik** (2016): 컨테이너가 뜨고 지는 것을 보고 스스로 설정을 바꾼다.
- **Envoy** (2016): 맨 앞문(웹 서버 자리)으로도, 작은 앱 여러 개로 나눈 구조(WAS 역사 6단계)에서 앱끼리 주고받는 요청의 중계로도 쓰인다. Kubernetes에 들어 있는 건 아니지만 그 환경에서 많이 쓰인다.
- **클라우드 로드 밸런서** (AWS ALB 등): 클라우드 회사가 대신 운영해 주는 앞문. Nginx를 직접 두지 않고 이것을 맨 앞에 두는 경우도 많다.

**6. 엣지: CDN이 맨 앞으로**
- CDN은 1999년(Akamai)부터 있었지만, 2010년대부터 Cloudflare 등이 사이트 전체의 맨 앞문을 맡는 경우가 많아졌다.
- CDN은 세계 곳곳에 둔 서버 중 사용자와 가장 가까운 곳에서 응답한다. 이렇게 사용자 가까이 있는 서버를 **엣지**라고 한다.
- 그래도 내 Nginx와 WAS는 그 뒤에 그대로 있다: 브라우저 → CDN → Nginx → WAS.
- Cloudflare는 Nginx로 하던 일을 직접 만든 프로그램으로 단계적으로 바꿨다 (2022년 Pingora 발표 등). 주된 이유는 Nginx 구조의 한계였고, 새 프로그램은 메모리 실수(보안 구멍의 흔한 원인)를 막아 주는 언어 Rust로 만들었다.
- 엣지에서 코드도 실행한다 (2017년 Cloudflare Workers 등). 앞의 Apache 모듈처럼, 웹 서버(카운터)와 WAS(주방)의 경계가 다시 흐려지고 있다.
- 주고받는 규칙(HTTP)도 HTTP/2(2015), HTTP/3(2022)로 발전해 더 빨라졌고, 웹 서버들이 이를 지원해 가고 있다.

**오늘 질문과 이어 보면**
- 웹 서버의 역할은 "파일을 보내는 곳"에서 "WAS 앞에서 요청을 받아 나눠 주는 카운터"로 넓어졌다.
- Nginx와 Node.js는 같은 방식(일꾼이 기다리지 않고 다른 연결을 처리)을 쓴다. Nginx가 처음 만든 방식은 아니지만, Node.js를 만든 라이언 달은 2009년 첫 발표에서 Apache와 Nginx를 비교하며 이 방식을 설명했다. 다만 Nginx는 일꾼이 여러 명, Node.js는 기본이 한 명이다. 웹 서버의 역사와 WAS의 역사가 여기서 만난다.

#### 웹의 발전 단계 (추가 질문)

자료의 6단계에 "그다음"을 붙였다. 질문 세 개는 3·4·5단계에서 답한다.

**큰 흐름 먼저**
정적 문서(1990~) → CGI(1993~) → 서버 내장형 실행(1996~) → WAS·기업용(1999~) → 브라우저 앱(2005~) → API·클라우드(2006~) → 그다음(엣지, AI)

※ 시기는 대략 처음 나온 때. 여기서도 앞 단계는 함께 쓰인다.

**1. 정적 문서 제공**
- 미리 만든 HTML 파일을 그대로 보낸다. 누가 와도 같은 페이지. (웹 서버의 역사 1단계)

**2. CGI 동적 처리**
- 요청이 오면 웹 서버가 바깥 프로그램을 실행하고 그 결과를 돌려준다. 요청마다 다른 페이지가 가능해졌지만, 매번 프로그램을 새로 켜서 느렸다. (WAS의 역사 2단계)

**3. 서버 내장형 실행 환경: 영어 약자는?**
- 답: 딱 하나로 정해진 약자는 없다. "내장형"을 어떻게 읽느냐에 따라 떠올릴 약자가 다르다.
- **HTML 속에 코드를 넣는다**로 읽으면: 이 단계의 대표 약자가 **ASP**(Active Server Pages), **JSP**(Java Server Pages), **PHP**다. 오늘 공부한 JSP가 바로 이 단계다.
- **웹 서버 안(또는 옆)에 실행 환경을 띄워 둔다**로 읽으면: CGI처럼 매번 켜지 않는 방식들의 이름이다.
  - 안에 끼우기: Apache의 **mod_php**(앞의 "카운터 안의 작은 주방"), IIS의 **ISAPI**
  - 옆에 띄워 두기: **FastCGI**(1996). 요즘 PHP(PHP-FPM)도 이렇게 돈다.
  - Java 쪽: **서블릿 컨테이너**(Tomcat). 한국에서는 Tomcat도 WAS라고 부르지만, 이 분류의 4단계 "WAS"는 J2EE 전체를 갖춘 WebLogic·JEUS 같은 큰 서버를 말한다 (WAS의 역사 4단계 참고).
- 영어로 이 시대를 넓게 부를 때는 **server-side scripting**이라고 한다 (약자 없음). 다만 2단계 CGI의 Perl 스크립트도 여기 들어가서 3단계만 가리키는 말은 아니다.
- ※ JSP·PHP처럼 서버에서 HTML을 만드는 것을, SPA가 나온 뒤에는 SSR(Server-Side Rendering)이라고 부르기도 한다 (7단계).

**4. WAS와 엔터프라이즈 플랫폼: 왜 "엔터프라이즈"인가?**
- 엔터프라이즈(enterprise) = **기업**. 이름에 그대로 들어 있다: J2EE = Java 2 Platform, **Enterprise Edition**. Java는 용도별로 판을 나눴다: SE(보통 프로그램), EE(기업 시스템), ME(휴대폰 같은 작은 기기).
- 왜 "기업용"이라는 큰 말을 붙였나: 이 단계의 목표가 홈페이지가 아니라 **회사 업무 전체**(주문, 결제, 재고, 인사)를 웹으로 옮기는 것이었기 때문이다. 기업 시스템에는 홈페이지에 없는 요구가 있었다.
  - 돈이 오가는 일은 "전부 성공 아니면 전부 취소"(트랜잭션)가 보장돼야 한다
  - 수많은 직원·고객이 동시에 써도 멈추지 않아야 한다 (서버 여러 대로 묶기)
  - 보안, 권한 관리
  - 이미 있던 옛 시스템(은행 등의 대형 컴퓨터, 메인프레임)과 연결
- 회사들의 뿌리도 기업 쪽이다. WebLogic을 판 BEA와 JEUS를 만든 티맥스소프트는 원래 트랜잭션 처리 소프트웨어(TP 모니터: Tuxedo, Tmax)를 팔았다. 메인프레임의 거래 처리를 더 싼 Unix 서버로 옮기던 기술이다. 그 경험을 Java·웹으로 넓힌 것이 이런 상용 WAS다.
- "플랫폼"인 이유: 서버 한 개가 아니라 **표준 규격 묶음**이다. 원칙적으로는 같은 앱을 WebLogic에도 JEUS에도 올릴 수 있다. 다만 서버마다 따로 쓰는 설정 파일과 고유 기능이 있어서, 실제로 옮길 때는 손볼 곳이 꽤 있었다.

**5. 브라우저 애플리케이션: 이것이 script인가?**
- 반은 맞다. **재료는 script**(여기서는 브라우저의 JavaScript. 3단계의 PHP도 "스크립트"지만 서버에서 돈다), 만든 결과가 **애플리케이션**이다.
  - 1995~: script는 HTML에 조금 덧붙이는 코드였다. 입력값 검사, 간단한 효과 정도.
  - 1990년대 후반~2000년대: Java 애플릿(1995), Flash(1996)처럼 브라우저에 추가 프로그램(플러그인)을 깔아 앱을 돌리는 방식도 있었다 (2002년부터 RIA, Rich Internet Application이라고 불렀다). 지금은 브라우저에서 아예 돌지 않는다 (Flash는 2020년 지원 종료).
  - 2005~: AJAX (WAS의 역사 5단계). Gmail·Google 지도가 "웹페이지인데 프로그램 같다"는 느낌을 줬다.
  - 2010~: **SPA**(Single Page Application). 페이지를 한 번 받은 뒤, 화면 전체를 브라우저의 JavaScript가 그리고 관리한다. AngularJS, React, Vue.
- 그래서 같은 JavaScript라도 "script"는 HTML 위의 작은 코드, "브라우저 애플리케이션"은 화면 전체를 책임지는 프로그램이다. 앞에서 본 "React·Vue는 브라우저에서 돈다"가 이 단계다.

**6. API 클라우드 구조**
- 서버는 화면(HTML) 대신 **데이터만 내주는 창구(API)**가 된다. 데이터는 보통 JSON(`{"name":"홍길동"}`처럼 값만 담은 글)으로 준다.
- 왜?
  - 5단계처럼 브라우저가 화면을 직접 그리니, 서버는 데이터만 주면 된다.
  - 2008년 아이폰 앱스토어 이후 스마트폰 앱이 폭발적으로 늘었다 (휴대폰 앱 자체는 그 전에도 Java ME 등으로 있었다). 웹과 앱이 같은 데이터를 쓰려면 서버가 화면이 아니라 데이터를 줘야 했다.
- 어디서 돌리나: 2006년 AWS 이후 서버를 클라우드에서 빌려 쓴다. 작은 서비스 여러 개(마이크로서비스)로 나눠 컨테이너(웹 서버의 역사 5단계)로 띄우거나, 서버 관리 없이 코드만 올리면 요청이 올 때 클라우드가 실행해 주는 방식(서버리스)을 쓴다.
- WAS의 역사 6단계(WAS가 앱 안으로, NestJS 앱은 보통 JSON을 줌)가 이 단계다.

**7. 그다음은? (예측이라 정답은 없다. 지금 보이는 흐름 세 가지)**
- **실행 위치가 사용자 가까이로: 엣지.** 코드 일부가 내 서버뿐 아니라 사용자와 가까운 CDN 서버에서도 돈다. (웹 서버의 역사 6단계)
- **서버와 브라우저가 일을 다시 나눈다.** 화면 만들기가 서버(JSP) → 브라우저(SPA)로 갔다가, 다시 서버로 일부 돌아오고 있다 (Next.js의 SSR 등). 또 WebAssembly(2017~)로 C·C++·Rust로 짠 프로그램도 **플러그인 없이** 브라우저에서 빠르게 돈다. 애플릿과 달리 브라우저에 들어 있는 기능이다.
- **API를 부르는 쪽에 AI가 더해진다.** 지금까지 API를 부르는 쪽은 주로 사람이 쓰는 브라우저와 앱이었다. 이제 AI 에이전트가 사람 대신 API를 부르고 일을 처리하기 시작했다. AI를 여러 서비스에 연결하는 표준(예: MCP, 2024)도 나왔다. 얼마나 커질지는 지켜볼 일이다.

**흐름을 꿰는 두 개의 질문**
- **화면을 만드는 코드는 어디서 도는가?** 서버(CGI, JSP) → 브라우저(SPA) → 일부 다시 서버(SSR)와 엣지로. 데이터를 처리하는 코드는 내내 서버에서 돈다.
- **누가 서버에 요청하는가?** 사람이 쓰는 브라우저 → 모바일 앱, 서비스끼리의 요청이 더해짐 → AI 에이전트도 더해지는 중. (검색 로봇처럼 사람 아닌 요청자는 처음부터 있었다.)

## 주제 2: C/S (클라이언트/서버)와 프로그래밍의 역사

- 웹을 공부하며 느낀 점이 "막힌 것에 대한 이해"였다면, C/S에서는 과거부터 미래까지 다시 고민해 보기
- BO가 C/S에서 웹으로 넘어간 계기는?

### Claude

※ BO는 백오피스(직원이 쓰는 사내 관리 시스템: 주문, 재고, 정산, 회원 관리 등)로 이해했다.

#### 먼저 두 개의 축
역사를 두 줄로 놓고 보면 흐름이 보인다.
- **축 1. 계산을 어디서 하나**: 중앙(메인프레임) → 각자 PC → 나눠서(C/S: 화면과 로직은 PC, 데이터는 DB 서버) → 다시 중앙(웹: 로직은 WAS) → 화면만 다시 클라이언트로(SPA, 모바일 앱), 업무 로직과 데이터는 중앙(클라우드 API)에 그대로 → ? 시계추처럼 오간다.
- **축 2. 사람이 기계에 말하는 수준**: 기계어 → 어셈블리 → 고급 언어 → 객체지향 → 그려서 만드는 도구(RAD) → 자연어(AI)? 대체로 사람 말 쪽으로 올라왔다. 다만 화면 만들기는 웹 초기에 한 칸 내려갔다가 프레임워크·로코드로 다시 올라왔다 (5·6장). 아래 단계도 계속 쓰인다.

#### 1. 기계에 직접 말하던 시절 (1940~50년대)
- 첫 컴퓨터들은 전선을 꽂거나, 0과 1로 된 명령(기계어)으로 프로그램했다.
- 어셈블리: 0과 1 대신 `ADD`, `MOV` 같은 짧은 단어로 바꿔 쓴 것.
- 클라이언트/서버라는 생각은 아직 없었다. 컴퓨터 한 대가 전부였다.

#### 2. 메인프레임과 고급 언어 (1950년대 후반~1970년대)
- 1957 **FORTRAN**(IBM): 과학 계산용. 수식을 거의 그대로 쓰는, 널리 쓰인 첫 고급 언어(사람 말에 가까운 언어).
- 1959 **COBOL**: 회사 업무(급여, 회계)용. 영어 문장처럼 쓴다. 지금도 은행 같은 큰 시스템에서 돈다.
- 1964 IBM System/360: 회사마다 중앙 컴퓨터(메인프레임)를 두는 시대.
- 처음(1950~60년대)에는 구멍 뚫은 카드 묶음을 맡기고 결과 인쇄물을 기다리는 일괄 처리가 보통이었다.
- 1970년대에는 직원 책상의 단말기(터미널, 예: IBM 3270)가 퍼졌다. 계산은 전부 중앙의 메인프레임이 하고, 단말기는 글자 화면을 보여 주고 키보드 입력을 보내기만 했다. 스스로 계산하지 못해서 "멍청한 단말(dumb terminal)"이라고 불렀다.
- 1972 **C** 언어(벨 연구소, Unix와 함께): 기계 가까이에서 빠르게 돌면서도 사람이 읽을 수 있는 언어. 이후 수많은 운영체제와 DB의 바탕이 됐다.

#### 3. PC와 DB: 계산은 책상 위로, 데이터는 한곳으로 (1970~1980년대)
- 1977 Apple II, 1981 IBM PC: 개인이 컴퓨터를 가졌다.
- 문제: 데이터가 PC마다 흩어졌다. 함께 쓰려면 연결이 필요해서 사내 네트워크(LAN)가 퍼졌다.
- 한편 PC와 별개로, 큰 컴퓨터 쪽에서 관계형 DB가 나왔다. 1970년 코드(E. F. Codd, IBM)가 이론을 내놓았고, 1979년 Oracle(당시 회사 이름은 Relational Software)이 SQL로 다루는 상용 DB를 내놓았다. 데이터를 표로 저장하고, SQL이라는 질의 언어로 꺼낸다.
- LAN으로 PC가 이어지자, 이 DB가 모두가 붙는 **DB 서버** 자리를 맡았다 (예: Sybase SQL Server, 1987).
- 1984 매킨토시, 1990 Windows 3.0: 마우스로 누르는 그림 화면(GUI)이 퍼졌다.
- 1985 **C++**: 객체지향(프로그램을 "물건(객체)" 단위로 나눠 짜는 방식)을 널리 퍼뜨린 언어. 객체지향 자체는 Simula(1967)에서 시작했다.

#### 4. C/S 전성기 (1980년대 후반~1990년대)
- 앞의 것들이 만났다: **PC의 그림 화면 + 사내 네트워크 + DB 서버** = 클라이언트/서버.
- **클라이언트**: 직원 PC에 설치한 Windows 프로그램. 화면과 업무 로직 대부분을 가진다 ("뚱뚱한 클라이언트", fat client).
- **서버**: Oracle, Sybase, MS SQL Server 같은 DB 서버. 일부 로직은 DB 안에 저장해 둔 프로그램(저장 프로시저)으로 둔다.
- 클라이언트가 서버에 SQL을 직접 보낸다. 둘 사이의 공용어가 SQL이었다. 이것이 **2계층(2-tier)** 구조다.
- 언어·도구: 화면을 그림 그리듯 배치하고 버튼에 코드를 붙이는 **RAD 도구**가 주인공이었다 (PowerBuilder, Oracle Forms 같은 일부는 "4GL"이라고도 불렀다).
  - PowerBuilder (1991): 데이터를 표로 다루는 DataWindow가 강력했다. 한국에서도 기업 사내 시스템에 많이 쓰였다고 알려져 있다.
  - Visual Basic (1991), Delphi (1995), Oracle Forms
- 이 시기 백오피스(ERP, 회계, 인사, 병원·관공서 업무)가 대부분 이렇게 만들어졌다.
- **3계층(3-tier)**: 클라이언트와 DB 사이에 업무 로직을 맡는 중간 서버를 두는 방식. 거래 처리 전문 소프트웨어(TP 모니터: Tuxedo, Tmax)가 이 자리에 섰다.
  - 웹 시대에는 이 자리를 주로 WAS가 맡게 됐다 (주제 1, 웹의 발전 단계 4단계: Tuxedo·Tmax를 팔던 회사들이 WebLogic·JEUS를 팔게 됐다).
  - 은행 같은 큰 시스템에서는 지금도 WAS 뒤에 TP 모니터를 함께 둔다.

#### 5. BO가 C/S에서 웹으로 넘어간 계기 (2000년 전후~2010년대)
C/S의 아픈 점과, 웹이 그것을 어떻게 풀었는지:
- **설치·업데이트**: C/S는 PC 수백 대마다 새 버전을 깔아야 했고, 버전이 섞이면 오류가 났다. → 웹은 서버만 고치면 모두에게 바로 반영된다.
- **PC 환경**: C/S는 Windows 버전, 여러 프로그램이 함께 쓰는 부품 파일(DLL)의 충돌("DLL 지옥")에 시달렸다. → 웹은 브라우저만 있으면 된다.
- **밖에서 접속**: C/S는 사내망 밖(지점, 집, 협력사)에서 DB에 직접 붙기 어렵고 위험했다. → 웹은 인터넷으로 어디서나 쓰고, DB는 안쪽에 숨긴다.
- **DB 연결**: 2계층 C/S는 PC마다 DB 연결을 하나씩 잡아서, 사람이 늘면 DB가 버거웠다. 3계층으로 풀 수 있었지만 비싸고 어려웠다. → 웹은 처음부터 3계층이라 WAS가 연결을 나눠 쓴다 (주제 1의 커넥션 풀).
- **때도 맞았다**: 2000년 전후 인터넷이 퍼지고, J2EE(주제 1)가 표준 도구를 줬다. 예를 들어 Salesforce(1999)는 "설치하는 소프트웨어는 그만(No Software)"을 내걸고, 설치형 C/S 영업관리 프로그램을 웹 서비스로 대체했다.
- **언어도 바뀌었다**: 화면 도구 언어(PowerBuilder, VB) + SQL → 서버는 Java(서블릿·JSP)나 C#(.NET, 2002), 화면은 HTML + JavaScript. 주제 1의 세계가 여기서 시작된다.
- **다른 길도 있었다**: C/S 프로그램을 서버에서 돌리고 화면만 보내는 터미널 서버(Citrix 등), 값싼 단말인 "네트워크 컴퓨터"(1990년대 후반). BO에서는 이미 모든 PC에 깔려 있던 브라우저가 대개 이겼다. 브라우저는 똑똑해진 단말, WAS는 메인프레임 자리인 셈이다.

그런데 처음 웹 BO는 C/S보다 **불편했다.** 엑셀 같은 표(그리드), 빠른 키보드 입력, 즉시 반응이 잘 안 됐다.
- 그래서 한국에서는 X-Internet·RIA 도구(투비소프트 MiPlatform, 2003 등)를 많이 썼다. 웹으로 배포하지만 화면은 C/S처럼 움직이는 방식이다. 다만 PC에 전용 실행 엔진을 ActiveX(IE에 프로그램을 깔게 하는 기술)로 설치해야 해서, IE 의존과 설치 문제가 일부 남았다.
- 이 도구들은 AJAX·SPA와 함께 2010년대까지 쓰였다. 그러다 스마트폰과 크롬 같은 IE 밖 브라우저가 퍼지고 ActiveX·플러그인이 퇴출되면서, HTML5(플러그인 없이 브라우저만으로 풍부한 화면을 만드는 웹 표준) 기반으로 넘어갔다. 같은 회사의 도구도 HTML5판(넥사크로 등)으로 바뀌었다.

정리: BO가 웹으로 간 것은 화면이 더 좋아서가 아니라 **배포·관리·접속** 때문이었다. 화면 품질은 나중에 따라잡았다.

#### 6. 지금 (2010년대~)
- 화면은 다시 클라이언트 쪽으로 왔다: SPA로 만든 BO 화면, 모바일 앱.
- C/S와 다른 점: SPA·앱은 DB에 SQL을 직접 보내지 않고 API만 부른다. 업무 로직과 DB 연결은 서버에 남는다 (주제 1: 데이터를 처리하는 코드는 내내 서버).
- 설치·업데이트도 쉬워졌다: SPA는 웹처럼 바로 바뀌고, 앱은 스토어가 깔아 준다. 다만 앱은 옛 버전이 한동안 섞여서, 이 점은 C/S를 닮았다.
- PC 프로그램도 돌아왔다: VS Code, Slack은 웹 기술로 만든 PC 프로그램이다 (Electron, 2013).
- BO를 만드는 방식: 직접 만들기, SaaS(남이 만든 서비스를 빌려 쓰기, Salesforce 등), 로코드 도구(코드를 적게 쓰고 화면을 조립해 만드는 도구, Retool 등). 로코드는 1990년대 PowerBuilder·VB의 "그려서 만든다"는 생각이 돌아온 것이다.
- 언어: 클라이언트는 TypeScript(2012, 웹), Swift(2014)·Kotlin(모바일). 서버는 Java·C#에 Go(2009), Node.js(TypeScript), Python이 더해졌다. Rust(2015)는 속도와 안전이 중요한 아래층에 쓰인다. COBOL도 여전히 돈다.

#### 7. 미래 (예측이라 정답은 없다)
- **축 2의 다음 칸, 자연어?** AI가 코드를 써 주면서, 사람은 "무엇을 원하는지"를 말로 설명하는 쪽으로 올라가고 있다. 기계어 → 고급 언어 때처럼 코드를 직접 쓰는 일은 줄어들 수 있다. 다만 컴파일러는 같은 코드를 늘 같은 결과로 바꾸지만 AI는 그렇지 않아서, 만든 코드를 사람이 읽고 확인하는 일은 남는다.
- **화면 대신 대화?** BO의 많은 일(조회, 보고서, 간단한 수정)을 메뉴를 찾아 누르는 대신 AI에게 말로 시키는 방식이 시도되고 있다. 이때 API를 부르는 쪽(클라이언트)은 AI이고, 서버는 지금처럼 API다. 다만 큰 AI 모델은 대부분 클라우드에서 돌아서, 사용자 화면은 대화창만 남는다. 축 1로는 중앙 쪽이다.
- **반대 방향도 있다**: 계산이 다시 사용자 기기로 오는 흐름(기기 안에서 도는 작은 AI, 인터넷이 끊겨도 되는 앱). 서버도 사용자 가까이로 흩어진다(엣지, 주제 1 웹 서버의 역사 6단계). 시계추가 어느 쪽으로 갈지는 아직 모른다.

#### 과거에서 미래로: 바뀐 것과 남은 것
- **매번 바뀐 것**: 계산을 어디서 하나(축 1), 얼마나 사람 말에 가깝게 쓰나(축 2).
- **C/S 이후 줄곧 남은 것**: 데이터는 서버(DB)에 모은다. PC 시대에 흩어졌던 데이터를 DB 서버로 모은 뒤로는 C/S의 DB 서버, 웹의 WAS+DB, 클라우드 API가 모두 같다. 다만 인터넷이 끊겨도 되는 앱처럼 원본을 기기에 두는 설계도 나오고 있어서, 이것도 바뀔 수 있다.
- **사라지지 않고 쌓인 것**: COBOL, Oracle, TP 모니터처럼 오래된 것도 아래층에서 계속 돈다.

- C/S에서 클라이언트(C)는 무엇을 맡았고, 웹으로 오면서 그 일은 어디로 갔을까?
- BO가 웹으로 넘어간 가장 큰 이유는 화면이 좋아서였을까?
- 2계층과 3계층의 차이는? 3계층의 가운데 자리는 웹 시대에 무엇이 맡았을까?

## 주제 3: 기술 조합으로 보는 BO의 발전 (C/S → 웹 → 클라우드 → 미래)

### 질문
- 주제 2에 이어, C/S에서 웹 BO로 발전하는 과정을 따로 정리하기
- C/S 프로젝트의 대표 기술부터 웹/서버까지, 그리고 클라우드 이후 미래 기술의 대표 기술 조합은?

### Claude

주제 2가 "왜 바뀌었나"였다면, 여기서는 **그때 프로젝트를 하면 무엇을 조합해 썼나**를 본다. 두 방향으로 정리한다.
- 세대별 조합: 그 시대 BO 프로젝트 하나를 층별로 펼쳐 본다
- 층별 변천: 화면, 업무 로직, 데이터, 배포가 각각 어떻게 바뀌었나

※ "대표 조합"은 흔했던 예다. 실제 프로젝트는 회사마다 달랐고, 한국 기업 기준의 예를 함께 적었다.
※ 세대는 차례로 끝나지 않고 겹친다. 2000년대에도 C/S는 .NET(WinForms)으로 계속 만들어졌고, 지금도 PowerBuilder·MiPlatform으로 만든 BO가 돈다 (주제 1·2: 앞 단계는 함께 쓰인다).
※ 직접 만들기 옆에는 늘 "사서 쓰기"(ERP 패키지)가 있었다. 클라우드에서는 "빌려 쓰기"(SaaS)가 됐다.

#### 세대별 대표 조합

**1세대. C/S 2계층 (1990년대)**
- 화면: PowerBuilder, Visual Basic, Delphi, Oracle Forms (PC에 설치하는 Windows 프로그램)
- 업무 로직: 화면 프로그램 안 + DB의 저장 프로시저 (주제 2. Oracle에서는 PL/SQL이라는 전용 언어로 짠다)
- DB: Oracle, Sybase, MS SQL Server, Informix
- 연결: 클라이언트가 DB에 SQL을 직접 보낸다. 통로는 DB 회사가 주는 연결 프로그램(드라이버)이나 ODBC(여러 DB에 같은 방식으로 붙게 해 주는 마이크로소프트 표준)
- 서버 운영체제: Unix(HP-UX·AIX·Solaris: HP·IBM·Sun의 Unix), Windows NT
- 출력(보고서·서식): PowerBuilder의 DataWindow, Crystal Reports
- 배포: 설치 디스켓·CD, 사내 파일 서버
- 한 줄: 화면과 로직이 PC에, 데이터는 DB 서버에.

**2세대. C/S 3계층 (1990년대 후반)**
- 화면: 1세대와 같은 도구
- 업무 로직: 가운데 서버로 옮긴다. TP 모니터(Tuxedo, Tmax), 분산 객체(다른 컴퓨터에 있는 프로그램 부품을 내 것처럼 부르는 기술: CORBA, 마이크로소프트 DCOM)
- 또는 ERP 패키지를 사서 쓰기: SAP R/3(1992)가 대표적인 3계층 C/S다 (PC의 SAP GUI + 업무 서버 + DB).
- DB: Oracle 등
- 한 줄: 로직이 PC에서 가운데 서버로. 웹 WAS 구조의 바로 앞 단계. 다만 비싸고 어려워서 은행·통신 같은 큰 시스템 위주였고, 많은 BO는 2계층에서 바로 웹으로 갔다 (주제 2).

**3세대. 초기 웹 BO (2000년대 초)**
- 화면: HTML + 약간의 JavaScript, 서버에서 만든 페이지(JSP, ASP, PHP). 대부분 IE 전용.
- 업무 로직: WAS에서 Java(J2EE) 또는 .NET(C#, 2002)
  - Java 쪽 흔한 조합: Struts(요청을 어느 코드·JSP로 보낼지 정해 주는 틀) + EJB(무거운 업무 로직 부품, 주제 1) + JDBC(Java에서 SQL을 직접 써서 DB에 붙는 표준)
  - EJB는 WebLogic·JEUS 같은 큰 WAS에서만 돌았다. Tomcat에서는 EJB 없이 Struts + JDBC로 짰다 (주제 1).
- 웹 서버(Apache, WebtoB) + WAS(Tomcat, WebLogic, WebSphere, JEUS)
- DB: Oracle, MS SQL Server
- 배포: 서버에 앱 묶음(WAR 파일, EJB를 쓰면 EAR 파일)을 올리면 끝. PC 설치가 없어졌다.
- 한 줄: 설치는 사라졌지만, 화면은 C/S보다 불편했다.

**4세대. 화면을 다시 풍부하게: RIA와 AJAX (2000년대 초중반~2010년대, 3세대와 겹침)**
- 화면은 두 갈래였다.
  - 한국에서 특히 많이: X-Internet/RIA 도구. 가우스(Gauce, 2001), MiPlatform(2003)·XPLATFORM(투비소프트). 브라우저에 실행 엔진(ActiveX)을 깔아 C/S 같은 그리드(엑셀 같은 표) 화면을 낸다. 해외에서는 Flash 기반의 Adobe Flex도 쓰였다.
  - 해외와 많은 한국 기업: 서버 페이지(JSP, ASP.NET) + jQuery(2006)·AJAX + 그리드 부품. 플러그인 없이 화면 일부를 새로고침 없이 바꾼다.
- 업무 로직: Spring + iBATIS(SQL을 따로 적어 두고 Java에서 불러 쓰는 도구, 2010년에 MyBatis로 이름이 바뀜) + WAS. 공공 쪽은 Spring 기반의 전자정부 표준프레임워크(2009~)가 표준처럼 쓰였다.
- 출력: 한국 웹 BO는 OZ Report, Crownix(RD), UbiReport 같은 리포트 도구를 함께 썼다.
- DB: Oracle
- 한국 공공 BO의 교과서 같은 조합: RIA + 리포트 도구 + 전자정부 프레임워크 + WebtoB·JEUS + Oracle
- 한 줄: 배포는 웹, 화면 느낌은 C/S. RIA는 대신 IE·ActiveX나 Flash 같은 플러그인에 묶였다.

**5세대. 현대 웹 BO (2010년대 중반~)**
- 화면: HTML5 + SPA(React, Vue, Angular) + TypeScript(자료형을 적는 JavaScript) + 그리드 부품. 한국 기업은 넥사크로(투비소프트), WebSquare(인스웨이브) 같은 HTML5 UI 도구도 많이 쓴다.
- 업무 로직: Spring Boot(Tomcat 내장) 앱 하나 + MyBatis(SQL을 직접 쓴다) 또는 JPA(SQL 대신 Java 객체로 DB를 다루는 Java 표준). 또는 Node.js(NestJS).
- 화면에는 데이터만 준다 (React·Vue는 보통 JSON, 넥사크로는 자체 XML 형식 등).
- 웹 서버: Nginx (맨 앞에서 요청을 받는 문, 주제 1)
- DB: Oracle, MySQL, PostgreSQL
- 배포: Jenkins 같은 도구로 빌드(실행 파일 만들기)·테스트·배포를 자동화한다 (CI/CD: 코드를 올리면 검사부터 서버 반영까지 자동으로)
- 한 줄: 화면은 브라우저가 그리고, 서버는 데이터만. 플러그인 없이 C/S만큼 편해졌다.

**6세대. 클라우드 BO (2010년대 후반~지금)**
- 화면: React·Vue·Next.js, 또는 로코드 도구(Retool 등)
- 또는 통째로 빌리기: SaaS(Salesforce 등. 1999년부터 있었고, 이 시기에 BO에 널리 퍼졌다)
- 업무 로직: Spring Boot·NestJS 앱 하나를 컨테이너로 띄우는 경우가 많다. 큰 시스템은 작은 서비스 여러 개(마이크로서비스)로 나누고, 앞에 API 게이트웨이(요청 입구를 하나로 모으는 것)를 둔다.
- 실행 환경: 컨테이너(Docker) + Kubernetes(컨테이너를 자동으로 띄우고 관리), 일부는 서버리스(AWS Lambda 등). 주제 1 참고.
- 데이터: 클라우드가 관리해 주는 DB(AWS RDS 등), 캐시(자주 쓰는 값을 메모리에 두고 빨리 꺼내는 곳, Redis). 큰 시스템은 메시지 전달(서비스끼리 할 일을 줄 세워 주고받는 통로, Kafka)도 쓴다.
- 배포·운영: CI/CD(GitHub Actions 등), 서버·네트워크 설정을 코드 파일로 적어 두고 자동으로 만들기(Terraform), 모니터링(서버 상태 지켜보기)
- 로그인: 클라우드 로그인 서비스(Okta, Microsoft Entra ID 등). 한 번 로그인으로 여러 시스템을 쓰는 SSO는 2000년대 사내 포털 때부터 썼고, 이제 SaaS까지 넓어졌다. 비밀번호를 넘기지 않고 권한을 빌려주는 표준(OAuth)도 함께 쓴다.
- 한 줄: 서버를 사지 않고 빌리며, 자주 배포한다.

**7세대. 미래 (예측이라 정답은 없다, 지금 시도되는 조합)**
- 화면: 기존 그리드 화면 + 대화창(AI에게 말로 시키기). 필요할 때 AI가 화면을 만들어 보여 주는 방식도 시도된다.
- 업무 로직: AI 에이전트가 기존 API를 "도구"로 불러 일을 처리한다.
  - LLM: 글을 읽고 쓰는 큰 AI 모델. API로 빌려 쓴다 (Claude 등)
  - MCP: AI가 사내 시스템을 도구로 쓰게 이어 주는 표준 (주제 1)
  - RAG: 사내 문서를 먼저 찾아, 그 내용으로 답하게 하는 방식
- 데이터: 기존 DB + 벡터 검색(글을 숫자 묶음으로 바꿔 두고, 글자가 달라도 뜻이 비슷한 문서를 찾는 것. RAG가 문서를 찾을 때 쓴다). 전용 벡터 DB도 있고, Oracle·PostgreSQL에 붙은 벡터 기능도 있다.
- 실행 환경: 클라우드·서버리스 그대로, 일부 계산은 엣지와 기기 안으로
- 개발·운영: AI 코딩 도구가 코드를 쓰고 사람이 검토한다. 로코드에도 AI가 붙는다. 장애 분석 같은 운영에도 AI를 쓰기 시작했다.
- 꼭 필요해지는 것: AI가 무엇을 했는지 남기는 기록(감사 로그), 권한 관리, 중요한 일은 사람이 승인하기
- 한 줄: 화면을 누르는 대신 말로 시키고, 서버의 API는 AI의 도구가 된다.

#### 층별로 보면

- **화면**: 1·2세대 PowerBuilder·VB (PC 설치) → 3세대 JSP·HTML (서버가 만든 페이지) → 4세대 MiPlatform (플러그인) 또는 JSP + jQuery·AJAX → 5·6세대 React·넥사크로 (HTML5) → 7세대 + 대화창·AI가 만드는 화면
- **업무 로직**: 1세대 화면 프로그램 + 저장 프로시저 → 2세대 TP 모니터 → 3세대 WAS(Struts, EJB) → 4세대 Spring(전자정부 프레임워크) → 5세대 Spring Boot·NestJS 앱 하나 → 6세대 큰 시스템은 마이크로서비스로 나눔 → 7세대 + AI 에이전트
- **데이터**: 1~4세대 Oracle(·Sybase 등) → 5세대 + MySQL·PostgreSQL → 6세대 클라우드가 관리해 주는 DB + Redis(·Kafka) → 7세대 + 벡터 검색
- **배포**: 1·2세대 설치 CD → 3·4세대 WAR를 WAS에 올리기 → 5세대 CI/CD 자동화 → 6세대 컨테이너·클라우드 → 7세대 + AI가 코드·운영을 돕기
- **만드는 방식**: 1·2세대 그려서 만들기(RAD) → 3세대 화면은 HTML 손코딩 → 4·5세대 한국은 RIA·넥사크로 같은 그려서 만드는 도구, 해외는 프레임워크 → 6세대 로코드·SaaS → 7세대 AI와 함께 만들기

#### 이어 보면
- 세대가 바뀔 때마다 앞 세대의 아픈 점을 푸는 조합이 나왔다: 설치 문제는 웹이, 불편한 웹 화면은 RIA와 AJAX가, 플러그인 의존은 HTML5가, 서버 관리 부담은 클라우드가 풀었다.
- "그려서 만들기"(PowerBuilder)는 한국에서는 RIA·HTML5 도구의 화면 편집기로 먼저 돌아왔고, 최근엔 로코드로 넓어졌다. 이제 "말로 만들기"(AI)를 시도한다 (주제 2의 축 2).
- DB, 특히 Oracle은 1세대부터 지금까지 남아 있다 (주제 2, 바뀐 것과 남은 것).

## 주제 4: 연대별 대표 기술 조합 (1950~2026, 그리고 앞으로)

### 질문
- 연대별 대표 기술 조합을 시대, 대표 아키텍처, client·front-end, server·back-end, database와 통합, 대표 배포 기술, 대표 제품 기술, 실행 환경으로 나눠 1950~2026년과 앞으로의 방향성까지 정리하기

### Claude

주제 2·3을 한 장의 표로 모은 것이다. 시대마다 "그때 시스템 하나를 만들면 각 칸에 무엇이 들어갔나"를 적었다.

※ 표가 넓어서 휴대폰에서는 옆으로 밀어서 본다. 표 속 낱말 풀이는 표 바로 아래에 있다.
※ 시대 칸은 대략 널리 퍼진 때이고, 괄호 속 연도는 처음 나온 해라서 시대 칸보다 이를 수 있다. 각 칸은 대표적인 예이고, 앞 시대 기술은 사라지지 않고 함께 쓰인다 (주제 1~3).
※ 1950~70년대(초기 컴퓨터·메인프레임)는 client와 server가 아직 나뉘지 않았다. client 칸에는 사람이 쓰던 입출력 장치를, server 칸에는 중앙 컴퓨터에서 프로그램을 짜고 돌리던 언어·소프트웨어를 적었다.
※ "database와 통합" = DB, 그리고 시스템끼리 잇는 방법. "대표 제품 기술" = 그 시대를 상징하는 제품·서비스.

#### 표 속 낱말
- 일괄 처리(batch): 일을 모아 한꺼번에 돌리고, 결과는 나중에 받는 방식
- 첫 운영체제(1956): IBM 704용 일괄 처리 모니터(GM-NAA I/O). 그 전에는 사람이 기계를 직접 조작했다
- 시분할: 컴퓨터 한 대를 여러 사람이 아주 짧게 번갈아 써서, 각자 혼자 쓰는 듯하게 하는 방식
- JCL: 메인프레임에 "이 프로그램을 이 파일로 돌려라"를 적는 작업 지시서
- 온라인 처리: 단말에서 넣으면 바로 처리해 답하는 방식 (일괄 처리의 반대). 호스트 = 중앙 메인프레임
- TP 모니터: 수많은 단말의 거래를 동시에 처리하는 소프트웨어. 메인프레임의 CICS(1969)가 먼저였고, 뒤에 Tuxedo·Tmax가 Unix로 옮겼다
- 계층형·망형 DB: 관계형(표) 이전의 DB. 데이터를 나무·그물 모양으로 잇는다
- 미니컴퓨터: 메인프레임보다 작고 싼 부서용 컴퓨터 (PDP-11 등)
- GUI: 마우스로 누르는 그림 화면. 처음은 Xerox Alto(1973)였고, 매킨토시(1984)가 대중화했다
- ODBC·JDBC: 프로그램이 여러 DB에 같은 방식으로 붙게 해 주는 표준 (ODBC는 마이크로소프트, JDBC는 Java)
- LAMP: Linux + Apache + MySQL + PHP. 2000년대 웹의 대표 조합
- EAI: 사내 여러 시스템을 가운데 중계 서버 하나로 잇는 소프트웨어
- SOAP: XML 문서로 다른 시스템의 기능을 부르는 약속 (REST의 앞 세대)
- SOA·ESB: 기능을 "서비스"로 나눠 서로 부르게 하는 설계(SOA)와 그 공용 통로(ESB)
- REST: 웹 주소(URL)와 HTTP로 데이터(보통 JSON)를 주고받는 API 방식. 2000년에 정의됐다
- 가상 머신(VM): 서버 한 대를 여러 대처럼 나눠 쓰는 기술
- PaaS: 코드만 올리면 서버 준비·실행은 클라우드가 해 주는 서비스
- NoSQL: 표 대신 문서나 "키-값"으로 저장하는 DB. 관계형 DB를 대신했다기보다 옆에 더해졌다 (Redis는 주제 3의 캐시)
- GitOps: Git에 적어 둔 설정대로 서버가 자동으로 맞춰지는 배포 방식
- GPU: AI 계산을 빠르게 하는 칩. 비싸서 클라우드에서 빌려 쓴다
- MCP, 벡터 검색, SSR, 서버리스, 컨테이너: 주제 1·3 참고

#### 칸마다 한 줄로 보면
- **대표 아키텍처**: 컴퓨터 한 대 → 메인프레임 중앙 집중 → PC로 흩어짐 → C/S로 나눔 → 3계층 웹 → 클라우드·마이크로서비스 → AI 연동
- **client·front-end**: 카드·인쇄물 → 글자 단말 → PC GUI → 브라우저(서버가 만든 화면) → SPA·모바일 앱 → + AI 대화창
- **server·back-end**: 어셈블리·FORTRAN → COBOL·CICS(메인프레임 TP 모니터) → 저장 프로시저 → Unix TP 모니터 → WAS(J2EE) → Spring → Spring Boot·Node.js API → + AI 에이전트
- **database와 통합**: 테이프 파일 → 계층형 DB → 관계형 DB(SQL) → 메시지 큐 → EAI·ESB → + NoSQL·빅데이터 → 관리형 DB·Kafka → + 벡터 검색·MCP. 관계형 DB는 1980년대부터 지금까지 중심에 남아 있다.
- **대표 배포 기술**: 카드 묶음 → 운영자 일괄 처리 → 디스켓·CD → WAR 파일 → 가상 머신 → CI/CD·컨테이너 → GitOps·AI 보조
- **대표 제품 기술**: IBM 704 → System/360 → PDP·VAX → IBM PC → Windows → WebLogic·JEUS → AWS → ChatGPT·Claude
- **실행 환경**: 진공관 컴퓨터 → 트랜지스터 메인프레임 → 미니컴퓨터·Unix → PC → Unix·Linux 서버 → 가상 머신 → 클라우드·컨테이너 → 엣지·GPU

#### 앞으로의 방향성 (예측이라 정답은 없다)
- **계산 위치**: 중앙(클라우드 GPU)과 기기·엣지 양쪽이 함께 커지고 있다. 시계추가 어느 쪽에 설지는 아직 모른다 (주제 2의 축 1).
- **화면**: 누르는 화면은 남고, 그 옆에 말로 시키는 창이 붙을 것으로 보인다 (주제 3의 7세대).
- **서버**: API가 사람의 화면뿐 아니라 AI 에이전트의 도구로도 쓰이기 시작했다. 그래서 API를 잘 정리해 두는 일이 더 중요해질 것으로 보인다.
- **데이터와 통합**: 표로 된 데이터와 문서(글)를 함께 찾는 일이 늘고 있다. 누가 무엇을 볼 수 있는지(권한), AI가 무엇을 했는지(기록)를 관리하는 일이 핵심 과제로 꼽힌다.
- **배포·개발**: 자동화가 늘고 AI가 코드를 쓰기 시작했다. 사람은 검토하고 승인하는 쪽으로 무게가 옮겨 갈 것으로 보인다.
- **실행 환경**: GPU가 비싼 핵심 자원이 되면서, 메인프레임 시절처럼 비싼 계산 자원을 나눠 쓰는 모습이 다시 보인다.

#### 이어 보면
- 70여 년 동안 바뀐 것은 대체로 두 가지다: 계산을 어디서 하나, 사람이 얼마나 쉬운 말로 기계에 시키나 (주제 2의 두 축).
- 매 시대 앞 시대의 불편을 푼 기술이 다음 대표가 됐다: 카드 일괄 처리는 온라인 단말이, 중앙 집중은 PC가, 흩어진 데이터는 DB 서버가, 설치는 웹이, 서버 관리는 클라우드가 풀었다.
- COBOL, 메인프레임, 관계형 DB처럼 오래된 칸의 기술도 아래층에서 계속 돈다.

### 스스로 확인해보기
- 1970년대 글자 화면 단말과 2020년대 브라우저는 무엇이 닮았고, 무엇이 다를까?
- "database와 통합" 칸에서 SQL이 나온 뒤로 계속 남아 있는 것은 무엇일까?
- 배포가 "카드 묶음"에서 "CI/CD"까지 오는 동안, 사람이 하던 일은 어디로 갔을까?
- 앞으로 칸에서 API를 부르는 쪽은 누구일까?
