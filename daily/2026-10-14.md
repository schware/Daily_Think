## Claude

### 한 줄 요약
JSP는 **서버**에서 실행되어 HTML을 만들고, JavaScript는 그 HTML을 받은 **브라우저**에서 실행된다. WAS는 JSP 같은 서버 프로그램을 실행해 주는 서버다.

### 요청 하나가 처리되는 순서
1. 사용자가 브라우저에서 `list.jsp` 주소를 연다.
2. WAS가 요청을 받아 JSP를 실행한다. 이때 Java 코드가 돌고, 필요하면 DB도 조회한다.
3. 실행 결과로 **HTML 문서(텍스트)** 가 만들어져 브라우저로 간다. JSP 코드 자체는 브라우저로 가지 않는다.
4. 브라우저가 HTML을 위에서부터 읽으며 화면을 그리다가, `<script>`를 만나면 그 JavaScript를 실행한다.
5. 그 뒤 버튼 클릭 같은 사용자 동작은 브라우저 안의 JavaScript가 처리한다. 서버의 데이터가 다시 필요하면 새로 요청을 보낸다.
   - 페이지 이동: JSP가 다시 실행되어 새 HTML 전체가 온다.
   - `fetch`/AJAX: 보통 데이터(JSON)만 받아서, JavaScript가 새로고침 없이 화면 일부만 바꾼다.

### JSP
- Java Server Pages. HTML 사이에 Java 코드를 섞어 쓰는 **서버 쪽** 기술이다.
- 처음 요청이 오면 WAS가 JSP를 **순수 Java 프로그램(서블릿)으로 바꾸고 컴파일**한다. 이후엔 그것을 바로 실행하고, JSP를 고치면 (개발 설정에서는 보통) 이 과정을 다시 한다.
- 결과물은 HTML 텍스트일 뿐이다. 브라우저에서 "페이지 소스 보기"를 하면 JSP 코드는 없고 HTML만 보인다.

### JavaScript
- 주로 브라우저 안에서 실행되는 언어다. (서버에서도 돌릴 수 있다 → 아래 Node.js)
- 서버가 HTML을 보낸 **뒤에** 브라우저에서 실행된다. 화면 요소(DOM)를 바꾸고, 클릭·입력에 반응하고, 서버에 추가 요청을 보낸다.
- 이름이 비슷하지만 Java와는 전혀 다른 언어다.

### 가장 헷갈리는 지점: 실행 순서
```jsp
<% String name = "홍길동"; %>
<script>
  var name = "<%= name %>";
  alert(name);
</script>
```
- `<% %>` 안은 서버에서 도는 Java 코드, `<%= %>`는 그 값을 그 자리에 찍는 표시다.
- 서버에서 JSP가 먼저 실행되어 `<%= name %>` 자리에 `홍길동`이 들어간다.
- 브라우저가 받는 것은 `var name = "홍길동";` 이라는 JavaScript 코드일 뿐이다.
- 그래서 JSP는 JavaScript **코드를 만들어낼** 수는 있지만, 반대로 JavaScript가 JSP 변수를 직접 바꿀 수는 없다. 서버에서 실행이 이미 끝났고, 그 변수도 응답을 보낼 때 사라졌기 때문이다.
- 반대 방향(브라우저 → 서버)은 **새 요청**에 값을 실어 보낸다. 예: `list.jsp?name=김철수`, 폼 전송, `fetch`. 그러면 JSP가 처음부터 다시 실행되고 `request.getParameter("name")`으로 그 값을 읽는다.
- 참고: 사용자 입력을 이렇게 그대로 넣으면 따옴표 때문에 코드가 깨지거나, 남이 넣은 스크립트가 실행될 수 있다(XSS). 그래서 특수문자를 안전한 글자로 바꿔 넣는다(이스케이프). 바꾸는 방법은 넣는 위치에 따라 다르다 (HTML 안인지, 여기처럼 JavaScript 문자열 안인지).

### WAS (Web Application Server)
- 요청이 올 때마다 **프로그램을 실행해서** 응답을 만들어 주는 서버다. 예: Tomcat(가장 많이 씀), JEUS, WebLogic, JBoss(WildFly)
- **웹 서버**(Apache, Nginx)와 비교하면:
  - 웹 서버: 이미 만들어진 파일(HTML, 이미지, CSS, JS)을 그대로 돌려준다 → 정적
  - WAS: JSP·서블릿을 실행해서 상황마다 다른 결과를 만든다 → 동적
- WAS가 하는 일:
  - JSP·서블릿을 실행하고 관리한다 (이 역할을 "서블릿 컨테이너"라고 부른다)
  - 요청마다 일꾼(스레드)을 하나씩 붙여, 여러 사람의 요청을 동시에 처리한다
  - 요청 사이에 "누가 로그인했는지" 같은 사용자별 정보를 기억한다 (세션)
  - DB 연결을 미리 만들어 두고 나눠 쓰게 해 준다 (커넥션 풀)
- 실무에서는 앞에 웹 서버를 두고, 정적 파일은 웹 서버가, 동적 요청은 WAS가 처리하도록 나누는 경우가 많다.

### 다시 정리: 네 가지의 관계 (추가 질문)

**먼저 둘로 나누기**
- **코드**: JSP, JavaScript → 누군가 실행해 줘야 하는 프로그램
- **서버**: 웹 서버, WAS → 요청을 기다렸다가 응답하는 프로그램 (서버 컴퓨터에서 돈다)

**짝으로 기억하기**
- JSP는 **WAS**가 실행한다. WAS 없이는 JSP가 돌지 않는다.
- JavaScript는 **브라우저**가 실행한다. 웹 서버·WAS는 JS 파일을 실행하지 않고 보내기만 한다.
- **웹 서버**는 이 구조에서 코드를 실행하지 않는다. 이미 있는 파일은 바로 보내고, JSP 요청은 WAS로 넘긴다.

**그림**
```
브라우저 (JavaScript 실행)
   ↕
웹 서버 (파일 전달, JSP는 WAS로)
   ↕
WAS (JSP 실행 → HTML)
   ↕
DB
```
※ 웹 서버는 빼도 된다. Tomcat 같은 WAS가 파일 전달도 할 수 있어서, 연습할 땐 WAS 하나면 충분하다.

**요청 따라가 보기**
- `list.jsp`: 웹 서버가 WAS로 넘김 → JSP 실행(DB 조회) → HTML이 브라우저로
- 그 HTML 속 `app.js`, `logo.png`: 브라우저가 다시 요청 → 웹 서버가 파일 그대로 보냄 (WAS는 쉼) → `app.js`는 브라우저에서 실행

**식당으로 비유하면**
- 웹 서버 = 카운터: 미리 만들어 둔 것은 바로 건네고, 요리 주문은 주방으로 넘긴다
- WAS = 주방
- JSP = 주방의 레시피: 손님은 레시피를 볼 수 없고, 완성된 요리(HTML)만 받는다
- JavaScript = 손님에게 주는 "자리에서 이렇게 하세요" 안내 카드: 따라 하는 건 손님 자리(브라우저)다. 레시피와 달리 손님도 볼 수 있다. 요리에 끼워 오기도 하고(HTML 속 `<script>`), 카운터에서 따로 받기도 한다(`app.js`). 더 필요하면 다시 주문(새 요청)한다

**웹 서버와 WAS를 왜 나누나**
- 이미 있는 파일은 웹 서버가 빨리 보내고, WAS는 JSP 실행에만 집중한다.
- WAS가 인터넷에 직접 노출되지 않아 더 안전하다.
- WAS를 여러 대 두면 웹 서버가 요청을 골고루 나눠 준다 (로드 밸런싱).

### Node.js (추가 질문: 원래 궁금했던 것)

**한 줄 요약**
Node.js는 언어가 아니라, JavaScript를 **브라우저 밖에서** 실행해 주는 프로그램이다. 덕분에 JavaScript로 **서버**도 만들 수 있다.

**앞의 짝에 넣어 보면**
- JSP(Java) → **WAS**가 실행
- JavaScript → **브라우저**가 실행
- JavaScript → **Node.js**가 실행 ← 새 짝

단, Node.js는 켜기만 해서는 서버가 아니다. 내 서버 코드를 실행해야 서버가 된다. (아래 "Node.js와 NestJS" 참고)

**같은 JavaScript, 할 수 있는 일은 다르다**
Chrome 안에서 JavaScript를 실행하던 부분(V8 엔진)을 떼어 내고, 파일·네트워크 기능을 붙여 브라우저 없이 돌게 만든 것이 Node.js다. 그래서 누가 실행하느냐에 따라 쓸 수 있는 기능이 다르다.
- 브라우저의 JavaScript: 화면을 바꿀 수 있다 (`document.getElementById` 같은 `document` 기능). 서버의 파일이나 DB에는 직접 손대지 못한다.
- Node.js의 JavaScript: 파일 읽기·쓰기, DB 연결, 요청 받기가 된다. 대신 화면이 없어서 `document`는 쓸 수 없다.

**Node.js가 쓰이는 두 가지**
1. **서버 만들기**: JSP + Tomcat 자리를 JavaScript + Node.js가 대신한다. Tomcat은 켜기만 하면 요청을 기다리는 서버라 JSP만 넣으면 되지만, Node.js는 내 서버 코드를 실행해야 서버가 된다. 그 코드가 요청을 받아 HTML이나 데이터(JSON)를 돌려준다 (보통 Express·NestJS 같은 틀로 짠다). 그래서 Tomcat 같은 WAS를 따로 설치하지 않는다.
2. **개발 도구 돌리기**: 서버를 만들지 않아도 Node.js를 설치하는 경우가 많다. `npm`(남이 만든 코드를 내려받는 도구)과, React·Vue로 짠 화면 코드를 브라우저용 JS 파일로 묶어 주는 도구(Vite 등)가 Node.js로 돌기 때문이다. React·Vue 자체는 브라우저에서 돈다.

**그림 (Node.js로 서버를 만든 경우)**
```
브라우저 (화면용 JS 실행)
   ↕
웹 서버 (Nginx, 없어도 됨)
   ↕
Node.js + 내 서버 코드
(서버용 JS 실행 → HTML/JSON)
   ↕
DB
```
※ Node.js 서버도 브라우저용 JS 파일(앞의 `app.js`)은 실행하지 않고 그대로 보낸다. Node.js가 실행하는 것은 서버용 JS 파일뿐이다.

**헷갈리지 않기: 둘 다 JavaScript여도 따로 돈다**
서버용 JavaScript(Node.js)와 화면용 JavaScript(브라우저)는 같은 언어지만 따로 도는 별개의 프로그램이다. 내 컴퓨터 한 대에서 둘 다 띄워 연습해도 마찬가지다. JSP 때와 똑같이, 브라우저 JavaScript가 서버의 변수를 직접 바꿀 수 없고 **요청**으로 주고받는다.

**왜 Node.js를 쓰나**
- 화면과 서버를 한 언어(JavaScript)로 만들 수 있다.
- WAS는 요청마다 일꾼(스레드)을 붙이지만, Node.js는 일꾼 하나가 DB 응답을 기다리는 동안 다른 요청을 먼저 처리한다. 그래서 기다림이 많은 요청(DB 조회, 채팅 등)을 많이 받는 데 강하다.

### Node.js와 NestJS (추가 질문)

**정리하면**
- **NestJS는 Node.js 안에 없다.** `npm`으로 따로 설치하는 틀이다. Node.js 안에 처음부터 있는 것은 요청을 받는 기본 부품(`http`)뿐이다.
- **Node.js는 켜기만 해서는 서버가 아니다.** JS를 실행하는 실행기라서, 내 코드가 "요청을 기다려라"(`listen`)라고 해야 서버가 된다.
- Tomcat은 다르다. 켜기만 해도 내 코드 없이 8080번 포트에서 요청을 기다린다.
- 그래서 Node.js가 내 코드(NestJS 등)를 실행하고 있을 때, 그 실행 중인 프로그램이 서버다.

**Node.js 안에 있는 것: 기본 부품**
```js
const http = require('http');
http.createServer((req, res) => {
  res.end('hello');
}).listen(3000);
```
`require`로 부품을 불러오고, 요청(req)이 오면 응답(res)으로 hello를 보낸다. 이 코드를 `server.js`로 저장해 `node server.js`로 실행하면, 3000번 포트(서버의 문 번호)에서 요청을 기다리는 서버가 된다. 마지막 `listen(3000)`이 없으면 아무 요청도 기다리지 않는다.

**NestJS, Express: 따로 설치하는 틀**
- 기본 부품만으로 서버를 짜기엔 번거로워서 만든 **틀(프레임워크)** 이다. 둘 다 `npm`으로 설치한다.
- Express는 주소별로 할 일 나누기를 쉽게 해 주는 단순한 틀이다.
- NestJS는 그 위에 입력값 검사, DB 연결 같은 것을 정해진 구조로 붙이게 해 주는 큰 틀이다.

**층으로 보면** (1~4는 위가 바로 아래를 쓰고, 5가 전부를 실행한다)
1. 내 코드: NestJS 규칙대로 작성
2. NestJS: 큰 틀 (npm 설치)
3. Express: 단순한 틀. NestJS가 기본으로 안에서 쓴다 (npm 설치)
4. `http` 부품: Node.js에 처음부터 들어 있음
5. Node.js: 1~4를 모두 실행하는 실행기

**NestJS 앱의 자리**
NestJS로 만든 앱은 처음 그림의 **WAS 자리**에 들어간다 (Node.js 그림의 "Node.js + 내 서버 코드" 칸). Tomcat 같은 WAS를 따로 설치하지 않을 뿐, 하는 일은 WAS와 같다. 세션, DB 연결 관리처럼 WAS가 해 주던 일은 NestJS나 다른 npm 패키지로 붙인다.

일상에서는 이것도 "웹 서버"라고 부르지만, 이 노트에서 웹 서버는 파일 전달과 요청 중계(HTTPS, 로드 밸런싱)를 맡는 Nginx 같은 것을 뜻한다.

**Java 쪽과 나란히**
- 요청 받기: Tomcat ↔ Node.js의 `http` 부품
- 서버 코드 틀: Spring ↔ Express, NestJS

NestJS는 구조가 Spring과 많이 닮았다. 요즘 Spring Boot는 Tomcat을 앱 안에 넣어 함께 실행해서, Node.js + NestJS와 모양이 비슷하다.

### WAS가 필요한 세상일까? (추가 질문)

**반은 맞다.**
- 요즘 서비스는 로그인, 검색, 결제처럼 요청마다 결과가 달라진다. 그래서 **WAS 역할**(코드를 실행해 결과를 만드는 일)이 없는 서비스는 거의 없다.
- 그런데 **웹 서버도 사라지지 않았다.** Nginx 같은 웹 서버는 지금도 많은 서비스의 맨 앞에서 암호화(HTTPS), 파일 전달, 요청 나눠 주기(로드 밸런싱)를 맡는다. 이미지·JS 파일은 CDN(세계 곳곳에 복사본을 두고 가까운 곳에서 보내 주는 서비스)이 맡기도 한다.
- 바뀐 것은 **WAS의 모양**이다. 예전엔 Tomcat·JEUS 같은 WAS를 따로 설치하고 그 안에 내 코드를 넣었다. 지금은 Spring Boot나 Node.js처럼 **WAS 역할이 내 앱 안에 들어가** 앱 하나로 실행하는 경우가 많다.
- 화면을 만드는 곳도 옮겨 갔다. 예전엔 서버(JSP)가 HTML을 다 만들었지만, 요즘은 서버는 데이터(JSON)만 주고 브라우저의 JavaScript(React 등)가 화면을 그리는 경우가 많다. 다만 Next.js처럼 Node.js 서버가 다시 HTML을 만들어 보내는 방식(SSR)도 많이 쓴다.

정리: "WAS만 필요한 세상"이라기보다, **WAS 역할은 어디에나 있고(이제는 앱 안에), 웹 서버는 맨 앞 카운터로 남은 세상**이다.

### WAS의 역사 (추가 질문)

**큰 흐름 먼저**
파일 전달(웹 서버) → 요청마다 프로그램 실행(CGI) → 프로그램을 띄워 두기(서블릿·JSP) → 크고 표준화된 WAS(J2EE) → 가볍게(Spring) → WAS가 앱 안으로(Node.js, Spring Boot)

※ 앞 단계가 사라진 게 아니라 위에 쌓였다. 웹 서버도, Tomcat·JEUS 같은 전통 WAS도 지금 함께 쓰인다.

**1. 파일만 보내던 시절 (1990~)**
- 첫 웹 서버(CERN httpd)는 미리 만든 HTML 파일을 보내 주기만 했다. 누가 와도 같은 페이지였다.

**2. CGI: 요청마다 프로그램 실행 (1993~)**
- 웹 서버가 요청을 바깥 프로그램(C, Perl 등)에 넘겨 실행시키고, 그 출력(HTML)을 받아 돌려준다. 이 방식을 공통 규칙(CGI)으로 정해서, 어느 웹 서버에서나 요청마다 다른 결과를 만들 수 있게 됐다.
- 문제: 요청이 올 때마다 프로그램을 새로 켰다 껐다 해서 느리고 무거웠다.

**3. 프로그램을 띄워 두기 (1995~1999)**
- 배경: 1995년에 Apache 웹 서버, PHP(처음엔 CGI 방식), Java, JavaScript(브라우저용)가 나왔다.
- 1996: 마이크로소프트 ASP. HTML 속에 코드를 넣는 방식이다.
- 1997: Java **서블릿**. 프로그램을 한 번 띄워 두고 요청마다 일꾼(스레드)만 붙이는, CGI의 느림에 대한 Java 쪽 해결책이다. (비슷한 때 FastCGI 같은 다른 해결책도 나왔다.)
- 1999: **JSP** 1.0. 서블릿에서 HTML을 한 줄씩 찍어 내던 불편을 줄이고 ASP에 맞서려고, HTML 속에 Java를 넣는 방식이 나왔다. 같은 해 Sun이 서블릿·JSP 실행 코드를 공개해 **Tomcat**이 나왔다.

**4. 애플리케이션 서버 전성기 (1999~2000년대)**
- 1999: **J2EE**. Java로 기업용 시스템을 만드는 표준 묶음(서블릿, JSP, EJB, DB 연결 등)이다. 이 중 EJB(업무 로직을 서버가 관리해 주는 부품)가 크고 무거운 부분이었다.
- 이 표준을 모두 갖춘 큰 서버가 **애플리케이션 서버**다. 상용으로 WebLogic(BEA, 지금은 Oracle), WebSphere(IBM), 국산 JEUS(티맥스소프트), 무료 오픈소스로 JBoss(지금 WildFly)가 있다.
- Tomcat은 이 중 서블릿·JSP 부분만 갖춘 가벼운 서버(앞에서 말한 서블릿 컨테이너)다. 한국에서는 Tomcat도 WAS라고 부르지만, 영어권에서는 servlet container와 application server를 나눠 부르는 일이 많다. (영어로 "WAS"라고 하면 보통 IBM WebSphere Application Server를 뜻한다.)
- 한국에서는 은행·공공기관을 중심으로 "웹 서버 + WAS" 구성(예: WebtoB + JEUS, Apache + Tomcat)이 널리 쓰였고, "WAS"라는 말도 특히 많이 쓴다.

**5. 가벼워지는 시대 (2004~)**
- 2004: **Spring** 1.0. 무거운 부품(EJB) 없이도 기업용 기능을 쓰게 해 줘서 Tomcat만으로 충분해졌다. "Tomcat + Spring"이 널리 쓰이기 시작했다.
- 2004: **Nginx**. 동시 접속이 많아도 가볍게 버티는 웹 서버.
- 2005: **AJAX**라는 이름이 붙으며 널리 퍼졌다 (기술 자체는 1999년부터 있었다). 이후 서버가 HTML 대신 데이터만 주는 방식이 크게 늘었다.

**6. WAS가 앱 안으로 (2009~)**
- 왜? 서비스를 작은 앱 여러 개로 나누고 클라우드에 자주 배포하게 되면서, 서버마다 WAS를 따로 설치·설정하기보다 앱 하나에 넣어 실행하는 편이 간단해졌다.
- 2009: **Node.js**. 원래 기다림 많은 요청을 일꾼 하나로 처리하려고 만들어졌다. 처음부터 WAS를 따로 두지 않고, 내 코드가 `http` 부품으로 직접 요청을 받는 방식이었다.
- 2014: **Spring Boot** 1.0. Tomcat을 앱 안에 넣어, 앱 파일 하나만 실행하면 서버가 뜬다. Java 쪽도 WAS를 따로 설치하지 않아도 되게 됐다 (기존 WAS에 올리는 방식도 여전히 쓴다).
- 2017: **NestJS**.

**7. 지금 (2020년대)**
- 지금 모습은 위 "WAS가 필요한 세상일까?" 참고.
- JEUS·WebLogic 같은 전통 WAS도 은행·공공기관 같은 큰 시스템에서 지금도 쓰인다.

**오늘 질문과 이어 보면**
JSP를 실행하던 Tomcat(3~4단계)과 NestJS 앱을 실행하는 Node.js(6단계)는 **같은 WAS 자리의 다른 세대**다. 다만 JSP는 HTML을 만들고, NestJS 앱은 보통 데이터(JSON)만 준다.

### 웹 서버의 역사 (추가 질문)

**큰 흐름 먼저**
문서 공유(CERN) → 누구나 쓰는 웹 서버(Apache) → 동시 접속 문제 → Nginx → 클라우드용 새 서버(Caddy 등) → CDN이 맨 앞에 서는 시대

※ 여기서도 앞 세대가 사라진 게 아니라 함께 쓰인다.

**1. 왜 시작됐나 (1989~1993)**
- 1989: CERN(유럽 입자물리연구소)의 팀 버너스리가 웹을 제안했다. 여러 컴퓨터에 흩어진 연구 문서를 링크로 잇자는 아이디어였다.
- 링크를 누르면 그 문서가 있는 컴퓨터가 문서를 보내 줘야 한다. 그래서 컴퓨터마다 "요청을 기다렸다가 문서를 건네주는 프로그램"이 필요했다. 이것이 웹 서버다.
- 1990: 첫 웹 서버(CERN httpd)와 첫 브라우저를 만들었다. 주고받는 규칙(HTTP)과 문서 형식(HTML)도 이때 함께 나왔다.
- 1993: CERN이 웹 기술을 누구나 무료로 쓰게 공개했다. 같은 해 쓰기 쉬운 그림 화면의 브라우저(NCSA Mosaic)도 나와, 웹이 빠르게 퍼졌다.

**2. NCSA → Apache: 누구나 쓰는 웹 서버 (1993~)**
- 1993: 미국 대학 연구소(NCSA)가 웹 서버 NCSA HTTPd를 만들었다. 앞에서 본 CGI도 여기서 나왔다.
- 1995: NCSA HTTPd 개발이 멈추자, 이를 쓰던 관리자들이 각자 고친 코드를 모아 **Apache**를 만들었다. 무료 오픈소스다. 같은 해 마이크로소프트 IIS도 나와 Windows 쪽에서 많이 쓰였다.
- 1996년부터 Apache가 가장 많이 쓰는 웹 서버가 되어 오랫동안 1위를 지켰다.
- 강점은 모듈(나중에 끼워 넣는 추가 기능)을 붙이기 쉽다는 것이다. 예: mod_php를 붙이면 PHP를 Apache 안에서 바로 실행한다.
- 그래서 앞에서 "웹 서버는 이 구조에서 코드를 실행하지 않는다"고 한 것은 웹 서버와 WAS를 나눈 구조(Apache + Tomcat, Nginx + Tomcat) 이야기다. Apache에 mod_php를 붙이면 웹 서버가 WAS 역할까지 한 몸에 맡는다 (카운터 안에 작은 주방이 있는 셈). Nginx도 모듈로 코드를 실행할 수 있다.

**3. 문제: 동시 접속 (1999, C10K)**
- 초기 Apache는 접속 하나마다 일꾼 하나를 붙였다.
- 인터넷이 느린 사용자가 연결을 오래 잡고 있으면 일꾼이 그만큼 묶였다. 일꾼마다 메모리를 차지해서 많이 늘릴 수 없었고, 정해 둔 최대 수에 닿으면 새 접속은 기다려야 했다.
- 1999: 댄 케겔이 "서버 한 대로 동시 접속 1만 개를 어떻게 버틸까?"라는 문제를 정리했다. 이름은 C10K(10K = 1만).

**4. Nginx: 일꾼 몇 명이 수천 연결을 처리 (2004~)**
- 러시아 개발자 이고르 시소예프가 포털 Rambler의 많은 접속을 감당하려고 만들었다. 2004년에 공개했다.
- 방식: 일꾼을 CPU 수만큼만 두고, 일꾼 하나가 수천 개 연결을 번갈아 처리한다. 기다리는 연결에 일꾼을 붙잡아 두지 않으니 메모리를 적게 쓴다.
  - 앞의 카운터 비유로 치면, 초기 Apache는 손님 한 명마다 직원 한 명이 붙어 손님이 메뉴를 고르는 동안에도 옆에서 기다린다. 손님이 몰리면 직원을 계속 늘려야 한다.
  - Nginx는 직원 몇 명이 여러 손님을 번갈아 응대하고, 고민 중인 손님은 두고 준비된 손님부터 처리한다.
- 대세가 된 이유:
  - 파일 전달이 빠르고 가볍다.
  - WAS 앞에서 요청을 대신 받아 뒤의 Tomcat·Node.js로 넘기는 역할(**리버스 프록시**)에 딱 맞았다. HTTPS 처리와 로드 밸런싱도 같이 맡는다.
- 요즘 새로 만드는 서비스에서는 웹 서버 자리에 Nginx가 가장 흔하다 (한국 은행·공공기관에서는 WebtoB·Apache도 여전히 많다). 2020년 전후로 사용 점유율에서 Apache를 앞섰다 (조사마다 다름).
- Apache도 2005년 실험적으로, 2012년 정식으로 비슷한 방식(event)을 넣었다. 다만 처리 중인 요청에는 여전히 일꾼이 하나씩 붙는 절충형이다.

**5. 그 이후 세대: 클라우드 시대 (2015~)**
- 배경 1: 컨테이너(앱을 상자처럼 포장해 어디서나 바로 띄우는 기술, 예: Docker)와 이를 자동으로 관리하는 Kubernetes로 서버가 수시로 생기고 사라졌다. 사람이 설정을 고쳐서는 따라갈 수 없었다.
- 배경 2: HTTPS에 필요한 인증서(사이트가 진짜임을 증명하는 파일)를 Let's Encrypt가 무료로 주면서, 모든 사이트가 HTTPS로 갔다.
- **Caddy** (2015): HTTPS 인증서를 자동으로 받아 붙여 준다. 설정이 아주 짧다.
- **Traefik** (2016): 컨테이너가 뜨고 지는 것을 보고 스스로 설정을 바꾼다.
- **Envoy** (2016): 맨 앞문(웹 서버 자리)으로도, 작은 앱 여러 개로 나눈 구조(WAS 역사 6단계)에서 앱끼리 주고받는 요청의 중계로도 쓰인다. Kubernetes에 들어 있는 건 아니지만 그 환경에서 많이 쓰인다.
- **클라우드 로드 밸런서** (AWS ALB 등): 클라우드 회사가 대신 운영해 주는 앞문. Nginx를 직접 두지 않고 이것을 맨 앞에 두는 경우도 많다.

**6. 엣지: CDN이 맨 앞으로**
- CDN은 1999년(Akamai)부터 있었지만, 2010년대부터 Cloudflare 등이 사이트 전체의 맨 앞문을 맡는 경우가 많아졌다.
- CDN은 세계 곳곳에 둔 서버 중 사용자와 가장 가까운 곳에서 응답한다. 이렇게 사용자 가까이 있는 서버를 **엣지**라고 한다.
- 그래도 내 Nginx와 WAS는 그 뒤에 그대로 있다: 브라우저 → CDN → Nginx → WAS.
- Cloudflare는 Nginx로 하던 일을 직접 만든 프로그램으로 단계적으로 바꿨다 (2022년 Pingora 발표 등). 주된 이유는 Nginx 구조의 한계였고, 새 프로그램은 메모리 실수(보안 구멍의 흔한 원인)를 막아 주는 언어 Rust로 만들었다.
- 엣지에서 코드도 실행한다 (2017년 Cloudflare Workers 등). 앞의 Apache 모듈처럼, 웹 서버(카운터)와 WAS(주방)의 경계가 다시 흐려지고 있다.
- 주고받는 규칙(HTTP)도 HTTP/2(2015), HTTP/3(2022)로 발전해 더 빨라졌고, 웹 서버들이 이를 지원해 가고 있다.

**오늘 질문과 이어 보면**
- 웹 서버의 역할은 "파일을 보내는 곳"에서 "WAS 앞에서 요청을 받아 나눠 주는 카운터"로 넓어졌다.
- Nginx와 Node.js는 같은 방식(일꾼이 기다리지 않고 다른 연결을 처리)을 쓴다. Nginx가 처음 만든 방식은 아니지만, Node.js를 만든 라이언 달은 2009년 첫 발표에서 Apache와 Nginx를 비교하며 이 방식을 설명했다. 다만 Nginx는 일꾼이 여러 명, Node.js는 기본이 한 명이다. 웹 서버의 역사와 WAS의 역사가 여기서 만난다.

### 웹의 발전 단계 (추가 질문)

찾아본 자료의 7단계를 그대로 따라가며, 중간에 붙인 질문 세 개(약자, 엔터프라이즈, script)에 답한다.

**한눈에 보기**
| 단계 | 시기 | 대표 |
|---|---|---|
| 1. 정적 문서 | 1990~ | CERN httpd, Apache |
| 2. CGI | 1993~ | Perl, C 프로그램 |
| 3. 서버 내장형 실행 | 1995~ | PHP, ASP, 서블릿 |
| 4. WAS·엔터프라이즈 | 1999~ | J2EE, WebLogic, JEUS |
| 5. 브라우저 애플리케이션 | 2005~ | AJAX, React |
| 6. API·클라우드 | 2006~ | REST, AWS, 모바일 앱 |
| 7. 그다음 | 지금 | 엣지, AI 에이전트 |

시기는 "흔해지기 시작한 때"다. 앞 단계는 사라지지 않고 함께 쓰인다.

**1. 정적 문서 제공**
- 미리 만든 HTML 파일을 그대로 보낸다. 누가 와도 같은 페이지. (웹 서버의 역사 1단계)

**2. CGI 동적 처리**
- 요청이 오면 웹 서버가 바깥 프로그램을 실행하고 그 결과를 돌려준다. 요청마다 다른 페이지가 가능해졌지만, 매번 프로그램을 새로 켜서 느렸다. (WAS의 역사 2단계)

**3. 서버 내장형 실행 환경 — 영어 약자는?**
- 뜻: 프로그램을 매번 켜지 않고, **웹 서버 안(또는 옆)에 실행 환경을 띄워 둔다.** CGI의 느림을 푼 방법이다.
- 딱 하나로 정해진 약자는 없다. 이 단계를 부르는 말과 약자는 이렇다.
  - **Server-side scripting**: 이 단계 전체를 부르는 가장 흔한 영어 표현 (약자 없음). PHP, ASP처럼 서버에서 도는 스크립트.
  - **SAPI / NSAPI / ISAPI** (Server API): 웹 서버 안에 프로그램을 끼워 넣는 연결 방식의 이름. NSAPI는 넷스케이프, ISAPI는 마이크로소프트 IIS용. PHP도 웹 서버와 붙는 부분을 SAPI라고 부른다.
  - **mod_php, mod_perl**: Apache 안에 끼우는 모듈. 앞의 "카운터 안의 작은 주방".
  - Java 쪽은 **서블릿 컨테이너**가 이 자리다.
- 비슷해 보이지만 다른 약자: **SSI**(Server Side Includes)는 이보다 단순한, HTML에 다른 파일·값을 끼워 넣는 기능이고, **SSR**(Server-Side Rendering)은 훗날(2010년대) "서버에서 HTML을 만든다"는 뜻으로 쓰는 말이다.

**4. WAS와 엔터프라이즈 플랫폼 — 왜 "엔터프라이즈"인가?**
- 엔터프라이즈(enterprise) = **기업**. 이름에 그대로 들어 있다: J2EE = Java 2 Platform, **Enterprise Edition**. Java는 용도별로 판을 나눴다.
  - SE(Standard Edition): 보통 프로그램용
  - EE(Enterprise Edition): 기업 시스템용
  - ME(Micro Edition): 휴대폰 같은 작은 기기용
- 왜 "기업용"이라는 큰 말을 붙였나: 이 단계의 목표가 홈페이지가 아니라 **회사 업무 전체**(주문, 결제, 재고, 인사)를 웹으로 옮기는 것이었기 때문이다. 기업 시스템에는 홈페이지에 없는 요구가 있었다.
  - 돈이 오가는 일은 "전부 성공 아니면 전부 취소"(트랜잭션)가 보장돼야 한다
  - 수많은 직원·고객이 동시에 써도 멈추지 않아야 한다 (서버 여러 대로 묶기)
  - 보안, 권한 관리
  - 이미 있던 메인프레임 같은 옛 시스템과 연결
- 뿌리도 기업 쪽이다. WebLogic을 판 BEA는 원래 기업용 거래 처리 소프트웨어(Tuxedo)를 팔던 회사였고, JEUS를 만든 티맥스소프트도 거래 처리 소프트웨어(Tmax)로 시작했다. 메인프레임 시절의 기업 거래 처리를 웹으로 옮긴 것이 WAS다.
- "플랫폼"인 이유: 서버 한 개가 아니라 **표준 규격 묶음**이다. 규격이 같으니 같은 앱을 WebLogic에도 JEUS에도 올릴 수 있었다.

**5. 브라우저 애플리케이션 — 이것이 script인가?**
- 반은 맞다. **재료는 script(JavaScript)**, 만든 결과가 **애플리케이션**이다.
  - 1995~: script는 HTML에 조금 덧붙이는 코드였다. 입력값 검사, 간단한 효과 정도.
  - 2000년대: Java 애플릿, Flash처럼 브라우저에 플러그인을 깔아 앱을 돌리는 시도(RIA, Rich Internet Application)가 있었다. 지금은 거의 사라졌다.
  - 2005~: AJAX. 새로고침 없이 데이터만 주고받는다. Gmail(2004), Google 지도(2005)가 "웹페이지인데 프로그램 같다"는 느낌을 줬다.
  - 2010~: **SPA**(Single Page Application). 페이지를 한 번 받은 뒤, 화면 전체를 브라우저의 JavaScript가 그리고 관리한다. AngularJS, React, Vue.
- 그래서 "script"는 HTML 위의 작은 코드, "브라우저 애플리케이션"은 브라우저가 화면 전체를 책임지는 프로그램이다. 앞에서 본 "React·Vue는 브라우저에서 돈다"가 이 단계다.

**6. API 클라우드 구조**
- 서버는 화면(HTML) 대신 **데이터(JSON)만 주는 API**가 된다. 주로 REST라는 방식으로 주소별 데이터를 준다.
- 왜?
  - 2007년 아이폰 이후 **모바일 앱**이 생겼다. 웹과 앱이 같은 데이터를 쓰려면 서버가 화면이 아니라 데이터를 줘야 했다.
  - 2006년 AWS 이후 **클라우드**에서 서버를 빌려 쓰게 됐다. 큰 서버 한 대 대신 작은 서비스 여러 개(마이크로서비스)로 나누고, 컨테이너로 띄우고, 서버리스로 관리까지 맡긴다.
- 앞에서 본 "Spring Boot·NestJS 앱이 JSON을 준다", "WAS가 앱 안으로"가 이 단계다.

**7. 그다음은? (예측이라 정답은 없다. 지금 보이는 흐름 세 가지)**
- **실행 위치가 사용자 가까이로: 엣지.** 코드가 내 서버가 아니라 사용자와 가까운 CDN 서버에서 돈다. (웹 서버의 역사 6단계)
- **서버와 브라우저의 재조합.** 화면 만들기가 서버(JSP) → 브라우저(SPA)로 갔다가, 다시 서버로 일부 돌아오고 있다(Next.js의 SSR, React Server Components). 또 WebAssembly로 Java·C·Rust 같은 언어도 브라우저에서 돌릴 수 있게 됐다.
- **API를 쓰는 주체가 AI로.** 지금까지 API를 부르는 쪽은 사람이 쓰는 브라우저와 앱이었다. 이제 AI 에이전트가 사람 대신 API를 부르고 일을 처리한다. AI가 여러 서비스에 붙는 표준(예: MCP, 2024)도 나왔다.

**흐름을 꿰는 두 개의 질문**
- **코드는 어디서 도는가?** 서버(CGI, WAS) → 브라우저(SPA) → 다시 서버와 엣지로. 시계추처럼 오간다.
- **누가 요청하는가?** 사람(브라우저) → 앱(모바일) → AI(에이전트).

10/12에 적은 "AI로 공부하는 것"의 고민이 7단계와 이어진다. 웹의 다음 사용자도 AI가 되어 가고 있다.
