### 한 줄 요약
JSP는 **서버**에서 실행되어 HTML을 만들고, JavaScript는 그 HTML을 받은 **브라우저**에서 실행된다. WAS는 JSP 같은 서버 프로그램을 실행해 주는 서버다.

### 요청 하나가 처리되는 순서
1. 사용자가 브라우저에서 `list.jsp` 주소를 연다.
2. WAS가 요청을 받아 JSP를 실행한다. 이때 Java 코드가 돌고, 필요하면 DB도 조회한다.
3. 실행 결과로 **HTML 문서(텍스트)** 가 만들어져 브라우저로 간다. JSP 코드 자체는 브라우저로 가지 않는다.
4. 브라우저가 HTML을 위에서부터 읽으며 화면을 그리다가, `<script>`를 만나면 그 JavaScript를 실행한다.
5. 그 뒤 버튼 클릭 같은 사용자 동작은 브라우저 안의 JavaScript가 처리한다. 서버의 데이터가 다시 필요하면 새로 요청을 보낸다.
   - 페이지 이동: JSP가 다시 실행되어 새 HTML 전체가 온다.
   - `fetch`/AJAX: 보통 데이터(JSON)만 받아서, JavaScript가 새로고침 없이 화면 일부만 바꾼다.

### JSP
- Java Server Pages. HTML 사이에 Java 코드를 섞어 쓰는 **서버 쪽** 기술이다.
- 처음 요청이 오면 WAS가 JSP를 **순수 Java 프로그램(서블릿)으로 바꾸고 컴파일**한다. 이후엔 그것을 바로 실행하고, JSP를 고치면 (개발 설정에서는 보통) 이 과정을 다시 한다.
- 결과물은 HTML 텍스트일 뿐이다. 브라우저에서 "페이지 소스 보기"를 하면 JSP 코드는 없고 HTML만 보인다.

### JavaScript
- 브라우저 안에서 실행되는 언어다. (서버에서 도는 JavaScript도 있다. 아래 Node.js 참고)
- 서버가 HTML을 보낸 **뒤에** 브라우저에서 실행된다. 화면 요소(DOM)를 바꾸고, 클릭·입력에 반응하고, 서버에 추가 요청을 보낸다.
- 이름이 비슷하지만 Java와는 전혀 다른 언어다.

### 가장 헷갈리는 지점: 실행 순서
```jsp
<% String name = "홍길동"; %>
<script>
  var name = "<%= name %>";
  alert(name);
</script>
```
- `<% %>` 안은 서버에서 도는 Java 코드, `<%= %>`는 그 값을 그 자리에 찍는 표시다.
- 서버에서 JSP가 먼저 실행되어 `<%= name %>` 자리에 `홍길동`이 들어간다.
- 브라우저가 받는 것은 `var name = "홍길동";` 이라는 JavaScript 코드일 뿐이다.
- 그래서 JSP는 JavaScript **코드를 만들어낼** 수는 있지만, 반대로 JavaScript가 JSP 변수를 직접 바꿀 수는 없다. 서버에서 실행이 이미 끝났고, 그 변수도 응답을 보낼 때 사라졌기 때문이다.
- 반대 방향(브라우저 → 서버)은 **새 요청**에 값을 실어 보낸다. 예: `list.jsp?name=김철수`, 폼 전송, `fetch`. 그러면 JSP가 처음부터 다시 실행되고 `request.getParameter("name")`으로 그 값을 읽는다.
- 참고: 사용자 입력을 이렇게 그대로 넣으면 따옴표 때문에 코드가 깨지거나, 남이 넣은 스크립트가 실행될 수 있다(XSS). 그래서 특수문자를 안전한 글자로 바꿔 넣는다(이스케이프). 바꾸는 방법은 넣는 위치에 따라 다르다 (HTML 안인지, 여기처럼 JavaScript 문자열 안인지).

### WAS (Web Application Server)
- 요청이 올 때마다 **프로그램을 실행해서** 응답을 만들어 주는 서버다. 예: Tomcat(가장 많이 씀), JEUS, WebLogic, JBoss(WildFly)
- **웹 서버**(Apache, Nginx)와 비교하면:
  - 웹 서버: 이미 만들어진 파일(HTML, 이미지, CSS, JS)을 그대로 돌려준다 → 정적
  - WAS: JSP·서블릿을 실행해서 상황마다 다른 결과를 만든다 → 동적
- WAS가 하는 일:
  - JSP·서블릿을 실행하고 관리한다 (이 역할을 "서블릿 컨테이너"라고 부른다)
  - 요청마다 일꾼(스레드)을 하나씩 붙여, 여러 사람의 요청을 동시에 처리한다
  - 요청 사이에 "누가 로그인했는지" 같은 사용자별 정보를 기억한다 (세션)
  - DB 연결을 미리 만들어 두고 나눠 쓰게 해 준다 (커넥션 풀)
- 실무에서는 앞에 웹 서버를 두고, 정적 파일은 웹 서버가, 동적 요청은 WAS가 처리하도록 나누는 경우가 많다.

### 다시 정리: 네 가지의 관계 (추가 질문)

**먼저 둘로 나누기**
- **코드**: JSP, JavaScript → 누군가 실행해 줘야 하는 프로그램
- **서버**: 웹 서버, WAS → 요청을 기다렸다가 응답하는 프로그램 (서버 컴퓨터에서 돈다)

**짝으로 기억하기**
- JSP는 **WAS**가 실행한다. WAS 없이는 JSP가 돌지 않는다.
- JavaScript는 **브라우저**가 실행한다. 웹 서버·WAS는 JS 파일을 실행하지 않고 보내기만 한다.
- **웹 서버**는 이 구조에서 코드를 실행하지 않는다. 이미 있는 파일은 바로 보내고, JSP 요청은 WAS로 넘긴다.

**그림**
```
브라우저 (JavaScript 실행)
   ↕
웹 서버 (파일 전달, JSP는 WAS로)
   ↕
WAS (JSP 실행 → HTML)
   ↕
DB
```
※ 웹 서버는 빼도 된다. Tomcat 같은 WAS가 파일 전달도 할 수 있어서, 연습할 땐 WAS 하나면 충분하다.

**요청 따라가 보기**
- `list.jsp`: 웹 서버가 WAS로 넘김 → JSP 실행(DB 조회) → HTML이 브라우저로
- 그 HTML 속 `app.js`, `logo.png`: 브라우저가 다시 요청 → 웹 서버가 파일 그대로 보냄 (WAS는 쉼) → `app.js`는 브라우저에서 실행

**식당으로 비유하면**
- 웹 서버 = 카운터: 미리 만들어 둔 것은 바로 건네고, 요리 주문은 주방으로 넘긴다
- WAS = 주방
- JSP = 주방의 레시피: 손님은 레시피를 볼 수 없고, 완성된 요리(HTML)만 받는다
- JavaScript = 손님에게 주는 "자리에서 이렇게 하세요" 안내 카드: 따라 하는 건 손님 자리(브라우저)다. 레시피와 달리 손님도 볼 수 있다. 요리에 끼워 오기도 하고(HTML 속 `<script>`), 카운터에서 따로 받기도 한다(`app.js`). 더 필요하면 다시 주문(새 요청)한다

**웹 서버와 WAS를 왜 나누나**
- 이미 있는 파일은 웹 서버가 빨리 보내고, WAS는 JSP 실행에만 집중한다.
- WAS가 인터넷에 직접 노출되지 않아 더 안전하다.
- WAS를 여러 대 두면 웹 서버가 요청을 골고루 나눠 준다 (로드 밸런싱).

### Node.js (추가 질문: 질문을 하게 된 이유)

**한 줄 요약**
Node.js는 JavaScript를 **브라우저 밖에서** 실행해 주는 프로그램(실행 환경)이다. 덕분에 JavaScript로 **서버**도 만들 수 있다.

**앞의 짝에 넣어 보면**
- JSP(Java) → **WAS**가 실행
- JavaScript → **브라우저**가 실행
- JavaScript → **Node.js**가 실행 ← 새 짝

Chrome 브라우저 안에서 JavaScript를 돌리던 엔진(V8)을 꺼내서, 브라우저 없이 컴퓨터에서 바로 돌게 만든 것이 Node.js다.

**같은 JavaScript, 할 수 있는 일은 다르다**
- 브라우저의 JavaScript: 화면(DOM)을 바꿀 수 있다. 서버의 파일이나 DB에는 직접 손대지 못한다.
- Node.js의 JavaScript: 파일 읽기·쓰기, DB 연결, 요청 받기가 된다. 대신 화면이 없어서 `document` 같은 것은 없다.

**Node.js가 쓰이는 두 가지**
1. **서버 만들기**: JSP + Tomcat 자리를 JavaScript로 대신한다. 보통 Express 같은 도구로 만든 Node.js 프로그램이 직접 요청을 받아 HTML이나 데이터(JSON)를 돌려준다. 그래서 Tomcat 같은 WAS를 따로 두지 않는다. 앞에 Nginx 같은 웹 서버를 두는 것은 Java 쪽과 같다.
2. **개발 도구 돌리기**: 서버를 만들지 않아도 Node.js를 설치하는 경우가 많다. React·Vue 같은 화면 개발 도구와 `npm`(라이브러리 설치 도구)이 Node.js 위에서 돌기 때문이다. 이때 Node.js는 내 컴퓨터에서 개발을 도울 뿐이고, 결과물인 JS 파일은 결국 브라우저에서 실행된다.

**그림 (Node.js로 서버를 만든 경우)**
```
브라우저 (JavaScript 실행)
   ↕
웹 서버 (Nginx, 없어도 됨)
   ↕
Node.js 앱 (JavaScript 실행 → HTML 또는 JSON)
   ↕
DB
```

**헷갈리지 않기: 둘 다 JavaScript여도 따로 돈다**
서버(Node.js)의 JavaScript와 브라우저의 JavaScript는 같은 언어지만, 서로 다른 컴퓨터에서 도는 별개의 프로그램이다. JSP 때와 똑같이, 브라우저 JavaScript가 서버의 변수를 직접 바꿀 수 없고 **요청**으로 주고받는다.

**왜 Node.js를 쓰나**
- 화면(브라우저)과 서버를 한 언어(JavaScript)로 만들 수 있다.
- 기다리는 시간이 많은 요청(DB 조회, 채팅 등)을 여럿 동시에 처리하는 데 강하다.
