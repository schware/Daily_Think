## 질문: Neo4j와 Backstage를 쓰는 것을 어떻게 생각해야 할까?

### 질문
- Neo4j, Backstage를 이용하는 것에 대해서 어떻게 생각해야 할까?

### Claude

#### 한 줄 답
둘 다 **이미 있는 문서와 지식을 보여 주고 이어 주는 도구**다. 문서도, "내가 하고 싶은 것"도 만들어 주지 않는다. 그래서 10-20의 생각대로 순서는 **문서 → 도구**다. 지금은 두 도구의 **생각 방식**만 가져오고, 도구 자체는 markdown으로 안 풀리는 문제가 실제로 생길 때 들인다.

#### 각각 무엇인가

| | Backstage | Neo4j |
|---|---|---|
| 정체 | 사내 개발자 portal framework (Spotify가 만들고 CNCF incubating project) | graph database (node와 relationship, 질의 언어 Cypher) |
| 푸는 문제 | "서비스가 많아서 누가 무엇을 맡는지, 문서가 어디 있는지 모른다" | "이것을 바꾸면 무엇이 영향을 받나"처럼 **관계 자체**가 질문일 때 |
| 핵심 기능 | Software Catalog, TechDocs, Software Templates, plugin | 관계 탐색, GraphRAG(문서를 graph로 만들어 LLM 검색에 씀) |
| AI agent와 | v1.40부터 Actions Registry + MCP actions plugin. Backstage의 action을 MCP tool로 노출한다 (아직 실험 단계) | Neo4j Labs의 MCP server로 agent가 Cypher를 실행한다. code를 graph로 만드는 MCP server는 community 프로젝트들이다 |

#### Backstage에서 볼 것
- **Software Catalog:** repository마다 `catalog-info.yaml`을 두고 이름, 담당자, 종류(service, library, API), 의존 관계를 적는다. portal이 이것을 모아 목록을 만든다.
- **TechDocs (docs-like-code):** 문서를 code 옆에 둔다. `catalog-info.yaml` + `mkdocs.yml` + `docs/index.md` 구조이고, portal이 이것을 웹 문서로 보여 준다.
- **Software Templates:** 새 project를 표준 구조로 찍어 낸다. 새 repository마다 `CLAUDE.md`, `specs/`, `docs/adr/`가 처음부터 들어가게 할 수 있다.
- **비용:** Backstage는 제품이 아니라 framework다. 직접 운영하려면 Node.js·React app과 database를 띄우고, plugin을 TypeScript로 고쳐 가며 유지해야 한다. 원래 여러 팀이 수십~수백 개 서비스를 다룰 때를 위한 것이다. 관리형 서비스(Spotify Portal, Harness IDP 등)도 있다.

#### Neo4j에서 볼 것
- **관계를 1급으로 다룬다:** "주문 서비스 → 공통 library → 이 ADR" 같은 연결을 질의로 따라간다.
- **AI와 쓰는 방식은 두 가지다.**
  1. GraphRAG: 문서를 entity와 관계로 쪼개 graph에 넣고, LLM이 답할 때 그 graph를 검색한다 (Neo4j 공식 `neo4j-graphrag` package).
  2. MCP: agent가 graph를 직접 질의한다. repository를 file·function·call 관계로 넣는 code graph server도 있다.
- **비용:** graph를 만드는 것보다 **최신으로 유지하는 것**이 일이다. code와 문서가 바뀔 때마다 graph도 다시 만들어야 한다. 그것 자체가 하나의 project가 된다.

#### 어떻게 생각하면 좋을까
1. **원본은 repository, 도구는 보기(view)다.** 주제 6의 원칙 6("프로젝트 지식은 저장소에서 관리한다")대로라면, 진짜 문서는 git의 markdown이다. Backstage는 그것을 모아 보여 주고, Neo4j는 그것에서 만든 index다. 도구 안에서만 고친 지식은 원칙과 어긋난다.
2. **규모를 보자.** 지금 GitHub에는 repository가 41개(그중 archive 11개) 있다. "무엇이 어디 있는지 모르겠다"는 문제는 이미 있다. 다만 그 답이 처음부터 Backstage일 필요는 없다. 표 하나로 먼저 풀 수 있다.
3. **도구를 들이는 것도 project다.** 10-15에 본 "많이 시작하고 끝을 못 낸다"는 패턴에, Backstage 구축이나 Neo4j graph 구축이 또 하나로 들어갈 수 있다. 들인다면 이것도 "명확한 제목"부터 시작한다.
4. **생각 방식은 지금 바로 가져온다. 비용이 거의 없다.**
   - Backstage에서: 각 repository에 "이것은 무엇이고, 무엇에 의존하나"를 적은 짧은 파일 하나 (`catalog-info.yaml` 흉내, 또는 `CLAUDE.md` 맨 위 몇 줄)
   - Backstage에서: 문서는 code 옆에 (`docs/`, `specs/`, `docs/adr/`)
   - Neo4j에서: 문서끼리의 관계를 link로 적는다 (spec → ADR → code). graph가 없어도 Claude는 link를 따라 읽는다.
5. **도구가 필요해지는 신호**
   - Backstage: repository 목록 표를 손으로 맞추기 힘들어질 때, 다른 사람과 함께 쓰게 될 때, 새 project를 같은 구조로 자주 만들 때
   - Neo4j: 여러 repository에 걸친 영향 분석("이 공통 class를 바꾸면 어느 서비스가 깨지나")을 반복해서 해야 할 때. 하나의 repository 안이라면 Claude Code가 code를 직접 읽는 편이 더 정확하고 싸다.

#### 시도해 볼 만한 제목 (예)
- "repository 41개를 표 하나로: 이름, 하는 일, 상태(진행/보관), 다음 할 일"
- "Java platform repository마다 `CLAUDE.md` 맨 위 5줄: 무엇이고 무엇에 의존하나"

## 추가 질문: AI agent가 지원하면 Neo4j는 쓸만한가?

### 질문
- AI agent가 지원하면 Neo4j는 쓸만한가?

### Claude

#### 한 줄 답
**쓸만해진다. 조건이 붙는다.** agent가 Cypher 작성, schema 설계, 질의와 해석을 맡으니 "배우고 만드는 비용"은 크게 준다. 하지만 **graph가 맞는가(정확성)**와 **graph가 최신인가(최신성)**는 agent가 지원해도 남는다. 그래서 graph를 code에서 기계적으로 만들고, 자동으로 다시 만들고, repository 하나로는 답이 안 나오는 질문에 쓸 때 쓸만하다.

#### agent가 바꿔 주는 것
- **Cypher를 몰라도 된다.** agent가 질의를 쓰고 결과를 읽어 준다.
- **연결이 쉬워졌다.** Neo4j 공식 MCP server가 있다 (`get-schema`, `read-cypher`, `write-cypher`). 읽기 전용으로 돌릴 수도 있다 (`NEO4J_MCP_READ_ONLY=true`).
- **시작이 가볍다.** 관리형 Aura는 instance마다 MCP가 들어 있고, Free tier에서도 추가 비용이 없다. 다만 Free는 node 50,000개, relationship 175,000개까지이고 backup이 없다.

#### agent가 지원해도 남는 것
1. **정확성:** LLM이 문서에서 entity와 관계를 뽑으면 틀린 관계가 섞인다. agent는 graph를 믿고 답하므로, 틀린 graph는 없는 것보다 나쁘다.
   - code 구조는 LLM이 아니라 **parser로** 넣는다. Java에는 jQAssistant가 있다. Java project를 scan해서 class, 의존, artifact를 Neo4j graph로 넣는다 (최근 release 2026-02).
2. **최신성:** graph는 code의 사본이다. code가 바뀌면 다시 만들어야 한다.
   - agent에게 맡기기보다 build(CI)에서 매번 scan하게 한다 (`mvn jqassistant:scan`).
3. **질문이 먼저다:** repository 하나 안의 질문은 Claude Code가 code를 직접 읽는 편이 더 정확하고 싸다. graph가 이기는 것은 이런 경우다.
   - 여러 repository에 걸친 의존 ("이 공통 class를 바꾸면 어느 서비스가 영향을 받나")
   - architecture 규칙 위반 찾기 ("controller가 repository를 직접 부르는 곳")
   - 전체 지도 (무엇이 무엇에 기대는가)

#### Sun&Moon에게 맞는 쓰임
Java이고 repository가 여러 개로 나뉘어 있어서, 맞는 쓰임이 두 가지 있다.
- **검증 도구로 (원칙 4 "생성과 검증을 분리한다"):** jQAssistant 규칙은 Cypher로 쓰고 build에서 돈다. Claude가 짠 code가 layer 규칙을 어기면 build가 잡는다. 사람이 정한 규칙을 LLM이 아닌 기계가 확인하니, 독립된 검증이 된다.
- **지도로:** agent가 MCP로 graph에 "이것을 바꾸면 어디가 영향을 받나"를 묻고, 그 결과를 들고 code를 읽으러 간다.

#### 지킬 규칙
- 원본은 code와 문서다. Neo4j는 **언제든 지우고 다시 만들 수 있는 index**로 둔다 (원칙 6).
- agent에게는 처음에 읽기 전용으로 연결한다.

#### 시도해 볼 만한 제목 (예)
- "Java repository 1개를 jQAssistant로 Neo4j에 넣고, 같은 영향 분석 질문을 graph와 code 읽기 두 방식으로 Claude에게 시켜 비교하기"
  - 끝: 두 답이 어디서 같고 다른지 표 하나
  - PC(local)에서 한다. 주제 6을 PC에서 이어 가기로 한 것과 같다.

## 추가 질문: Obsidian 활용법은?

### 질문
- Obsidian을 어떻게 활용하면 좋을까?

### Claude

#### 한 줄 답
Obsidian의 vault는 **markdown 파일이 든 폴더**일 뿐이다. Daily_Think repository를 그대로 vault로 열 수 있다. 그래서 Obsidian은 repository를 보고 쓰는 **창(view)**으로 쓰고, 원본과 기록은 지금처럼 git에 둔다. 오늘 이야기한 Neo4j와 Backstage의 생각 방식을 가장 싸게 해 볼 수 있는 도구이기도 하다.

#### 오늘 이야기와 이어지는 기능

| 오늘 이야기 | Obsidian에서 | 비용 |
|---|---|---|
| Neo4j: 관계를 따라간다 | link + backlinks + graph view. 문서끼리 link를 걸면 무엇이 무엇을 가리키는지 바로 보인다 | 무료, 파일만 |
| Backstage catalog: 목록 표 | **Bases** (core plugin). 각 note의 frontmatter(상태, 다음 할 일 등)를 database 표처럼 보여 준다. `.base` 파일은 YAML이고, data는 그대로 markdown과 frontmatter에 있다 (1.9.10부터 정식) | 무료 |
| daily 정리 | Daily notes core plugin. `daily/YYYY-MM-DD.md` 형식에 맞출 수 있다 | 무료 |
| AI agent와 함께 | vault가 그냥 파일이라 Claude Code가 직접 읽고 쓴다. 1.12.4(2026-02)부터 공식 CLI도 있어서 terminal에서 Obsidian을 조작할 수 있다 | 무료 |

#### iPhone이 가장 어려운 부분
지금 흐름은 "iPhone → Claude Code(cloud) → git"이다. Obsidian iPhone 앱은 기기 안이나 iCloud의 파일을 읽는다. 그래서 git과 맞추는 방법을 골라야 한다.
- **Obsidian Git plugin (iPhone):** 많이 쓰지만, iOS에서 큰 repository를 clone·pull할 때 앱이 죽는다는 보고가 있다 (다른 plugin 작성자의 주장). GitHub API를 쓰는 대안 plugin들은 사용자가 아직 적다.
- **Obsidian Sync (유료):** Standard가 월 $4(연 결제)이고 vault 1개, 1 GB다. PC ↔ iPhone은 안정적이지만, git과 Sync라는 동기화가 두 개가 된다.

**추천:** 역할을 나눈다.
- iPhone: 지금처럼 Claude Code 앱으로 메모와 질문
- PC: Daily_Think clone을 Obsidian vault로 열어 읽고, link를 걸고, 정리한다. git은 PC에서 한다 (desktop의 Obsidian Git plugin은 무난하다).
- 10-15에 정한 것처럼 `index/memo.md`는 한 곳(iPhone)에서만 쓴다.

#### 설정할 때 지킬 것
- **link 형식:** Obsidian 기본값인 `[[wikilink]]`는 GitHub에서 link로 보이지 않는다. 설정(Files & links)에서 wikilink를 끄고 일반 markdown link를 쓰게 하면, GitHub·Claude·Obsidian 셋 다 같은 link를 읽는다.
- **`.obsidian/` 폴더:** vault 설정 폴더가 생긴다. `workspace.json`처럼 자주 바뀌는 파일은 `.gitignore`에 넣는다.
- **public repository:** Daily_Think는 public이다. Obsidian에 개인 메모를 쌓기 시작하면 private vault를 따로 두는 것이 안전하다.
- **원본은 git:** Obsidian 안에서만 쓰는 기능(Canvas, 일부 plugin data)에 중요한 내용을 두지 않는다 (원칙 6).

#### 시도해 볼 만한 제목 (예)
- "PC에서 Daily_Think를 Obsidian vault로 열고, `topics/` 문서끼리 link를 걸어 graph view로 보기"
  - 끝: graph view 화면 1장과, 새로 건 link 목록

## 추가 질문: harness 개념은?

### 질문
- harness 개념은 어떻게 될까?

### Claude

#### 한 줄 답
**agent = model + harness.** model(LLM)은 글을 받아 글을 내놓을 뿐이다. 기억도 없고, 혼자서는 아무것도 실행하지 못한다. 그 model을 일하게 만드는 **나머지 전부**가 harness다. loop, tool, context와 memory, 권한, hook, 검증이 여기에 들어간다. Claude Code 자체가 Claude를 위한 harness다.

#### 말의 뿌리
- harness는 원래 말에 채우는 **마구**다. 힘은 말에서 나오지만, 그 힘을 수레에 전하고 방향을 잡는 것은 마구다.
- software에서는 먼저 **test harness**(test를 돌리고 결과를 모으는 틀)로 쓰였다.
- 지금은 AI agent를 감싸는 실행 환경을 뜻한다.
- 회사 이름 Harness(CI/CD, 10-21에 나온 Harness IDP)와는 다른 이야기다.

#### harness는 두 층이다

| 층 | 누가 만드나 | 무엇이 들어 있나 |
|---|---|---|
| 1. 도구가 주는 harness | Anthropic (Claude Code, Agent SDK) | agent loop, tool(Read·Edit·Bash), context 관리(compaction), permission mode, hook, subagent, MCP |
| 2. 사람이 repository에 만드는 harness | Sun&Moon | `CLAUDE.md`, `docs/`·`specs/`·`docs/adr/`, test, linter, CI, `settings.json`과 hook, 진행 기록 파일 |

2번을 잘 만드는 일을 요즘 **harness engineering**이라고 부른다. engineer가 만드는 것이 code에서 "agent가 일하는 환경과 제약"으로 옮겨 간다는 뜻이다.

#### 두 회사의 사례
- **Anthropic: 오래 걸리는 agent를 위한 harness (2025-11)**
  - 문제: session마다 기억이 끊긴다. 한 번에 너무 많이 하려 들거나, 너무 일찍 "다 됐다"고 한다.
  - 첫 session(initializer): 요청을 **기능 목록(JSON, 처음엔 모두 failing)**으로 펼치고, `init.sh`(실행 방법), 진행 기록 파일, 첫 commit을 만든다.
  - 이후 session(coding): 진행 기록, git log, 기능 목록을 먼저 읽고, 기본 동작을 확인한 뒤 **기능 하나만** 한다. 깨끗한 상태로 commit하고 기록을 남긴다.
  - 기억은 대화가 아니라 **파일과 git**에 있다. 기능 목록을 JSON으로 둔 것은 model이 markdown보다 덜 함부로 고치기 때문이다.
  - 검증: browser 자동화로 사람처럼 끝에서 끝까지 확인한 뒤에만 "통과"로 바꾼다.
- **OpenAI: harness engineering (2026-02, 2차 보도 기준)**
  - 약 5개월 동안 사람이 code를 직접 쓰지 않고 agent로 제품을 만든 실험이다. 사람은 환경을 설계하고 PR과 CI로 방향을 잡았다.
  - `AGENTS.md`는 백과사전이 아니라 **약 100줄짜리 지도(목차)**로 두고, 깊은 내용은 version 관리되는 `docs/`에 둔다. "repository에 없으면 agent에게는 없는 것이다."
  - 규칙은 **기계로 강제**한다. custom linter의 error message가 "어떻게 고치라"까지 알려 준다.
  - 시간이 지나며 생기는 어긋남(entropy)은 정기 점검과 작은 정리 PR로 걷어 낸다.

#### 지금까지의 이야기와 이어 보면
- **주제 6의 7원칙이 사실상 harness engineering이다** ([daily 2026-10-15](2026-10-15.md)).
  - 원칙 3 명세, 원칙 6 repository 지식 → 문서 층
  - 원칙 4 생성과 검증 분리 → test, linter, review agent
  - 원칙 5 자율성은 위험에 비례 → permission, hook, sandbox
- **10-20 "문서 정리가 먼저"** = harness의 첫 부품을 만드는 일이다.
- **오늘의 jQAssistant 규칙** = "기계로 강제"하는 부품이다.
- **실제 예가 지금 이 session에 있다.** 응답이 끝날 때마다 나오는 Stop hook("commit하고 push하라")은 cloud 환경이 넣은 harness다. `CLAUDE.md`의 "git은 Sun&Moon이 한다"는 Sun&Moon이 만든 harness다. 둘이 부딪히고 있어서, harness도 서로 맞춰야 하는 설계물이라는 것을 보여 준다.
- **harness는 고정이 아니다.** Anthropic은 model이 좋아지면 예전에 필요했던 장치가 짐이 된다고 말한다 (예: Sonnet 4.5에 필요했던 context reset이 Opus 4.5에서는 필요 없어짐). 만들고, 쓰고, 덜어 낸다.

#### 시도해 볼 만한 제목 (예)
- "Java repository 1개에 최소 harness 붙이기: `CLAUDE.md` 100줄 이하 지도 + build·test 명령 + 기능 목록 JSON(모두 failing) + 진행 기록 파일"
  - 끝: 새 session이 그 파일들만 읽고 기능 하나를 통과시키는 것

## 생각: XML, Markdown, YAML로 Claude Code에 접근해 보기

### 생각
- XML, Markdown, YAML로 Claude Code에 접근해 보겠다.

### Claude

#### 한 줄 답
좋은 출발점이다. 사람이 만드는 harness(앞 질문의 2층)는 거의 전부 이 세 형식과 **JSON**으로 되어 있다. 핵심은 **형식마다 맡는 자리가 다르다**는 것이다. Markdown은 본문, YAML은 짧은 설정, XML은 prompt 안의 경계, JSON은 기계가 읽는 설정과 상태를 맡는다.

#### 형식별 자리

| 형식 | Claude Code에서 쓰는 곳 | 누가 주로 읽나 |
|---|---|---|
| Markdown | `CLAUDE.md`, `.claude/rules/*.md`, skill·subagent의 본문, `specs/`, `docs/adr/` | 사람과 Claude 둘 다 |
| YAML | Markdown 맨 위 **frontmatter**(`---`로 감싼 부분). skill, subagent, rule의 설정. 그 밖에 GitHub Actions, `catalog-info.yaml`, Obsidian `.base` | Claude Code(설정으로 읽음) |
| XML | prompt나 본문 안에서 섞인 내용을 나누는 **tag** (`<instructions>`, `<context>`, `<example>`, `<document>`) | Claude |
| JSON | `.claude/settings.json`(권한, hook), `.mcp.json`, Anthropic harness의 기능 목록 | Claude Code와 program |

- **Markdown:** `CLAUDE.md`는 200줄 이하를 권장한다. `@path`로 다른 파일을 불러올 수 있지만, 불러온 파일도 시작할 때 다 읽히므로 context 비용은 같다.
- **YAML frontmatter:** 파일의 첫 줄이 `---`여야 한다. **모르는 field는 error 없이 무시된다.** 오타나 대소문자가 틀리면 조용히 효과가 없다.
  - 예: skill은 `allowed-tools`(kebab-case)를 쓰고, subagent는 `disallowedTools`(camelCase)를 쓴다.
- **XML:** Anthropic 공식 문서가 권하는 방식이다. 정해진 tag 이름은 없으니 내용을 설명하는 이름을 일관되게 쓴다. 문서 전체를 XML로 쓰기보다 Markdown 안에서 경계가 필요한 곳에만 쓴다. Anthropic은 model이 좋아질수록 형식이 덜 중요해진다고도 말한다. 필수가 아니라 유용한 도구다.
  - Java에서는 `pom.xml`, jQAssistant 규칙처럼 Claude가 **읽고 고치는 대상**으로도 XML을 만난다.
- **JSON:** 권한과 hook은 JSON이다. `CLAUDE.md`는 Claude가 참고하는 context일 뿐 강제가 아니다. 반드시 막아야 하는 것은 `settings.json`의 deny나 hook으로 막는다.

#### 세 형식이 한 파일에: subagent 예
`.claude/agents/spec-reviewer.md` (원칙 4 "생성과 검증을 분리한다"의 검토 agent)

```markdown
---
name: spec-reviewer
description: specs/ 명세를 구현 전에 검토한다. 명세를 쓴 뒤에 쓴다.
tools: Read, Grep, Glob
model: sonnet
---

# 역할
명세를 읽고 빠진 것을 찾는다. code는 고치지 않는다.

<checklist>
- 인수 조건을 test로 확인할 수 있는가
- 바꾸면 안 되는 것이 적혀 있는가
- 완료 조건이 한 줄로 있는가
</checklist>

<output_format>
문제 목록만 bullet로 쓴다. 없으면 "없음".
</output_format>
```

- 위의 `---` 사이가 YAML(설정), 아래가 Markdown(본문, 이 agent의 system prompt), 그 안의 tag가 XML(경계)이다.

#### Java용 path rule 예
`.claude/rules/java.md`: Java 파일을 다룰 때만 읽힌다.

```markdown
---
paths:
  - "**/*.java"
---

# Java 규칙
- build와 test는 `./mvnw verify`로 확인한다.
- controller에서 repository를 직접 부르지 않는다.
```

#### 작게 시작하는 순서
1. `CLAUDE.md` (Markdown): 무엇인지, build·test 명령, 바꾸면 안 되는 것
2. `.claude/rules/java.md` (YAML + Markdown): Java 파일에만 걸리는 규칙
3. `.claude/agents/spec-reviewer.md` (YAML + Markdown + XML): 검토 agent 하나
4. `.claude/settings.json` (JSON): secret 파일과 운영 명령 deny

#### 시도해 볼 만한 제목 (예)
- "Java repository에 `.claude/` 파일 세 개 만들기: `rules/java.md`, `agents/spec-reviewer.md`, `settings.json`"
  - 끝: 명세 하나를 spec-reviewer가 검토해 문제 목록을 내놓는 것
